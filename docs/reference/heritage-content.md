# 역사관 콘텐츠 기준

제품 범위는 [계획서](../product/planning-proposal.md#역사관-콘텐츠-구성-2026-11-10), 실행 환경은 [replit.md](../../replit.md#역사관-개발-범위)를 따른다. 공개 역사 자료와 회원 전용 사진첩의 저장·참조 계약을 구분한다. 관리자 편집·업로드나 DB 테이블을 추가하지 않는다.

## 공개 자료

`shared/heritage/`의 JSON을 타입이 있는 공통 모듈로 읽는다. 화면·메뉴·소개 요약은 같은 자료를 재사용한다. 원천은 사용자가 지정한 [역대회장 명단](https://app.notion.com/p/rapl/7f284ed2f9b74ea59fb77fb16378f64e)과 [연혁](https://app.notion.com/p/rapl/c619eafe4d514df0a22063d90789b70d)이며, 현 임원은 기존 공개 임원 데이터를 사용한다. 홈페이지에서 Notion을 실시간 조회하지 않는다.

| 자료 | 책임 |
|---|---|
| `presidents.json` | 대수·성명·학번·졸업기수·재임 연도. 원천의 기간 겹침·학번과 기수 차이를 추정 보정하지 않음 |
| `timeline.json` | ID·기록일·제목·설명·기사 링크·회장 대수·기부 기록·앨범/문서 ID. 연혁과 기부 목록의 공통 원본 |
| `officers.json` | 대수별 직책·성명·확인된 기수/설명/사진. 현 임원 화면도 재사용 |
| `awards.json` | ID·기록일·수여 기관·상명·졸업생 수상자·공적·앨범 ID |
| `documents.json` | 문서 ID·제목·공개 승인된 파일 경로 |

기록일은 연도·월·일 중 자료에 있는 범위만 저장한다. 기사 링크의 날짜는 제공된 연혁의 기록일이며 기사 본문에서 행사일을 재확인한 것으로 취급하지 않는다. 기부 금액·주체·목적은 확인된 값만 기록하고 결의와 전달·기탁·기부를 구분한다. 근거 없는 기부액 합계나 미확인 기부자 이름을 만들지 않는다.

공개 문서는 `client/public/documents/heritage/`에 두고 해당 연혁에서 연결한다. 사진첩 원본과 회원 자료를 이 디렉터리나 `client/public/`, `attached_assets/`, 공유 JSON에 넣지 않는다. 기존 공개 임원 사진은 별도 공개 자료로 유지한다. 2026-11-14 사용자가 다음카페 역대임원진 31건의 공개 반영을 승인했다. 해당 사진은 `client/public/images/executives/`에 두고 기존 대수·직책·성명 항목에 연결한다. 재임 기간은 기존 확정 명단을 우선하며 원문 기간과의 차이는 로컬 이관 기록에 남긴다. 원본의 ‘이미지 없음’ 대체 그림은 인물 사진으로 등록하지 않는다.

## 회원 전용 사진첩

2026-11-14 사용자 결정으로 사진첩 목록·앨범 상세·사진 원본은 로그인한 승인 회원만 볼 수 있다. 일반회원과 권리회원 모두 이용하며 로그인·승인 상태는 기존 서버 정책으로 판단한다. 다른 역사관 메뉴는 공개 상태를 유지한다.

- `/about/heritage/albums`와 메뉴 순서·연도 필터·`album` 쿼리는 유지한다. 비로그인 방문에는 기존 로그인 안내를 표시한다.
- 서버 최초 HTML과 클라이언트 모두 고정된 사진첩 메타데이터와 `noindex, nofollow`를 사용한다. canonical은 사진첩 목록 경로이며 사이트맵에서는 제외한다. 실제 제목·사진은 공개 HTML·메타데이터에 넣지 않는다.
- `GET /api/heritage/albums`는 승인 회원 세션을 확인한 후 목록과 사진 설명·앱 내부 사진 주소를 반환한다. `GET /api/heritage/photos/:id`도 같은 인증 후 목록에 연결된 사진만 반환한다. 쿠키 없는 직접 주소 접근은 차단한다.
- 기존 Object Storage의 비공개 영역을 사용한다. `PRIVATE_OBJECT_DIR/heritage/development/`와 `heritage/production/`을 분리하고 `REPLIT_DEPLOYMENT="1"`일 때만 production을 읽는다. 공개 버킷·공개 서명 URL을 만들지 않는다.
- 각 환경의 `catalog.json`이 사진첩 정본이다. `schemaVersion: 1`, `albums`, `photos`를 저장한다. 앨범은 `id`, `title`, `date`, 선택 `description`, `coverPhotoId`, 순서 있는 `photoIds`; 사진은 `id`, `caption`, 선택 `credit`, `file`을 갖는다. `file`은 같은 영역의 `photos/<SHA-256>.<jpg|png|webp|gif>`를 가리키는 파일명이다. 임의 URL·경로 이동·인증정보를 허용하지 않는다.
- 목록은 2 MiB 이하이며 날짜·고유 ID·대표 사진과 참조 관계를 서버에서 검증한다. 모든 사진은 앨범에 속해야 한다. 목록이 없으면 빈 목록으로 표시하고, 읽기 실패나 잘못된 목록은 빈 목록으로 숨기지 않는다. 서버는 최대 60초 동안 읽은 목록을 재사용하되 각 요청의 인증은 생략하지 않는다.
- 목록·사진 응답은 `private, no-store`로 처리한다. 사진은 기존 형식 제한·`nosniff`·스트리밍을 재사용한다. 브라우저에 Object Storage 경로·접속정보나 원본 사이트의 인증정보를 보내지 않는다.

## 사진첩과 자료 연결

- 최근 앨범은 한국 시각의 올해를 포함한 최근 5개 연도다. 전체·이전 연도 목록을 제공하며 5년을 보존 기간으로 해석하지 않는다.
- 사진은 기존 Dialog로 확대한다. 뒤로가기와 원래 사진 버튼의 포커스를 유지한다.
- 연혁·수상·기부는 앨범 ID만 참조한다. 공개 화면에서는 제목·대표 사진을 조회하지 않고 ‘관련 사진첩’ 링크로 연결한다. 기부는 해당 연혁의 앨범 참조를 재사용한다.
- 다음카페 동창회앨범 52건은 회원 전용 사진첩 이관 대상이다. `posts`에 넣거나 글당 40개 이미지 제한으로 나누지 않는다. 수상자와 미제공 자료에는 임의의 인물·사진·예시 앨범을 넣지 않는다.

## 자료 추가와 확인

공개 자료는 소스 변경과 릴리스로 반영한다. 사진첩은 승인된 대상 환경에 최종 목록·사진만 저장한다. 원본 백업·이관 SQLite는 로컬에 보존하며 Replit에 복사하지 않는다. 기존 원격 목록이 있으면 먼저 대조한다. 사진의 형식·해시·크기와 목록 참조를 확인하고 사진을 저장한 뒤 목록을 마지막에 반영한다. 원본 ID/대상 ID와 적용 해시는 로컬 이관 기록에 남긴다. 개발 이관은 운영 영역의 변경이나 배포를 뜻하지 않는다.

`node scripts/check-heritage-content.mjs`는 공개 JSON·참조 ID 형식·날짜·공개 문서 파일을 읽는 정적 검사다. 비공개 앨범의 존재 여부는 확인하지 않는다. `node --import tsx scripts/check-heritage-catalog.ts <catalog.json>`은 지정한 최종 목록 파일의 구조와 참조를 검사하며 Storage·DB·회원 API를 호출하지 않는다. 공개 기록의 앨범 ID 존재 대조는 해당 환경의 최종 목록과 함께 자료 반영 시 수행한다. 타입·변경 파일 lint·서식 검사는 필요한 범위로 Replit 개발 환경에서 수행한다.

기존 공개 구조의 적용 이력은 [2026-11-10 개발 기록](../history/heritage-2026-11-10.md)과 [2026-11-11 릴리스 기록](../history/heritage-release-2026-11-11.md)에 보존한다. 회원 전용 변경의 실제 적용·검사 범위는 [2026-11-14 개발 기록](../history/member-albums-2026-11-14.md)에서 구분한다.
