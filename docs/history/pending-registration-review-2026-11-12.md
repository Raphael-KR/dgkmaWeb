# 가입 승인 명부 대조 표시

- 목표: 관리자 가입 승인 대기에서 신청자별 명부 대조 근거를 확인한다.
- 범위: 기존 관리자 목록 API와 심사 카드, 공통 데이터 계약. 앞선 반응형·프로필·배지 미커밋 변경은 보존한다.
- 완료 조건: 대기 사유·현재 대조·후보·승인 가능 여부·재대조를 Replit 개발 사본에 반영한다.
- 제외: 승인 정책 완화, 실제 신청 승인·거절, DB 구조·데이터 변경, Sheets 조회·동기화, 운영 배포·실계정 QA.
- 검사: 변경 파일 lint·서식, 앱·변경된 기존 검사 코드의 타입 검사, 문서 링크·공백. 앱·DB·HTTP 실행형 검사는 수행하지 않는다.

## 확인한 누락과 처리 기준

기존 관리자 목록은 이름·이메일·상태·신청일·ID만 반환했다. 승인 트랜잭션의 명부 대조는 이미 있었으나 화면에는 결과가 없었다. 앞선 회원 배지 정리에서 보존한 관리자 통계는 전체 연결 건수이므로 신청자별 대조를 대신하지 못한다.

[제품 정책](../product/planning-proposal.md#회원과-카카오-로그인)을 먼저 보완했다. 서버는 신청 자료의 기존 파서와 이름·전화번호 정규화를 재사용하고, 관련 명부·계정을 읽어 현재 결과를 계산한다. 과거 대기 사유를 현재 승인 불가 사유로 간주하지 않는다. 후보·기수·졸업 정보와 필드 일치·연결 여부를 반환한다. 사용자가 전체 전화번호 표시를 요청하여 신청·명부 번호는 관리자 심사에서 모두 표시하도록 확정했다. 필수 정보가 없으면 자료 보완 필요로 표시하며 추측하거나 자동 보정하지 않는다. 재대조·화면 버튼 상태는 실제 승인 시 재검사를 대체하지 않는다.

## 실행 결과

사용자 추가 결정에 따라 각 이름·전화번호 항목은 일치 시 값 하나와 `일치` 배지를 표시하고, 불일치 시 신청·명부 양쪽 값만 표시하며 별도 불일치 배지를 붙이지 않는다. 서로 다른 글자는 신청 측 연한 노란색·명부 측 연한 파란색으로 강조하며 출처 라벨을 함께 둔다. 원본 값은 유지하고 일치 판정에만 기존 이름·전화번호 정규화를 적용한다. 신청 측에 없는 기수·졸업 정보는 명부 참고 정보로 구분한다.

이어 각 후보 레코드의 명부 정보 전체 표시가 확정됐다. 12개 관리 항목을 관리자 심사 응답에 명시적으로 포함하고 성명·핸드폰 대조와 나머지 참고 정보를 구분한다. 카카오 식별자·신청 원문 JSON·연결된 타인 계정의 개인정보는 반환하지 않는다. 데이터가 일부 없는 기존 신청도 확보된 이름·핸드폰으로 후보를 찾되, 기존 승인 요건이 충족되지 않으면 승인 가능으로 표시하지 않는다.

Replit 개발 사본의 `main`은 로컬과 같은 `e5f167d`였으며 기존 미커밋분을 대조한 뒤 변경 파일만 직접 반영했다. 명부·계정 후보는 신청 묶음에 관련된 자료를 최대 두 조회로 읽고 명시적인 관리자 응답으로 투영한다. 원본 가입 자료 파서는 공통 파일로 옮겼으며 기존 함수 본문과 가입 생성·승인·거절 메서드의 보존을 소스 비교로 확인했다. 읽기 응답은 `no-store`이며 일반 명부·회원 API의 개인정보 계약을 바꾸지 않았다.

TypeScript 실행 셸의 `C.UTF-8` locale 경고는 있었으며 타입 오류는 없었다.

공통 CSS에서 신청 측 노란색·명부 측 파란색 강조 규칙이 실제 생성됐고 CSS 경고는 없었다. 기존 관리자 DTO 검사에는 승인된 전화번호·대조 필드 계약을 반영했으며 실행하지 않고 타입만 검사했다. 기존 합성 자료를 재사용했고 새 회원·명부 시험 데이터나 DB는 만들지 않았다. 결과·명령·입력 해시·문서 검사는 `.superpowers/pending-review-2026-11-12/`에 보관한다.

코드·개발 사본 적용과 실제 실행 상태를 구분한다. 개발 서버 재시작, 브라우저 확인, 실계정·DB 조회 시험, 실제 신청 승인·거절, 커밋·push·운영 배포는 수행하지 않았다. 따라서 캡처 속 신청자의 실제 일치 결과와 새 조회 API·글자 강조의 실행 화면은 미확인이다. 실행 중인 개발 서버에 새 서버 코드를 적용하려면 재시작이 필요하다.
