아래 개발 작업과 후속 운영 작업의 승인·실행을 구분한다.

- 목표: 사용자 요청에 따라 Replit 개발 명부의 개인정보를 백업 없이 삭제한다.
- 범위: Development DB `heliumdb`의 `alumni_database`와 종속 `alumni_name_aliases`, 확인된 해당 명부 원문 백업.

- 제외: 회원 계정·신청·글·댓글·회비·Google Sheets 원본·운영 DB 삭제, 재동기화, 릴리스·실계정 QA.
- 검증: 대상 DB·전후 집계·FK·trigger·컬럼·시퀀스 확인과 문서 정합성. 행 원문과 새 dump·snapshot은 남기지 않는다.

## 결정과 적용 순서

2026-11-12 사용자가 `동문 명부(alumni_database)를 초기화 하라. 백업도 두지 마라. 개인정보라서 완전히 지워져야 한다.`고 요청했다. 직전 작업 대상인 Replit 개발 DB에 적용한다. 일상 동기화의 주소·전화 값 보존과 구분한 명시적 행 삭제이며, 컬럼은 유지한다. 명부의 회원 연결 값도 행과 함께 사라지지만 기존 회원 계정·승인 상태는 변경하지 않는다.

관련 제품 정책·DB 런북·스키마 설명·Replit 안내를 먼저 갱신한다. PG* 기본 개발 연결의 실제 DB와 종속 관계·건수를 확인하고, 두 테이블만 명시하여 트랜잭션에서 비운다. 범위를 넓히는 `CASCADE`는 사용하지 않으며 시퀀스는 재사용 충돌을 피하도록 유지한다. 새 연결에서 결과를 재확인한다. 로컬·Replit 작업 경로의 원문 백업 여부도 확인하며 행 원문을 출력하거나 복제하지 않는다.

## 실행 상태

2026-11-12 09:44 KST PG* 기본 연결에서 `current_database()=heliumdb`를 확인했다. 대상 FK는 명부 → users와 별칭 → 명부 두 개이고 사용자 정의 trigger는 없었다. 명부 3,458건, 별칭 0건, 회원과 연결된 명부 1건이었다. 행 원문 대신 건수·컬럼·FK·trigger·시퀀스만 기록했다.

09:46 KST 기존 명부 동기화와 같은 advisory lock 및 대상 테이블 잠금을 잡고 `TRUNCATE TABLE public.alumni_name_aliases, public.alumni_database CONTINUE IDENTITY RESTRICT`를 한 트랜잭션에서 COMMIT했다. 자동 `CASCADE`, 시퀀스 재시작, 테이블·컬럼 삭제, 백업·snapshot 생성은 하지 않았다. 새 연결의 READ ONLY 조회 결과는 다음과 같다.

## 백업 확인 범위와 남은 한계

새 명부 backup·dump·복구용 snapshot과 행 원문 로그는 만들지 않았다. 로컬·Replit 프로젝트에서 SQL·JSON·내보내기 파일·전송 아카이브의 명부 SQL 데이터 표식과 명부 행 객체를 확인했다. 로컬 953개, Replit 1,114개 파일·아카이브 항목에서 명부 원문 백업을 발견하지 않았고 읽기 오류도 없었다. Replit `/tmp`에는 dgkma·alumni·backup 이름의 작업 경로가 없었다. 원문을 복제하지 않았으며 삭제할 별도 명부 백업 파일도 발견되지 않았다.

검사는 애플리케이션 작업 파일 범위다. `.git` 객체 저장소·의존 패키지·`attached_assets`·플랫폼의 checkpoint·스토리지 사본은 이 파일 검사 결과에 포함하지 않는다. 운영 DB·Google Sheets 원본과 다른 회원 자료는 이번 삭제 대상이 아니다.

2026-11-12 확인한 [Replit 데이터 복구 안내](https://docs.replit.com/features/data-and-storage/data-recovery)는 개발 checkpoint 복구를 기본 제공하고 최대 7일을 안내한다. 제공된 Replit 연결 도구에는 개발 DB 복구 이력을 삭제하는 기능이 없으며, 공개 문서에서도 개발 이력의 즉시 개별 삭제 절차를 확인하지 못했다. **개발 DB의 행 초기화는 완료했으나 Replit 내부 복구 이력·스토리지 사본까지 물리적으로 완전 삭제됐다고 보장할 수 없다.** 그 범위의 즉시 삭제·잔존 여부 확인은 Replit 측 확인이 필요하다. 앱이나 전체 DB를 제거하는 작업, 복구 실행·지원 문의 전송은 수행하지 않았다.

개인정보 없는 실행 근거는 Git 제외 경로 `.superpowers/alumni-reset-20261112/`의 `development-before.json`, `reset-result.json`, 로컬·원격 백업 검사 집계에 남겼다. 실제 명부 동기화·운영 DB 작업·배포·실계정 QA·커밋·push는 하지 않았다.

## 운영 명부 초기화

- 목표: 후속 사용자 요청에 따라 운영 명부에 데이터가 있으면 백업 없이 삭제한다.
- 범위: Production DB `neondb`의 `alumni_database`와 종속 `alumni_name_aliases`, 확인된 해당 명부 원문 백업.
- 완료 조건: 새 운영 DB 연결에서 두 테이블 0건, 다른 업무 자료·구조·시퀀스 유지, 백업 확인 범위와 플랫폼 한계 보고.
- 제외: 회원 계정·신청·글·댓글·회비·Google Sheets 삭제, 개발 DB 재변경, 자동 재동기화, 배포·실계정 QA.
- 검증: 명시적 운영 연결과 DB 이름·건수·종속 관계 확인 → 대상 잠금과 단일 트랜잭션 → 새 연결 검증. 원문·dump·새 snapshot은 남기지 않는다.

2026-11-12 개발 초기화 완료 후 사용자가 운영 DB도 같은 방식으로 초기화하도록 명시했다. 앞선 개발 작업의 운영 제외는 해당 작업의 범위이며 이번 승인으로 운영 명부만 새 대상이 됐다. 관련 기준 문서에 백업 없는 운영 삭제 예외를 먼저 반영했다.

운영 DB는 PITR·예약 백업이 별도로 제공된다. SQL 행 삭제를 과거 복구 이력의 삭제로 보고하지 않는다. 명부만 지우는 범위를 다른 업무 자료의 복구 이력 전체 삭제·운영 DB 제거로 확대하지 않으며, 제공된 연결 도구와 공식 절차로 확인 가능한 범위를 기록한다.

### 운영 실행과 확인

09:53 KST 운영 owner 연결에서 같은 동기화 advisory lock과 두 테이블의 배타 잠금을 잡았다. 대상 DB·행 수·trigger 조건을 재확인한 뒤 명시한 두 테이블만 `TRUNCATE ... CONTINUE IDENTITY RESTRICT`로 비우고 COMMIT했다. 새 READ ONLY 연결에서 다음 결과를 확인했다.

대상 컬럼·FK·trigger 유무·시퀀스 값은 전후 동일했다. 기존 회원의 명부 연결 행은 사라졌지만 회원 계정·승인 상태·업무 자료를 수정하지 않았다. 개발 PG* 기본값은 유지했고 개발 DB를 다시 변경하지 않았다. 앱 코드·서버 재시작·배포·실계정 QA·명부 재동기화는 수행하지 않았다.

작업 파일·아카이브의 원문 백업 검사를 갱신했다. 로컬 979개·Replit 1,114개 항목에서 명부 SQL 데이터 표식이나 명부·별칭 행 객체를 발견하지 않았고 읽기 오류도 없었다. 위 개발 기록과 같은 검사 제외 범위를 유지하며, 별도 명부 원문 백업의 삭제 대상은 발견되지 않았다. 새 백업은 만들지 않았다.

**운영 DB의 현재 명부 행 삭제는 완료했지만 운영 PITR·예약 백업·플랫폼 스토리지의 과거 사본까지 완전 삭제했는지는 미확인이다.** 공식 데이터 복구 안내는 DB 전체의 PITR 비활성화 설정을 제공하나, 특정 테이블만 과거 이력에서 지우는 기능은 확인하지 못했다. 제공된 Replit 연결 도구에도 복구 이력 관리 기능이 없다. 다른 업무 자료의 복구 이력까지 삭제하거나 운영 DB 자체를 제거하지 않았으며 즉시 완전 삭제의 잔여 범위는 Replit 측 확인이 필요하다.

개인정보 없는 실행 근거는 `.superpowers/alumni-reset-production-20261112/production-before.json`, `production-reset-result.json`, 로컬·원격 백업 검사 집계에 남겼다. 로컬·Replit 기준 문서의 링크와 `git diff --check`로 정합성을 확인하며 운영 배포·Git 게시와 구분한다.
