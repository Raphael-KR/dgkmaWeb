# 가입 승인 상태 전환

- 목표: 인증 완료 → 승인 취소 → 승인 대기, 승인 대기 → 거부 → 승인 거부 → 재심사 → 승인 대기. 승인 거부 → 삭제 → 신청정보·카카오 연결 해제도 지원한다.
- 기준: [제품 정책](../product/planning-proposal.md#회원과-카카오-로그인)을 먼저 갱신했다. 기존 전화번호 전체 표시·명부 12개 항목·일치/차이 강조를 유지한다.
- 범위: 관리자 상태별 목록·버튼, 상태 전환 트랜잭션, 기존 회원 재승인, 재로그인·잔여 세션의 접근 차단.
- 보존: 기존 회원 ID·글·댓글·회비·명부 연결·다른 미커밋 변경. DB 구조와 회비 판정은 바꾸지 않는다.
- 최초 개발 검사: Replit 변경 코드 lint·서식·앱 타입/경계·변경된 기존 테스트 타입, 문서 정합성·diff 공백. 당시 실행형 테스트·실제 회원 처리·DB 작업·서버 재시작·릴리스·실계정 QA는 수행하지 않았다. 이후 요청된 개발 서버 재시작과 집중 검사 결과는 아래에 구분한다.

## 적용 전 상태

로컬·Replit main `e5f167d`와 기존 작업 파일의 해시 일치를 확인했다. 기존 가입 거부는 unlink와 로컬 삭제를 수행했으므로 상태 보존으로 대체한다. 이미 삭제된 과거 신청은 복원하지 않는다. 개발 코드 적용과 실제 회원 처리·런타임 확인은 아래처럼 구분한다.

## 거부된 신청 삭제 결정

사용자가 승인 거부 → 삭제 → 신청정보·카카오 연결 삭제 경로를 추가했다. 기존 회원이 포함될 때의 처리 범위를 질문했고, 사용자는 **기존 계정·글·회비·명부 연결 보존**을 선택했다. 따라서 회원 탈퇴의 `removeLocalUsers`를 사용하지 않는다. 삭제는 rejected에서만 가능하고 unlink 실패 시 신청을 보존한다. 내부 회원 식별자와 미승인 상태는 유지하며, 새 OAuth 접속 시 새 심사 신청을 만들고 자동 승인을 막는다. 이 구현은 실제 회원이나 카카오 연결의 삭제 실행 승인이 아니다.

## 구현과 개발 반영

- 상태별 목록은 기존 관리자 심사 API의 `status` 필터를 사용한다. 인증 완료는 자동 가입 회원을 포함해 `users.is_verified=true`에서 읽는다. 조회용 회원 투영은 신청 행을 생성하지 않으며 `recordType`·`memberId`로 실제 회원과 신청의 식별자를 구분한다.
- `registration-decision-storage.ts`는 승인 취소·거부·재심사·삭제의 현재 상태와 신원 잠금을 관리한다. 신규·기존 회원의 승인과 명부 claim은 `registration-approval.ts`의 같은 트랜잭션에서 수행한다. 승인 취소는 자기 자신을 차단하고 취소 간 잠금·현재 관리자 확인으로 관리자 교차 취소 경쟁을 막는다.
- 거부는 보존만 수행한다. 거부 신청 삭제는 기존 Kakao admin 설정·unlink 클라이언트와 엄격한 식별자 검사를 재사용하고 실패·이미 해제된 응답을 구분한다. 기존 계정에는 미승인·연결 해제 상태만 반영하며 글·댓글·납부·명부 연결을 정리하는 `removeLocalUsers`는 호출하지 않는다.
- 로그인은 대기·거부를 자동 승인하지 않는다. 기존 회원의 신청을 삭제한 뒤 새 OAuth로 돌아오면 대기 신청을 다시 만들고 승인 전 세션을 발급하지 않는다. 앱 진입점의 `/api`·`/objects` 가드는 승인 상태를 다시 확인해 늦게 저장된 세션도 차단한다.
- 기존 전화번호 전체·12개 명부 필드·일치/양쪽 차이 강조는 유지했다. 개인정보 안내·프로젝트 지침·스키마 계약·DB 런북·구조 문서를 같은 상태 정책으로 맞췄다. DB 컬럼·제약·마이그레이션·회비 판정은 바꾸지 않았다.
