# 동문회 Google 주소록 동기화

관리 원본은 Google Sheets의 `구글주소록양식` 탭(A:G)이다. `alumni.dkom@gmail.com` 주소록의 관리 대상은 `2026-11-20` 라벨이다. 2026년 3월 6일 CSV를 가져올 때 생성된 `3. 6.에 가져옴`과 같은 라벨이다. 명부 휴대전화가 기본 키다. `010-0000-…`는 실제 휴대전화가 없는 동문에게 부여한 고유번호이므로 전체 자릿수를 보존한다. `신문사`가 붙은 카드는 다른 라벨과 겹쳐도 보호한다.

2026-11-20 전체 동기화에서 관리 필드가 충돌하면 명부 값을 적용한다. 같은 동문으로 확인한 주소록 카드에는 `통합주소록` A열의 UUID를 사용자 지정 항목 `alumni_uid`로 저장한다. 전화번호와 이름이 서로 다른 카드를 가리키면 기존 UUID와 가져오기 당시의 명부도 대조해 카드를 식별한다. 다른 사용자 지정 항목, 보조 연락처와 소속 라벨은 보존한다.

### 비교와 판정

- 성(Family Name)은 명부의 기수 표기, 이름(Given Name)은 동문 성명이다. 번호의 하이픈·공백과 국내 번호의 `+82` 국제 표기를 정규화해 카드의 모든 전화번호와 대조한다.
- 같은 번호가 명부와 주소록에 각각 하나씩 있고 신원 충돌이 없으면 기수·성명·전화 유형·동문 분류·직책의 차이를 표시한다. 관리 가능한 조직 항목만 수정하며 병원명 등과 뒤섞인 항목은 검토로 보낸다.
- 기수와 성명이 같아도 전화 키가 다르면 번호 변경 후보로 둔다. 번호와 이름이 서로 다른 동문을 가리키거나 한 카드가 두 명부 행에 대응하면 수동 검토한다. 일반 동기화 CLI는 이들을 자동 분리·병합·삭제하거나 전화 키를 바꾸지 않는다.
- 신규 후보는 명부 키와 기수·성명이 모두 미발견인 행이다. 온라인 미리보기는 동문회 계정의 저장된 연락처 전체를 읽어 라벨 밖 중복을 확인한다. 라벨 밖 카드나 신문사 카드가 후보에 연결되면 생성을 보류한다. 검토 CSV에는 대상 라벨의 비보호 카드만 상세 표시한다.

### 로컬 준비

Mac에서 저장소 루트를 작업 디렉터리로 사용한다. Google Cloud 프로젝트에서 **Google People API**와 **Google Sheets API**를 사용 설정한다. Google Auth Platform에서 동의 화면을 설정하고 OAuth 클라이언트를 **Desktop app** 유형으로 만든다. 외부 앱의 게시 상태가 테스트라면 동문회 주소를 테스트 사용자에 추가한다. 다운로드한 클라이언트 JSON은 사용자 전용 경로 `~/.config/dgkma-alumni-contacts/desktop-client.json`에 저장하고 권한을 `600`으로 설정한다. 개인 주소록 접근에는 동문회 계정의 OAuth 동의가 필요하다. [Google의 인증 정보 설정 안내](https://developers.google.com/workspace/guides/create-credentials)

```sh
python3 -m venv local-backups/.alumni-contacts-venv
source local-backups/.alumni-contacts-venv/bin/activate
python -m pip install -r scripts/alumni_contacts/requirements.txt
```

### 읽기 전용 미리보기

원본 시트 URL의 `/d/`와 `/edit` 사이 값을 `ALUMNI_SPREADSHEET_ID`에 설정한다. 다음 명령을 처음 실행하면 동문회 계정을 선택해 Sheets 읽기, 연락처 읽기 및 계정 이메일 확인에 동의한다. 검토 폴더는 실행할 때마다 새 경로를 사용한다.

```sh
alumni_client="$HOME/.config/dgkma-alumni-contacts/desktop-client.json"
alumni_review="local-backups/alumni-review-$(date +%Y%m%d-%H%M%S)"
python -B -m scripts.alumni_contacts preview \
  --client "$alumni_client" --sheet-id "${ALUMNI_SPREADSHEET_ID:?원본 시트 ID를 설정하세요}" \
  --output "$alumni_review"
```

`review.csv`에서 명부 행 번호, 판정, 주소록의 대응 카드, 변경 필드를 확인한다. 전화번호 열에는 끝 네 자리만 표시한다. `plan.json`은 검토 시점 데이터의 지문과 적용 가능 행을 담는다. 이미 내보낸 자료로만 비교할 때는 다음 명령을 사용한다. CSV 미리보기의 판정 범위는 제공한 내보내기 자료이며, 이 파일로 만든 계획은 쓰기에 사용할 수 없다.

```sh
python -B -m scripts.alumni_contacts csv-preview \
  --source-csv "$alumni_roster_csv" --contacts-csv "$alumni_contacts_csv" \
  --output "$alumni_review"
```

### 확인한 행 적용

운영자가 이번 온라인 미리보기에서 적용할 행을 확정한 뒤 실행한다. 아래 예시는 확인한 명부 행 번호 하나를 `alumni_row`에 설정한 경우다. 여러 행은 `--rows` 뒤에 공백으로 나열할 수 있다. 최초 적용 시에는 동일한 동문회 계정으로 연락처 쓰기 권한에 별도 동의한다.

```sh
python -B -m scripts.alumni_contacts apply \
  --client "$alumni_client" --sheet-id "$ALUMNI_SPREADSHEET_ID" \
  --plan "$alumni_review/plan.json" --rows "${alumni_row:?확인한 명부 행 번호를 설정하세요}"
```

적용 시 원본과 전체 주소록을 다시 읽고 미리보기 지문을 확인한다. 신규 카드는 가져오기 라벨에 생성한다. 기존 카드 수정에는 바뀐 필드만 보내며, 직전에 대상 라벨과 CONTACT 소스 버전을 다시 확인한다. 각 쓰기 뒤 연락처 ID로 재조회하고 관리 값과 라벨을 검증한다. 기존 연락처에서는 관리 필드에 함께 들어 있는 부가값도 대조한다. 각 실행 뒤 새 미리보기에서 반영한 행의 `일치` 여부를 확인한다. [Google People API 연락처 관리](https://developers.google.com/people/v1/contacts)

읽기·쓰기 토큰과 작업 기록은 사용자 전용 `~/.local/state/dgkma-alumni-contacts/`에 보관한다. 같은 상태 디렉터리를 계속 사용한다. 도구는 로컬 적용 실행을 잠그고 각 요청 전에 `operations.jsonl`에 행과 상태를 기록한다. 중간에 멈추면 이전 행은 이미 반영됐을 수 있다. 새 미리보기와 기록을 대조하고 결과가 불명확한 생성 요청은 재전송하지 않는다. 외부 기기에서의 동시 생성은 People API가 휴대전화 고유 제약을 제공하지 않으므로, 적용 시간에는 다른 가져오기나 수동 편집을 피한다.

### 2026-11-20 확인 결과

이번 운영 요청의 쓰기 범위는 전체 계정에서 재검토한 신규 후보 68명의 생성과 기존 가져오기 라벨의 이름 변경이다. 생성 후 기수·성명·휴대전화 키·관리 값·소속 라벨을 대조하고, 동일한 라벨의 이름을 `2026-11-20`으로 변경한다. 마지막에 기존 멤버와 신규 68명의 소속, `신문사` 멤버를 다시 확인한다.

첫 비교에서는 Mac에서 원본 3,458행과 대상 라벨 CSV 3,378카드를 대조했다. 3,225행 일치, 68행 신규 후보, 11행 수정 후보, 154행 수동 검토였다. 이때의 개인별 목록은 Git에서 제외한 `local-backups/alumni-contacts-review-20261120/review.csv`에 보관한다.

같은 날 동문회 계정의 기존 Cloud 프로젝트 `My First Project`에서 데스크톱 클라이언트를 발급하고 People API를 활성화했다. Sheets API는 이미 활성 상태였다. 동문회 계정을 테스트 사용자로 등록하고, 사용자 동의 후 로컬 Python으로 읽기 전용 연결과 저장된 인증의 재사용을 확인했다. 프로젝트의 OAuth 앱은 외부 테스트 상태다. 연락처·시트 권한을 포함한 테스트 사용자 인증은 동의 7일 뒤 만료된다. [Google 테스트 사용자 정책](https://support.google.com/cloud/answer/15549945)

People API에서 읽은 저장 연락처는 3,383카드였다. 대상 라벨 3,378카드와 라벨 밖 5카드를 포함한다. 이전 신규 후보 68행을 현재 명부에서 재식별해 전체 휴대전화번호, 기수·성명, 기수 없는 일반 성명으로 대조했다. 세 기준 모두 대응 카드가 0개였다. 신문사 관련 후보도 0개였다. 온라인 미리보기의 전체 판정 건수는 첫 비교와 일치했고, 주소록 쓰기는 실행하지 않았다. 전체 온라인 결과는 `local-backups/alumni-contacts-account-review-20261120/review.csv`, 68명 개별 판정은 같은 폴더의 `candidate-recheck.csv`에 있다.

후속 적용에서 동문회 계정의 쓰기 동의를 받고 위 68명의 카드를 생성했다. 같은 라벨 ID에서 이름을 `2026-11-20`으로 변경했다. 변경 뒤 읽기 전용 연결에서 68명의 서로 다른 카드 ID, 기수·성명·전화 키·분류·직책·라벨 소속을 원본과 대조했다. 전체 주소록은 3,451개, 대상 라벨은 3,446개였다. 기존 3,383카드의 관리 값·버전과 기존 멤버십이 보존됐고, 라벨 밖 5개와 그중 `신문사` 2개도 그대로였다. 명부 행별 결과는 `local-backups/.alumni-reaudit/create-68/final-rows.csv`에 있다.

별도 요청으로 기존 공유 카드 12장과 명부 24행을 조사했다. 이 12쌍에 한해 보존본에서 행을 구분한 번호, 현행 명부의 휴대전화 키, 기존 카드의 추가 필드 소유를 확인한 뒤 분리한다. 예전 실번호와 현재 고유번호가 다른 건은 과거 동문회 주소록의 이름·기수·번호·사망 분류까지 대조한다. 먼저 새 카드를 읽어 검증하고, 기존 카드는 같은 연락처 ID에서 다른 회원의 번호를 분리한다. 원본 시트 및 `신문사`는 보존한다.

2025-01-12 명부 보존 버전에서 대상 24행의 ‘학번’ 열에 서로 다른 번호가 기록됐음을 확인했다. 현재와 다른 과거 전화번호 1건은 2023-12-25 동문회 주소록에서 소유자와 분류를 확인했다. 조사한 12쌍을 모두 분리하고 독립된 읽기 전용 연결에서 24개의 현행 휴대전화 키가 각자의 카드에만 있는지와 소속 라벨·관리값을 다시 확인했다. 최종 `2026-11-20` 라벨은 3,458명, `신문사`는 기존 2명이며 이번 12쌍의 미해결 건은 0쌍이다.

### 2026-11-20 전체 대조 및 UUID 반영

명부 3,458명과 라벨의 기존 카드 3,458장을 일대일로 연결했다. 전화번호가 달라진 회원은 3월 6일의 명부와 현재 명부의 학적 정보, 기존 카드의 기수·성명과 전화번호를 대조했다. 명부 우선 원칙에 따라 전화번호 129장, 이름·기수 표기 3장, 동문 분류·직책 15장을 수정했다. 항목 간 중복이 있다. 카드 전부에 사용자 지정 항목 `alumni_uid`를 저장했다.

쓰기 후 별도의 읽기 전용 OAuth 연결로 원본 시트와 저장된 연락처 전체를 다시 읽었다. 명부 관리값과 UUID가 모두 일치한 카드는 3,458장이고 남은 변경은 0건이다. 라벨 밖 5장(신문사 2장 포함)의 버전과 조회 필드가 적용 전과 같았다. 이번 적용 계획과 카드별 재조회 기록은 비공개 로컬 폴더 `local-backups/alumni-uid-sync-20261120/`에 있다. 저장한 계획의 결과는 저장소 루트의 Python 환경에서 다음 명령으로 재검증한다.

```sh
python -B -m scripts.alumni_contacts.reconcile verify local-backups/alumni-uid-sync-20261120
```
