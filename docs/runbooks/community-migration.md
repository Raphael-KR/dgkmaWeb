# 커뮤니티 일회성 이관 도구

분류·제외·실행 시점은 [이관 기준](../product/community-archive-migration-proposal.md)을 따른다. 다음카페와 밴드는 각각 전체 후보를 한 번에 반영하며 증분 이관하지 않는다. 다음카페와 밴드는 각자의 자료 준비·적용 도구를 사용한다. 운영 대상은 운영 이전을 승인한 릴리스에서 사용한다. 정식 운영 개시 전에는 다음카페 운영 이전분에도 초기 개발 데이터 정책을 적용한다.

## 밴드 자료 준비

`YYYY-MM-DD`는 한국 시간으로 하루가 끝나 백업이 완료된 날짜다. 분류표·실명 대조표·검산 결과는 로컬 비공개 폴더 `local-backups/community/migration/band-YYYY-MM-DD/`에 보관한다.

| 작업 | 명령 | 확인 대상 |
|---|---|---|
| 원천 분류 | `python3 scripts/prepare-band-classification.py --through YYYY-MM-DD` | 모든 원글 ID, 분류 단서, 자동 게시, 댓글·첨부 관계 |
| 본문 변환 | `python3 scripts/prepare-band-posts.py YYYY-MM-DD` | 표시 문자열·줄바꿈, 제한 글, 첨부만 있는 글 |
| 댓글 준비 | `python3 scripts/prepare-band-comments.py --through YYYY-MM-DD` | 같은 글 안의 원댓글·답글 키, 표시 문자열, 첨부 상태 |
| 실명 대조 | `python3 scripts/resolve-band-authors.py YYYY-MM-DD` | 개발 명부 읽기 전용. 성명 유일 일치를 우선하며 동명이인은 명시된 졸업기수로 대조 |
| 미디어 검산 | `python3 scripts/audit-band-media.py YYYY-MM-DD` | 원천 ID와 소유 글·댓글·앨범, 크기와 해시, 미확보 항목 |
| 첨부 준비 | `python3 scripts/prepare-band-assets.py YYYY-MM-DD` | 사진·문서와 이관용 영상 후보, 구형 문서 변환 및 보류 사유 |
| 목적지 결정 | `python3 scripts/prepare-band-classification.py --through YYYY-MM-DD --decide-destinations` | 로컬 `migration/band-11089836-reviewed-destinations.json`의 원본 ID·해시별 검토 결과를 함께 읽어 `classification-decisions.json`을 생성한다. 검토표에 명시한 제외 사유는 원글과 종속 댓글·답글에 적용한다. 제외 결정이 없는 빈 목적지와 원본 해시 변경은 확인 대기로 둔다. 사무국이 글 단위로 확인한 실명은 해당 원본에만 적용한다. 게시 보류 사유는 게시판과 별도로 검산한다. |
| 준비 결과 검산 | `python3 scripts/report-band-readiness.py --through YYYY-MM-DD` | `readiness.json`에서 원글·댓글·답글의 분류, 실명, 상위 글과 첨부의 보류 사유 확인 |

검토한 프로필·가입 댓글 자료가 있는 마감본은 `python3 scripts/resolve-band-authors.py YYYY-MM-DD --reviewed-preview`로 함께 읽는다. 실명 대조 뒤 준비 결과 검산과 이관 후보 생성을 다시 실행한다. 가입 댓글에서 이름과 계정의 연결이 모호하다고 확인된 건은 보류한다. 명부의 졸업기수가 없는 행도 성명 중복 판정에 포함한다. 밴드별 비공개 `band-11089836-author-rules.json`에 사무국이 지정한 스팸 계정 키와 원문 근거, 향후에도 사용할 성명·기수 표기 조합을 보관한다. ‘(알 수 없음)’ 표시와 확정한 스팸 계정은 글별 실명 확인보다 먼저 제외한다.

밴드의 신규 가입 유형과 구형 가입 안내 양식, 본문의 가입 인사 태그와 원문 검토 결과를 대조한다. 가입 안내·가입 인사·가입 환영 카드는 모두 백업 전용이다. 원글의 제외 결정은 그 글의 댓글·답글·첨부에도 적용한다. 자동글과 별도 안내 카드는 피드와 구분해 유형별로 집계한다. 실명 대조에는 가입 댓글의 로컬 원문을 사용할 수 있다. 다른 글·댓글은 각자의 작성자와 상위 글을 기준으로 판단한다. 개발에는 확정 실명·이관 본문과 선별한 파일만 전송한다.

### 개발 이관과 검산

스티커를 확보하지 못한 댓글·답글은 백업의 원문 본문과 대조한다. 글자가 있으면 원래 문구를 이관하고, 본문이 비어 있고 유일한 내용이 미확보 스티커이면 제외 사유를 기록한다. 본문을 읽을 수 없는 경우는 보류한다. 스티커 외에 첨부가 있으면 해당 첨부를 별도로 검산한다.

댓글·답글에 달린 사진과 영상은 해당 댓글의 원본 ID와 순서를 기준으로 백업 파일 및 개발 저장소의 크기·해시를 대조한다. 사진 수로 이관을 보류하지 않는다. 실제 파일을 확보하지 못한 경우와 상위 글이 보류된 경우를 구분한다. 댓글 첨부의 열람에는 게시글과 댓글의 회원·가림 권한을 적용한다.

개발 게시판에 현재 백업을 적용할 때는 SQLite의 완료일과 준비 묶음의 날짜를 대조한다. 사무국이 소유자까지 확인한 밴드 계정은 해당 마감 폴더의 비공개 `confirmed-author-accounts.json`에 계정 키·확인한 실명·근거 원글 ID와 원본 해시를 기록한다. 댓글을 근거로 쓸 때는 댓글 묶음의 해시와 해당 글 안의 댓글 ID를, 답글이면 상위 댓글 ID도 기록한다. 실명 대조 도구는 해당 원문에서 계정 키와 당시 표시명을 확인한다. 같은 사람의 계정이 여럿이면 각각의 근거를 보관하고, 각 계정의 이관 자료에 같은 실명을 표시한다. 사무국이 확인한 졸업기수는 로컬 확인 기록에 남긴다. 재학생에게 당시 직책을 표시하도록 지정하면 실명과 `historicalRole`을 별도로 기록한다. 게시글·댓글의 작성자 표시를 만들 때 두 값을 조합한다. 보류 내역과 원문 링크는 로컬에서 검토한다.

이미 개발에 반영된 가입글이나 탈퇴·스팸 작성자의 자료를 제외할 때는 이전 영수증의 원본 ID·개발 ID와 새 명세의 제외 사유를 대조한다. 원글·원댓글과 함께 제외되는 답글까지 먼저 확인한다. 홈페이지에서 추가한 댓글이나 원문과 다른 편집 내용이 발견되면 해당 삭제를 중단한다. 새 연결에서 남은 글·댓글을 검증한 뒤 로컬 개발 대응표를 갱신한다. 원본 백업과 검증 영수증을 보존한다.

첨부 준비 시 5MiB를 초과한 JPEG는 로컬 libjpeg-turbo의 `jpegtran -copy all -optimize -progressive`로 처리한다. `djpeg -rgb`가 해독한 원본·결과의 크기와 픽셀을 포함한 해시가 같고 용량 상한을 충족하면 원본 해시와 함께 이관 후보로 기록한다. 사무국이 재인코딩을 허용한 사진은 원본 ID·입력 해시·사본 해시를 검토 파일에 연결한다. 원본과 사본의 해상도·표시 방향이 같고 사본이 용량 상한 이내인지 확인한다.

이관 마감일에 검증한 사진 색인을 마감 폴더의 `source-photo-index.json`에 고정한다. 이후 밴드 백업을 증분해도 이관 묶음은 같은 기준일의 원글·댓글·사진으로 검증한다.

개별 보류를 해소할 때는 마감 폴더의 비공개 `reviewed-post-content.json`에 원글 ID·원본 해시와 처리할 항목을 기록한다. 만료 파일은 파일 ID와 백업의 만료 기록을 대조한다. 기사 본문은 검토한 구간만 가리고, 식별 정보가 있는 사진은 원본과 가림 처리 사본의 해시를 대조해 사본만 개발 저장소로 보낸다. 공지 원문 게시와 신청 폼 생략도 지정한 원글에만 적용한다. 개발 반영 전후에 원글별 첨부·댓글 수와 기존 이관 자료를 대조한다.

원래 모습으로 게시하는 글, 확정한 게시판, 백업 전용 글과 사진은 원글 ID·원문 해시별 결정을 따른다. 복사 금지 표시가 있는 글은 수집 시 허용된 열람 범위와 실제 보존 바이트를 확인하고, 확보되지 않은 제한 파일의 ID와 사유를 남긴다. 설문은 원글 안내문, 투표는 안내문·질문·선택지·확인된 합계만 변환기로 전달한다. 개별 응답 필드는 개발 명세에서 제외한다. 이관 댓글의 길이 예외는 원문과 변환값의 길이가 일치하는 개발 이관 명세에만 적용한다.

404로 남은 사진은 원본이 제공한 다운로드·미리보기 주소와 보관 파일을 확인해 생략할 사진 ID를 고정한다. 공유 카드에서는 원본이 허용한 게시물 주소와 원본 ID를 확인한다. 장소는 장소명과 주소만 사용한다. 앨범 카드는 원본 앨범 번호·사진 수·열람 허용 상태를 마감 사진 색인과 대조하고, 기존 앨범을 가리키면 사진 ID 집합과 실제 저장 목록을 확인한다. 보류 목록에는 원글 결정에 따라 함께 처리될 댓글과 독립적으로 확인할 댓글을 구분해 기록한다.

피드와 사진 색인이 다르면 원글 번호와 사진 ID로 전체 사진을 대조한다. 피드에 첨부된 순서를 먼저 유지하고 추가 사진은 밴드 사진 번호순으로 둔다. 영상 표지는 제외하고 누락·제한된 사진은 기록한다. 회원 전용 사진첩에는 동문회·기수·모교 활동과 역사자료를 넣는다. 원글이 없는 사진은 사무국이 선택한 앨범의 행사명·날짜와 사진 해시를 대조해 같은 행사 앨범에만 연결한다. 같은 행사 앨범에 동일 파일이 있으면 그 항목을 재사용한다. 기존 앨범 확장 시 기존 순서와 대표 사진을 보존하고 새 사진을 마지막에 붙인다. 일반 글은 검증된 사진을 모두 원글의 사진 칸에 둔다.

마감 폴더의 비공개 `photo-destinations.json`에는 원글별 원문 해시, 순서가 있는 사진 ID, 목적지(`post` 또는 `heritage`)와 분류 근거를 기록한다. 역사관 대상은 사진을 앨범에 저장하고 원글 본문에는 링크를 한 번 넣는다. 일반 글은 10장이나 40장을 넘어도 원문에서 확인한 사진 전부를 같은 글에 둔다. 글의 게시판 분류와 사진의 배치는 따로 판정한다. 원글의 스티커는 생략하되 본문과 사진의 개수·순서는 원본과 대조한다. 링크 미리보기에는 안전한 HTTP(S) 주소를 쓰고 본문 없는 글의 제목은 전체 첨부 수에서 만든다.

일정 카드에서는 원글별 일정 ID를 대조해 같은 일정은 한 번만 표시한다. 제목·시작 및 종료 일시·장소명과 주소 중 원본에 있는 값만 본문 끝에 덧붙인다. 종일은 날짜로 표시하고, 종료값이 없으면 시작만 표시한다. 카드의 설명·작성자·초대 및 응답 정보는 추출 대상에서 제외한다. 원글의 접근 제한과 다른 첨부 보류 사유는 별도로 확인한다.

독립 앨범 결정은 마감 폴더의 비공개 `reviewed-album-photos.json`에 마감 사진 색인의 해시·원본 앨범 번호·선정 사진 ID를 기록한다. 기존 앨범에 이어 붙일 때는 해당 원글 ID와 추가 전 앨범 해시를 기록한다. 같은 원본 밴드 앨범에 속하는 별도 행사에는 해당 묶음의 사진 ID 하나를 `referencePhotoId`로 같이 기록한다. 사무국이 추정 자료로 표시하도록 한 사진에는 추정 문구와 확인된 밴드 게시일을 기록한다. 선택한 사진 ID별 설명(`caption`)과 제공자(`credit`)는 `photoDetails`에 기록한다. 게시일을 앨범 날짜로 사용하는 경우 앨범 설명(`description`)에 날짜의 의미를 명시한다.

앨범이 있으면 준비 명령에 `--album-files <마감폴더 안의 묶음/photos 경로>`를 지정할 수 있다. 생성된 `post-albums.json` 또는 변경된 앨범과 그 사진 항목을 묶음의 `catalog.json`으로 둔다. `photos/`에는 새 사진 항목의 실제 파일을 넣는다. `node --import tsx scripts/apply-band-albums-development.mjs --preview <묶음> <목록 SHA-256>`으로 기존 목록과 추가분을 확인한다. `--apply <묶음> <목록 SHA-256> <미리보기의 priorSha256>`으로 파일별 검증과 카탈로그 병합을 수행한다. 게시글 적용 도구는 실제 저장 목록의 앨범 내용과 원글 링크를 대조한다.

1. 로컬에서 `python3 scripts/prepare-band-manifest.py --through YYYY-MM-DD --decisions <분류결정파일> --decisions-sha256 <결정파일 SHA-256>`을 실행한다. `manifest-status.json`에서 원본별 선정·보류·제외와 파일·영상 대기열의 SHA-256을 확인한다.
2. 비어 있지 않은 각 대기열은 `python3 scripts/package-band-development-uploads.py YYYY-MM-DD <대기열 SHA-256>`으로 묶는다. 영상에는 `--videos`를 붙인다. Replit 개발에서 `node --import tsx scripts/upload-band-development.mjs --validate <묶음 폴더> <묶음 명세 SHA-256>`으로 검산한 뒤, `--upload`와 마지막 인자 `<새 영수증 경로>`로 업로드하고 결과를 재조회한다. 영상에는 각각 `--validate-videos`와 `--upload-videos`를 쓴다. 첨부 영수증 `uploaded-assets.json`과 영상 영수증 `uploaded-videos.json`을 같은 마감일의 로컬 준비 폴더에 둔다.
3. 1번 명령을 같은 입력으로 다시 실행한다. 필요한 영수증이 대기열과 일치하면 `development-manifest-<SHA-256>.json`이 생성된다. 해당 파일과 해시를 Replit 개발에서 `node --import tsx scripts/apply-band-development.mjs <최종 명세> <명세 SHA-256> --preview`로 검산한다. 첨부가 있으면 영수증 경로와 SHA-256을 전달한다. 이미 반영된 작성자의 글·댓글을 제외할 때는 그 뒤에 `--retire <제외 명세> <제외 명세 SHA-256>`을 붙이고 직전 검증 명세를 같은 폴더에 둔다. 제외 명세는 직전 영수증의 원본 ID·개발 ID, 변경 전후 명세의 지문, 확인한 제외 사유를 담는다. 추가·제외 예정 건수와 검증된 파일 수를 확인한다.
4. 같은 인자에서 `--preview`를 `--apply`로 바꾸면 개발 DB `heliumdb`에 게시글·댓글·답글을 한 트랜잭션으로 추가한다. 같은 원본 ID의 내용이 일치하면 재사용하고 다르면 중단한다. 중단 후에는 같은 최종 명세로 `--preview`부터 재실행한다. 적용 후 도구는 새 연결에서 해당 글·댓글의 내용과 상위 관계, 기존 다음카페 게시글의 건수·지문을 확인하고 원본 ID와 개발 DB ID를 대응한 영수증을 남긴다. 이미 반영된 자료는 같은 명령의 `--verify`로 DB 쓰기 없이 전체 건수와 내용을 확인하고 새 영수증을 만들 수 있다. 개발 사진첩 카탈로그의 보존 여부는 별도로 전후 대조한다.
5. 개발 DB의 재조회 영수증을 로컬 마감 폴더로 회수한 뒤 `python3 scripts/record-band-development.py <영수증>`으로 대응표를 기록한다. 원글은 원본별로, 댓글·답글은 백업의 원문 댓글 묶음별로 개발 ID를 연결한다.

밴드 사진·일반 첨부의 앱 경로는 `/objects/band-imports/{uuid}`다. 실제 객체는 환경별 비공개 루트의 `heritage/band-media/{development|production}/11089836/uploads/{uuid}`에 두고, 영상과 카탈로그는 같은 루트의 `videos/`와 `posts/`에 둔다. 일반 객체에는 해당 환경의 이관 범위 표시(`importScope`)가 있어야 한다. 공유 저장소에서도 기존 운영 서버가 이미 차단한 물리 경로를 사용하며, 일반 `uploads/`나 논리 경로에 이관 객체의 사본을 두지 않는다.

밴드의 백업 반영 명령은 개발만 대상으로 한다. 운영에는 아래 개발→운영 도구로 검증한 게시글·댓글·답글, 이관 전용 첨부, 영상·재생 목록과 사진첩을 함께 이전한다.

## 다음카페 도구의 공통 인자와 환경

로컬과 Replit에서 같은 `local-backups/community/tools/` 소스를 사용한다. 실행에 필요한 Python·MJS 8개만 Git으로 관리한다. 같은 트리의 원본·SQLite·바이너리·변환물·payload·영수증은 계속 Git 제외다. Replit에서 `node --import tsx <도구> <workspace> <payload-directory> <mode> <environment> <expected-database>` 형식으로 호출한다. 백업 입력 도구의 `environment`는 development만 허용하며 DB 이름은 heliumdb를 명시한다. production 입력은 거부한다. 선택한 실제 DB 이름을 확인하고 다르면 쓰지 않는다.

- 백업→개발 DB는 앱의 기본 PG* 선택을 유지한다. 운영 DB 선택은 아래 개발→운영 도구에만 있으며 Replit의 PROD_DATABASE_URL을 사용한다. PG*를 해제하거나 바꾸지 않는다.
- 파일 저장소는 개발 PRIVATE_OBJECT_DIR을 사용한다. 운영 이전 도구만 PROD_PRIVATE_OBJECT_DIR을 사용한다. 운영용 값은 실제 운영 앱 PRIVATE_OBJECT_DIR과 일치해야 한다. 운영자에게서 두 환경의 실제 루트가 동일함을 확인한 경우 이전 명령에만 `PROD_PRIVATE_OBJECT_DIR="$PRIVATE_OBJECT_DIR"`를 전달할 수 있다. 확인 없이 개발 경로를 대입하지 않는다. URL·Secret·비공개 경로를 로그에 출력하지 않는다. 설정 추가 자체는 이번 작업에서 실행하지 않았다.
- 백업 이관의 사진첩 경로는 개발 비공개 루트의 heritage/development다. 운영 이전 도구만 운영 루트의 heritage/production을 사용한다. 게시글 첨부는 선택한 루트의 uploads 경로와 기존 앱 참조 계약을 사용한다.

## 게시글

apply-post-migration.mjs는 최종 v2 posts.json과 files/를 입력한다. `--validate`는 파일·본문·메타데이터 검증만 하고 DB·Storage에 연결하지 않는다. `--preview`는 대상 DB 이름·기존 게시글/댓글 수·카테고리를 읽어 출력하고 쓰지 않는다.

`--apply`는 비어 있는 posts에 전체 후보를 삽입한다. `--reset-and-apply`는 명시적으로 선택한 경우에만 posts 전체 행을 삭제하고 전체 후보를 삽입한다. 댓글은 기존 FK의 ON DELETE CASCADE로 함께 정리한다. 카테고리·회원·명부·회비·스키마·시퀀스·Storage 파일은 삭제하지 않는다. 리셋과 DB 삽입은 하나의 트랜잭션이며 DB 오류 시 미완료 트랜잭션을 취소한다. 커밋된 작업의 자동 원복은 하지 않는다.

첨부는 먼저 저장·해시 대조한다. DB 실패 시 남은 파일을 자동 삭제하지 않는다. 새 DB 연결에서 전체 건수·대상 ID·본문/메타데이터·작성자·날짜·첨부 참조를 대조한다. 기존 행을 비교·병합·upsert하지 않는다. 이 도구의 전체 리셋을 플랫폼별 자동 실행으로 연결하지 않는다. BAND의 실제 실행 순서는 별도이며 선행 이관 자료를 지우지 않는다.

## 사진첩

apply-heritage-albums.mjs는 catalog.json과 photos/를 입력한다. `--validate`는 로컬 최종 자료만 검사하고, `--preview`는 실제 DB 환경과 카탈로그 존재 여부만 확인한다. `--apply`는 전체 사진을 저장·해시 대조한 뒤 선택 환경의 카탈로그를 전체 교체한다. 서로 다른 카탈로그를 이유로 중단하거나 앨범 ID별 증분 병합하지 않는다. 미리보기 후 다른 작업이 카탈로그를 바꾼 경우에는 Storage generation 조건이 덮어쓰기를 거부한다.

같은 해시 파일은 재전송하지 않을 수 있으나 이는 파일 전송 재사용이며 앨범 증분 이관이 아니다. 새 카탈로그에서 빠진 이전 파일은 물리 삭제하지 않는다. 글당 이미지 40개 제한으로 앨범을 나누지 않는다.

## 영수증·로컬 기록

적용 영수증은 payload 폴더의 application-<environment>-<실행별 식별자>.json에 새로 저장한다. 기존 파일은 덮어쓰지 않는다. source ID·대상 ID·환경·입력 해시·검증 결과를 남긴다. 백업→개발 적용용 record-cafe-application.py / record-heritage-application.py에는 영수증 파일 경로를 명시한다. 운영 이전은 별도의 스냅샷·이전 영수증으로 원천/개발/운영 게시글 ID와 앨범 ID를 추적하며 백업 적용 영수증으로 기록하지 않는다. 검증한 결과만 로컬 SQLite의 해당 환경 최신 대응표에 기록하고 다른 환경·플랫폼은 변경하지 않는다. 기존 실행 영수증은 보존한다. 원본 백업·SQLite를 Replit에 올리지 않는다.

HWPX는 내용·외부 PCX 이미지 대조를 수행하지 않는다. 기존 업로드 확장자·용량·압축 구조 보안 검사는 유지한다.

## 개발 완료본 → 운영 이전

promote-community-content.mjs는 백업 posts.json/catalog.json을 입력받지 않는다. `node --import tsx <도구> <workspace> <새 snapshot 디렉터리> <mode> [예상 운영 DB 이름]`으로 사용한다.

| mode | 읽기·쓰기 |
|---|---|
| --export-development | 개발 heliumdb의 import_data가 있는 발행 게시글(가린 글 포함), 해당 밴드 글에 연결된 이관 댓글·답글, 개발 사진첩·연결 파일을 읽어 새 비공개 로컬 묶음 생성. DB/Storage 쓰기 없음 |
| --validate | 내보낸 development-content.json·blobs의 문서/파일/참조/해시만 검증. DB/Storage 연결 없음 |
| --preview-production | 위 검증 후 운영 DB 이름·카테고리·필수 컬럼·기존 글과 댓글 수·사진첩 카탈로그 존재 확인. 쓰기 없음 |
| --apply-production | posts가 빈 경우에만 운영으로 전체 이전. 해시와 파일 메타데이터가 모두 일치하는 기존 객체 재사용, 카탈로그 전체 교체 |
| --reset-and-apply-production | 명시적으로 선택한 경우 posts 전체·종속 댓글 리셋과 글·댓글·답글 삽입을 한 DB 트랜잭션에서 수행한 뒤 카탈로그 교체 |

내보내기 중 개발 콘텐츠 편집을 중지한다. 게시글과 밴드 이관 댓글은 한 REPEATABLE READ 읽기 전용 스냅샷으로 확보하고 사진첩은 복사 전후 카탈로그 해시를 대조한다. 회원 계정·명부·회비·세션·일반 테스트 글·초안·홈페이지에서 작성한 댓글은 묶음에서 제외하며 제외 게시글 수를 보고한다. 이관 글·댓글에 회원 계정 연결이 있으면 임의 ID 매핑 없이 중단한다. 카테고리는 운영의 기존 이름으로 대응한다.

development-content.json v2에는 개발 게시글과 댓글 ID·상위 연결·원작성 메타데이터·작성 당시 소속·수정 버전·가림 상태·시각, 사진첩 카탈로그, 파일의 논리 경로·이름·MIME·크기·해시를 담는다. 파일은 blobs/<SHA-256>으로 보관한다. 이전에 내보낸 다음카페 v1 묶음도 검증해 재사용할 수 있다. 파일·본문에 개인정보가 있을 수 있으므로 Git·공개 저장·채팅 로그에 넣지 않는다. 쿠키·토큰·DB URL·버킷 Secret은 포함하지 않는다.

운영은 개발의 글·댓글 ID, 상위 관계, 앱 내부 첨부 경로와 앨범 ID를 유지한다. 생성 시각·원작성 시각을 UTC로 유지하고 두 ID 시퀀스를 다음 삽입에 맞춘다. 일반 첨부와 사진첩은 운영 uploads 및 heritage/production/photos에, 밴드 전용 객체는 운영 heritage/band-media/production에 저장한다. 다운로드 이름·MIME·크기·해시와 비공개 범위를 대조한다. 새 DB 연결에서 전체 글과 댓글·답글을 스냅샷과 대조하고 운영 카탈로그 해시를 확인한다. 이전 영수증은 스냅샷 해시와 결과를 연결한 새 파일로 보존한다.

운영 미리보기 연결은 파일 복사 전에 닫고 모든 파일을 검증한 뒤 DB 연결을 새로 연다. 개발에서 경조사 데이터가 없는 글은 운영에서도 SQL NULL로 저장한다.

파일 복사·DB 커밋·카탈로그 교체는 하나의 원자적 트랜잭션이 아니다. 실패 시 단계와 filesVerified/databaseCommitted/catalogPublished를 구분해 보고하며 자동 삭제·커밋 후 원복은 하지 않는다. 현재 실패 범위를 확인하고 별도 실행 지시로 처리한다. Storage의 기존 파일을 물리 삭제하지 않는다.

공개 역사관 JSON·공개 문서·임원 사진은 기존 Git 코드 릴리스 대상이다. 운영 개시 전 개발 완료본과 같은 코드 후보를 릴리스하고, 데이터 이전과 코드 배포 결과는 따로 확인한다. 도구 작성·정적 검사만으로 내보내기·이전·운영 릴리스를 시작하지 않는다.
