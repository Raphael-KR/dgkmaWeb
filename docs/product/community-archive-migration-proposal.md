# 다음카페·밴드 이관 기준

로컬 백업 자료를 dgkmaWeb으로 이관할 때 적용하는 분류·공개 범위·저장·변환·검증 기준이다. 수집은 [백업 운영 문서](../runbooks/community-backup.md), 원 게시판별 목적지는 [다음카페 이관 계획](daum-cafe-migration-plan.md)을 따른다.

## 이관 단위와 입력

다음카페 백업, 다음카페 마이그레이션, 밴드 백업, 밴드 마이그레이션은 네 개의 독립 작업이다. 각 작업의 대상·범위·진행 상태·완료 조건·실행 결과를 따로 관리하고 보고한다. 한 플랫폼의 승인·완료를 다른 플랫폼에 적용하거나, 백업 완료를 마이그레이션 시작으로 연결하지 않는다.

- 다음카페 `dkkmob` 마이그레이션: 다음카페 백업만 입력으로 삼아 분류·변환·대상 환경을 확정하고 별도 실행 지시 후 처리한다.
- 밴드 `@dkom` 마이그레이션: 확정한 기준일까지의 밴드 백업만 입력으로 삼는 별도 작업이다. 다음카페의 분류·변환·적용 결과를 그대로 재사용하거나 완료로 취급하지 않는다.
- 원본과 이관 대응표는 로컬 SQLite에서 관리한다. Replit에 이관 전용 DB·테이블을 만들거나 SQLite·원본 백업을 업로드하지 않는다. 홈페이지에는 선택한 최종 자료·허용 첨부만 목적지별 기존 구조로 이관한다.
- 새 ‘이전 카페’ 게시판을 만들지 않는다. 기존 게시판에 분류한다.
- HWP 등 구형 첨부는 로컬 원본을 보존하고 허용 형식으로 변환한 뒤 이관한다. 이름만 바꾸거나 기존 업로드 보안 규칙을 완화하지 않는다.
- 원본 백업과 변환 결과·이관 상태는 구분한다. 원본 ID·게시판·작성자 표시·작성일·본문·댓글·첨부를 보존하고 비밀번호·쿠키·인증 토큰은 저장하지 않는다.

## 이관 후 공개 범위

이관 자료에는 **dgkmaWeb의 분류 체계와 목적지별 접근 정책**을 적용한다.

| 이관 목적지 | 적용할 열람 범위 |
|---|---|
| 커뮤니티 게시판의 각 카테고리 | 로그인한 승인 회원 전용 |
| 역사관 사진첩 목록·앨범 상세·사진 원본 | 로그인한 승인 회원 전용 |
| 동문회 소개·회칙과 사진첩 외 역사관 자료 | 현재 목적지 정책에 따라 비로그인 공개 |

본문·첨부·사진도 해당 목적지의 열람 범위를 따른다. 원본의 접근 등급은 출처 기록으로 보존하되, 그 등급만으로 추가 승인을 요청하거나 이관을 보류하지 않는다. 목적지의 회원 인증·관리 권한은 유지하며 로컬 원본 백업은 비공개로 보존한다.

## 저장 경계

`local-backups/community/archive.sqlite3`는 수집 목록·본문 원본 참조·파일 참조·내용 해시·원본/대상 ID 대응·변환/적용 상태를 관리하는 로컬 작업 DB다. 디렉터리 0700·파일 0600으로 제한하고 Git·Replit·클라우드 동기화에서 제외한다. 원문 JSON과 다운로드 파일은 같은 로컬 백업 트리에 유지한다. 캐시나 폐기 가능한 앱 테스트 데이터로 취급하지 않는다.

이관 입력은 다음카페 `local-backups/community/daum-dkkmob/`, 밴드 `local-backups/community/band-11089836/`로 구분한다. 공통 SQLite의 `source`·`container_id`로 원천을 식별하며 변환·이관 대응표와 결과 집계에서도 이 구분을 유지한다. 기존 백업·SQLite·실행 영수증을 이동하거나 삭제하지 않는다.

게시글 본문은 기존 `posts.content` Tiptap JSONB에 저장한다. `event_data`·`source_text`는 경조사 전용 의미를 유지한다. 원작성자를 현재 회원과 이름으로 자동 연결하거나 임의의 회원 계정을 만들지 않는다. 게시글 원출처·작성자·작성일은 이관 본문에 명시하고 원본 ID/대상 ID의 추적은 로컬 SQLite에 둔다. 이관 글의 `author_id`는 NULL을 사용하며 ‘작성자 계정 미연결’로 표시한다. 일반 작성 API의 회원 인증·작성자 부여, 수정·삭제·가리기 권한은 바꾸지 않는다.

## 자료별 분류

- 원 상위 메뉴·하위 게시판별로 목적지를 정한다. 원본 ID·원 분류·대상 메뉴/카테고리·공개 범위를 이관 대응표에 기록한다.
- 게시판 자료는 기존 게시판의 내용에 맞는 카테고리로 분류한다. 확인되지 않은 내용을 경조사 사실정보로 추정하지 않는다.
- 동창회앨범은 회원 전용 역사관 사진첩으로 이관한다. 게시글의 이미지 40개 제한을 적용하거나 앨범을 분할하지 않는다. 목록과 확보한 사진은 대상 환경의 비공개 Object Storage에 저장하며 [역사관 콘텐츠 기준](../reference/heritage-content.md)을 따른다.
- 역대임원 자료는 공개 역사관의 기존 항목과 대조·병합한다. 동일 대수·직책·성명은 합치고 사진을 재사용한다. 회장 재임 기간은 확정된 역대회장 명단을 우선한다.
- 과거 인사말·연혁·회칙은 해당 시기의 자료로 구분한다. 현행 소개·연혁·회칙을 자동으로 덮어쓰지 않는다.

## 본문·첨부 변환 기준

게시판으로 이관하는 글은 허용된 Tiptap 문단·표·기본 인라인 서식·링크·이미지로 정규화하고 원문 텍스트를 공백 차이 외 동일하게 보존했는지 대조한다. 지원하지 않는 옛 글꼴·색상·상첨자 서식은 원문 백업에 남기고 이관 본문에는 텍스트를 보존한다. 원본 확보 실패 이미지는 누락 안내로 표시하고 변환 결과의 한계를 기록한다.

HWP 첨부의 자동 변환은 로컬 CLI `rhwp`를 사용한다. 사용자가 지정한 변환본은 로컬 선택 기록에 따라 우선 적용한다. 에이전트가 한컴오피스나 외부 변환 웹사이트를 사용하지 않는다. 글자 서식 차이는 허용하되 텍스트·표·이미지 누락이나 읽기 불능은 허용된 서식 차이로 처리하지 않는다. 원본·변환 경고·선택 기록을 보존하고 원문에 없는 데이터를 만들지 않는다. 사용자 제공본의 선택과 변환기 검사 결과는 구분한다.

## 플랫폼별 이관 절차

1. 개발 완료 후 사용자가 지정한 플랫폼·대상 환경·실행 범위만 처리한다.
2. 그 플랫폼의 로컬 백업으로 게시판별 분류·원출처 표시·허용 첨부 변환을 준비하고 대상·보류·누락을 구분한다.
3. 확정한 적용 목록을 기존 저장 계약·[DB 운영 런북](../runbooks/database-operations.md)에 따라 반영한다. 원본/대상 ID·환경·적용 해시는 해당 플랫폼의 로컬 대응표에 기록한다.
4. 새 연결에서 건수·내용·첨부 연결·중복을 확인하고 그 플랫폼의 이관 결과만 보고한다. 다른 플랫폼의 백업·이관 결과로 대신하지 않는다.
