# 다음카페·밴드 이관 기준

로컬 백업 자료를 dgkmaWeb으로 이관할 때 적용하는 분류·공개 범위·저장·변환·검증 기준이다. 수집은 [백업 운영 문서](../runbooks/community-backup.md), 원 게시판별 목적지는 [다음카페 이관 계획](daum-cafe-migration-plan.md)을 따른다.

## 이관 단위와 입력

다음카페 백업, 다음카페 마이그레이션, 밴드 백업, 밴드 마이그레이션은 네 개의 독립 작업이다. 각 작업의 대상·범위·진행 상태·완료 조건·실행 결과를 따로 관리하고 보고한다. 한 플랫폼의 승인·완료를 다른 플랫폼에 적용하거나, 백업 완료를 마이그레이션 시작으로 연결하지 않는다.

- 다음카페 `dkkmob` 마이그레이션: 확정된 전체 자료를 한 번에 반영하는 일회성 이관이다. 증분 비교·병합·재동기화 기능을 만들지 않는다. 대상 환경의 posts 전체 행(일반·경조사·발행·가림·초안 포함)과 종속 댓글은 실제 이관 직전에 리셋한다. 테이블·컬럼·카테고리·회원·명부·회비와 로컬 원본 백업은 삭제하지 않는다. 다음카페 백업만 입력으로 삼고 별도 실행 지시 후 처리한다.
- 밴드 `@dkom` 마이그레이션: 백업 데이터만 날짜 기준으로 증분 수집하며, 이관은 확정한 기준일까지의 전체 백업본을 한 번에 반영하는 일회성 작업이다. 반복 증분 이관·동기화 기능을 만들지 않는다. 다음카페의 분류·변환·적용 결과를 그대로 재사용하거나 완료로 취급하지 않는다.
- 원본과 이관 대응표는 로컬 SQLite에서 관리한다. Replit에 이관 전용 DB·테이블을 만들거나 SQLite·원본 백업을 업로드하지 않는다. 홈페이지에는 선택한 최종 자료·허용 첨부만 목적지별 기존 구조로 이관한다.
- 새 ‘이전 카페’ 게시판을 만들지 않는다. 기존 게시판에 분류한다.
- HWP 등 구형 첨부는 로컬 원본을 보존하고 허용 형식으로 변환한 뒤 이관한다. 이름만 바꾸거나 기존 업로드 보안 규칙을 완화하지 않는다.
- 원본 백업과 변환 결과·이관 상태는 구분한다. 원본 ID·게시판·작성자 표시·작성일·본문·댓글·첨부를 보존하고 비밀번호·쿠키·인증 토큰은 저장하지 않는다.

## 이관 대상 환경

백업→개발 이관과 개발→운영 이전을 분리한다. 백업 입력 도구는 개발 DB·개발 파일 저장소만 대상으로 한다. 개발에서 수정·완성한 이관 게시글(import_data가 있는 발행 글, 가림 상태 포함)과 연결 첨부, 전체 사진첩 카탈로그·사진을 묶어 내보내고 운영 개시 직전에 그 묶음을 운영에 반영한다. 운영은 원본 백업을 다시 읽거나 변환하지 않는다. 회원 계정·명부·회비·세션·일반 테스트 글·초안·댓글은 이 콘텐츠 이전에 포함하지 않는다. 이관 글의 author_id는 NULL이며 명부와 이름으로 연결하지 않는다.

게시글 ID·본문·작성자 표시·원작성일·출처·가림 상태·수정 버전은 개발 완료본대로 유지하고 카테고리는 이름으로 대응한다. 첨부의 앱 내부 경로와 앨범 ID도 유지하되 물리 파일은 운영 저장소에 복사·해시 확인한다. 공개 역사관 JSON·문서·사진은 Git 코드 릴리스로 함께 반영하고 DB 이전 도구로 복제하지 않는다. 원본 백업·SQLite·개발 내보내기 묶음은 비공개로 관리한다. 실제 내보내기·리셋·이전·배포는 별도 실행 지시에서 수행한다.

## 이관 후 공개 범위

이관 자료에는 **dgkmaWeb의 분류 체계와 목적지별 접근 정책**을 적용한다.

| 이관 목적지 | 적용할 열람 범위 |
|---|---|
| 커뮤니티 게시판의 각 카테고리 | 로그인한 승인 회원 전용 |
| 역사관 사진첩 목록·앨범 상세·사진 원본 | 로그인한 승인 회원 전용 |
| 동문회 소개·회칙과 사진첩 외 역사관 자료 | 현재 목적지 정책에 따라 비로그인 공개 |

본문·첨부·사진도 해당 목적지의 열람 범위를 따른다. 원본의 접근 등급은 출처 기록으로 보존하되, 그 등급만으로 추가 승인을 요청하거나 이관을 보류하지 않는다. 목적지의 회원 인증·관리 권한은 유지하며 로컬 원본 백업은 비공개로 보존한다.

## 저장 경계

`local-backups/community/archive.sqlite3`는 수집 목록·본문 원본 참조·파일 참조·내용 해시·원본/대상 ID 대응·변환/적용 상태를 관리하는 로컬 작업 DB다. 디렉터리 0700·파일 0600으로 제한하고 Git·Replit·클라우드 동기화에서 제외한다. 원문 JSON과 다운로드 파일은 같은 로컬 백업 트리에 유지한다. 캐시나 폐기 가능한 앱 테스트 데이터로 취급하지 않는다.

이관 입력은 다음카페 `local-backups/community/daum-dkkmob/`, 밴드 `local-backups/community/band-11089836/`로 구분한다. 공통 SQLite의 `source`·`container_id`로 원천을 식별하며 변환·이관 대응표와 결과 집계에서도 이 구분을 유지한다. 기존 백업·SQLite·실행 영수증을 이동하거나 삭제하지 않는다.

게시글 본문은 기존 `posts.content` Tiptap JSONB에 저장한다. `event_data`·`source_text`는 경조사 전용 의미를 유지한다. 원작성자를 현재 회원과 이름으로 자동 연결하거나 임의의 회원 계정을 만들지 않는다. 원작성자 이름·원작성일·출처 플랫폼·원본 ID·원 게시판·원문 주소는 본문과 분리한 posts 메타데이터로 이관한다. 화면의 작성자·날짜·출처 표시는 해당 DB 값으로 제공한다. 원본 ID/대상 ID의 적용 추적은 로컬 SQLite에도 유지한다. 이관 글의 `author_id`는 회원 계정에 연결하지 않고 NULL로 둔다. 원작성자 이름을 회원 계정 미연결 안내로 대체하지 않으며, 나중에 가입해도 과거 글의 수정·삭제 권한을 부여하지 않는다. 원작성자 이름은 posts.author_name에 저장한다. 다음카페의 등록 작성자가 ‘운영자’이고 제목 끝이 ` / 이름` 형식으로 명확한 경우, 끝의 이름을 author_name으로 옮기고 제목에서는 해당 접미부만 제거한다. 이름으로 회원 계정을 연결하지 않는다. 카페 등록 작성자와 원래 제목은 원본 백업에서 보존하며, 구분자·이름이 불명확한 제목은 임의로 분해하지 않는다. 원작성일·출처는 posts.import_data에 저장하며 [스키마 계약](../reference/database-schema.md#게시글-이관-출처-저장)을 따른다. 일반 작성 API의 회원 인증·작성자 부여, 수정·삭제·가리기 권한은 바꾸지 않는다.

다음카페 이관 게시글은 `import_data.platform=daum-cafe`를 기준으로 본문 바로 위에 한 칸 표처럼 테두리가 있는 공통 안내 박스를 표시한다. 문구는 “[다음카페:동국대학교한의과대학총동창회](https://cafe.daum.net/dkkmob)에서 이관되었습니다.”로 통일한다. 안내는 본문 JSON에 삽입하지 않으며 본문 검색·편집·학술 첫 문단에 섞이지 않는다. 기존 원문 링크와 게시판 출처 표시는 유지한다.

## 자료별 분류

- 원 상위 메뉴·하위 게시판별로 목적지를 정한다. 원본 ID·원 분류·대상 메뉴/카테고리·공개 범위를 이관 대응표에 기록한다.
- 게시판 자료는 기존 게시판의 내용에 맞는 카테고리로 분류한다. 확인되지 않은 내용을 경조사 사실정보로 추정하지 않는다.
- 다음카페 동국임상연구회·학술 게시판 자료는 자유 게시판에 이관하고 본문 첫 문단에 `#학술`을 일반 텍스트로 한 번 넣는다. 학술 카테고리는 신설하지 않는다. 태그 텍스트는 Tiptap JSON에 보존해 향후 본문 검색 대상으로 사용하며, 원분류는 출처·로컬 대응표에 별도로 유지한다.
- 동창회앨범은 회원 전용 역사관 사진첩으로 이관한다. 게시글의 이미지 40개 제한을 적용하거나 앨범을 분할하지 않는다. 목록과 확보한 사진은 대상 환경의 비공개 Object Storage에 저장하며 [역사관 콘텐츠 기준](../reference/heritage-content.md)을 따른다.
- 역대임원 자료는 공개 역사관의 기존 항목과 대조·병합한다. 동일 대수·직책·성명은 합치고 사진을 재사용한다. 회장 재임 기간은 확정된 역대회장 명단을 우선한다.
- 다음카페 모교 연혁은 역사관 이관 대상으로 포함한다. 학교·한의대·부속병원 등의 모교 기록임을 표시하고 동문회 연혁과 구분해 연결한다.
- 과거 인사말·연혁·회칙은 해당 시기의 자료로 구분한다. 현행 소개·연혁·회칙을 자동으로 덮어쓰지 않는다.

## 본문·첨부 변환 기준

게시판으로 이관하는 글은 현재 설치·설정된 Tiptap 스키마의 문단·H1~H4·목록·인용·구분선·코드·표·기본 인라인 서식·링크·이미지로 정규화하고 원문 텍스트를 공백 차이 외 동일하게 보존했는지 대조한다. 굵게·기울임·밑줄·취소선은 HTML 태그뿐 아니라 동일 의미의 인라인 CSS도 해당 Tiptap mark로 변환한다. CSS 글꼴·크기로 제목 레벨을 추측하지 않고 H1~H4 태그를 기준으로 한다. 새 확장이나 임의 CSS·HTML 실행을 도입하지 않는다. 지원하지 않는 옛 글꼴·색상·상첨자 서식은 원문 백업에 남기고 이관 본문에는 텍스트를 보존한다. 원본 확보 실패 이미지는 누락 안내로 표시하고 변환 결과의 한계를 기록한다.

HWP 첨부의 자동 변환은 로컬 CLI `rhwp`를 사용한다. 사용자가 지정한 변환본은 우선 적용한다. 선택된 HWPX는 내부 내용·이미지 대조 없이 첨부하며 외부 PCX 참조 이미지 누락은 원래 문서의 특성으로 기록하고 보류하지 않는다. 원본·변환 경고·선택 기록은 보존한다. 기존 업로드 형식·용량·압축 파일 보안 검사는 유지한다. 에이전트가 한컴오피스나 외부 변환 웹사이트를 사용하지 않는다.

## 플랫폼별 이관 절차

1. 개발 완료 후 사용자가 지정한 플랫폼·대상 환경·실행 범위만 처리한다.
2. 그 플랫폼의 로컬 백업으로 게시판별 분류·원출처 표시·허용 첨부 변환을 준비하고 대상·보류·누락을 구분한다.
3. 확정한 적용 목록을 기존 저장 계약·[DB 운영 런북](../runbooks/database-operations.md)에 따라 반영한다. 원본/대상 ID·환경·적용 해시는 해당 플랫폼의 로컬 대응표에 기록한다.
4. 새 연결에서 건수·내용·첨부 연결·중복을 확인하고 그 플랫폼의 이관 결과만 보고한다. 다른 플랫폼의 백업·이관 결과로 대신하지 않는다.

두 플랫폼의 일회성 이관 실행은 구분한다. posts 전체 리셋은 실제 이관 실행 순서에 맞춰 적용하며, 플랫폼마다 자동 반복해 먼저 이관한 자료를 지우지 않는다. 백업의 증분 수집과 서버 이관은 별개다.
