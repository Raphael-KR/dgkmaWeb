# 이전 커뮤니티 백업과 다음카페 이관

2026-11-13 사용자 결정. 제품 범위는 [계획서](planning-proposal.md#7-다음-개발-목표)를 따른다.

## 확정 범위

- 다음카페 `dkkmob`: 관리자 열람 범위의 로컬 원본 백업 후 dgkmaWeb 이관. 운영 DB 쓰기·배포는 별도 승인 범위다.
- 밴드 `@dkom`: 현재 운영 중이므로 최초 백업과 반복 수집을 준비한다. 홈페이지 이관은 별도 단계다.
- 원본과 이관 대응표는 로컬 SQLite에서 관리한다. Replit에 이관 전용 DB·테이블을 만들거나 SQLite·원본 백업을 업로드하지 않는다. 홈페이지에는 선택한 최종 게시글·허용 첨부만 기존 구조로 이관한다.
- 새 ‘이전 카페’ 게시판을 만들지 않는다. 기존 게시판에 분류한다.
- HWP 등 구형 첨부는 로컬 원본을 보존하고 허용 형식으로 변환한 뒤 이관한다. 이름만 바꾸거나 기존 업로드 보안 규칙을 완화하지 않는다.
- 원본 백업과 변환 결과·이관 상태는 구분한다. 원본 ID·게시판·작성자 표시·작성일·본문·댓글·첨부를 보존하고 비밀번호·쿠키·인증 토큰은 저장하지 않는다.

## 저장 경계

`local-backups/community/archive.sqlite3`는 수집 목록·본문 원본 참조·파일 참조·내용 해시·원본/대상 ID 대응·변환/적용 상태를 관리하는 로컬 작업 DB다. 디렉터리 0700·파일 0600으로 제한하고 Git·Replit·클라우드 동기화에서 제외한다. 원문 JSON과 다운로드 파일은 같은 로컬 백업 트리에 유지한다. 캐시나 폐기 가능한 앱 테스트 데이터로 취급하지 않는다.

기존 `posts.content` Tiptap JSONB에 최종 본문을 저장한다. `event_data`·`source_text`는 경조사 전용 의미를 유지한다. 원작성자를 현재 회원과 이름으로 자동 연결하거나 임의의 회원 계정을 만들지 않는다. 게시글 원출처·작성자·작성일은 이관 본문에 명시하고 원본 ID/대상 ID의 추적은 로컬 SQLite에 둔다. 2026-11-14 후속 결정으로 이관 글의 `author_id`는 NULL을 사용한다. 계정 없는 글을 탈퇴한 회원으로 추정하지 않고 ‘작성자 계정 미연결’로 표시한다. 일반 작성 API의 회원 인증·작성자 부여, 수정·삭제·가리기 권한은 바꾸지 않는다.

## 분류·권한과 변환

다음카페는 일반 게시판 11개와 앨범 게시판 2개에서 170건을 확인했다. ‘한 줄 수다’는 0건이다. 일반 게시글 87건은 개발 DB의 기존 공지·자유·소식 카테고리에 맞춘 분류 미리보기를 로컬에 작성한다. 자료가 없거나 성격이 다른 내용을 경조사 사실정보로 추정하지 않는다. 공개홈의 연혁·인사말을 자동 갱신하지 않는다.

모든 이관 글에 회원 전용 정책을 적용한다. 원 카페의 운영진 한정 등 더 좁은 열람 권한은 확대하지 않는다. 제한 여부가 확인되지 않은 자료는 이관 목록에서 보류한다.

2026-11-14 관리자 화면에서 임원 게시판은 특별회원 이상, Q&A는 운영자 이상, 나머지 게시판은 정회원 이상 열람임을 읽기 전용으로 확인했다. 임원 게시글 1건은 이관 보류하며 Q&A는 0건이다.

같은 날 사용자 정정에 따라 앨범형 자료를 일반 `posts`로 자동 분류하지 않는다. `동창회앨범` 52건은 역사관 사진첩으로 이관하며 게시글의 이미지 40개 제한을 적용하거나 앨범을 분할하지 않는다. 후속 결정으로 역사관 사진첩의 목록·상세·사진 원본을 로그인한 승인 회원만 열람하게 한다. 선택한 앨범 정보와 확보한 사진만 개발 환경의 비공개 Object Storage에 반영한다. DB 테이블을 추가하지 않으며 저장·인증 경계는 [역사관 콘텐츠 기준](../reference/heritage-content.md)을 따른다. 원본에서 확보하지 못한 사진은 누락으로 기록한다.

2026-11-14 후속 사용자 승인으로 `역대임원진` 31건은 기존 공개 역사관 임원 자료에 반영한다. 동일 대수·직책·성명은 기존 항목에 합치고 사진을 재사용한다. 회장 재임 기간은 확정된 역대회장 명단을 우선하며 과거 카페의 상이한 기간으로 덮어쓰지 않는다. 사진첩의 회원 전용 정책은 그대로 유지한다.

일반 글은 허용된 Tiptap 문단·표·기본 인라인 서식·링크·이미지로 정규화하고 원문 텍스트를 공백 차이 외 동일하게 보존했는지 대조한다. 지원하지 않는 옛 글꼴·색상·상첨자 서식은 원문 백업에 남기고 이관 본문에는 텍스트를 보존한다. 원본 확보 실패 이미지는 누락 안내로 표시하고 변환 결과의 한계를 기록한다.

첨부 변환은 로컬 오픈소스 CLI `rhwp`를 사용한다. 2026-11-13 사용자 지시에 따라 공식 안정 릴리스 0.9.0으로 업데이트하고 한컴오피스·외부 변환 웹사이트는 사용하지 않는다. 검사 실패는 실제 영향에 따라 구분한다. 후속 사용자 결정으로 글자 서식 차이는 허용하며 원문 데이터 보존을 기준으로 이관한다. 텍스트·표·이미지 데이터 누락이나 읽기 불능은 허용된 서식 차이로 처리하지 않는다. 원본과 변환 경고는 유지한다. 원격에서 이미 깨진 이미지·파일은 누락으로 기록하고 대체 내용을 만들지 않는다.

## rhwp 결함 기여 준비

2026-11-13 사용자 요청에 따라 글자 서식 차이 1건의 원인을 조사하고 공개용 최소 재현 샘플·버그 보고서·수정안을 준비한다. 원본 백업과 변환물은 기존 위치에 보존하며, 기여용 소스와 합성 샘플은 `/Users/raphael/Playground/rhwp`에서 관리한다. 공개 샘플에 원문·작성자·개인정보를 포함하지 않는다. GitHub 게시 전 최종 본문과 첨부를 사용자에게 제시한다. 이 작업은 dgkmaWeb 런타임 또는 DB 변경을 포함하지 않는다. 2026-11-13 사용자 요청으로 `rhwp 한컴 기호 변환 조사` 대화로 분리했다. dgkmaWeb에서는 기존 백업과 제공된 변환 결과를 사용하며 rhwp 엔진 조사를 중복 수행하지 않는다.

사용자가 직접 한컴오피스로 변환해 제공한 HWPX를 독립 대조 자료로 사용한다. HWP와 HWPX의 문자 표현 길이가 달라져 서식 위치가 바뀌는 것 자체를 결함으로 판정하지 않는다. 한컴 변환 결과와 다른 기호 매핑·문자 경계·검증 판정을 구분해 보고하며, 비공개 원문과 한컴 변환본은 공개 첨부에서 제외한다.

2026-11-14 사용자 결정으로 `dbpl-35.hwp`의 이관용 변환 결과는 사용자가 한컴오피스로 만든 `local-backups/community/conversions/rhwp-0.9.0/inputs/dbpl-35.hwpx`를 사용한다. 로컬 명시적 변환 선택 기록을 CLI 자동 변환 결과보다 우선 적용한다. 원본 HWP·rhwp 변환본·실패 기록은 보존하며, 사용자 제공본의 선택을 rhwp 검사 통과로 바꿔 기록하지 않는다.

후속 사용자 결정에 따라 표준 유니코드 Box Drawing 선기호 128종과 한컴 전용 선기호 후보를 구분한 합성 HWP 1개를 만든다. rhwp 변환은 로컬에서 수행하고 한컴오피스 변환은 사용자가 맡는다. 같은 원본의 두 HWPX를 대조한 뒤 확인된 대응만 수정 대상으로 확정한다. 한컴 전용 후보의 연속 코드값만으로 변환 규칙을 추정하지 않는다.

## 수행 순서

### 날짜별 증분 수집

2026-11-14 사용자 결정으로 기준 시간대는 `Asia/Seoul`이며, 실행 시작 시점의 당일 00:00을 배타적 상한으로 고정한다. 오늘 작성된 게시글·댓글·첨부는 저장하거나 다운로드하지 않는다. 수정 시각이 제공되면 같은 상한을 적용한다. 자동 실행 예약은 이번 결정에 포함하지 않는다.

- 최초 백업에서 빠진 과거 자료는 기존 목록·커서로 이어서 보충한다. 이미 저장한 원본 ID·해시·파일은 재사용하며 매번 전체를 새로 수집하지 않는다.
- 이후 목록 탐색은 마지막으로 완료한 날짜 다음 날부터 전날까지다. 날짜별 목록 탐색 완료와 본문·댓글·첨부 확보 상태를 구분하고 실패·보류 항목은 별도 재처리 대상으로 남긴다.
- 원문을 저장하기 전에 항목별 원본 날짜를 검사한다. 과거 글의 댓글에도 별도로 적용한다. 오늘 자료가 섞인 목록 응답을 통째로 파일에 남기지 않는다. 날짜가 확인되지 않는 새 항목은 날짜 확인 대기로 기록하며 본문·첨부 수집은 보류한다.
- 이미 존재하는 백업은 이 정책 변경을 이유로 삭제하지 않는다. 수집 기준일·시간대·날짜별 건수·보류·실패와 체크포인트를 로컬에 기록한다.
- 밴드의 현재 관찰된 게시글·댓글 응답은 `created_at`을 제공하고 별도 수정 시각을 제공하지 않는다. 따라서 작성일 증분만으로 과거 글의 모든 수정·삭제 또는 실제 수정 날짜를 검출했다고 보고하지 않는다. 수집 중 관찰한 변경은 원본 버전으로 구분하며 원문을 자동 삭제하지 않는다.

### 수집 목록 보완

2026-11-14 재개 시 다음카페 메뉴에서 기존 일반 게시판 11개 외에 `역대 임원진`·`동창회 앨범`의 앨범형 게시판 2개와 `한 줄 수다`를 확인했다. 기존 87건은 일반 게시판 수집 결과이며 전체 카페 백업 완료 건수로 사용하지 않는다. 이 항목들도 원본 날짜와 관리자 열람 범위를 확인해 로컬 백업에 포함한다.

1. 로컬 원본 목록·본문·댓글·첨부를 확보하고 건수·파일·해시와 미확보 사유를 기록한다.
2. 로컬 SQLite에 원본 식별자와 상태를 인덱싱한다. 재수집은 동일 ID/해시를 재사용하고 이전 버전을 보존한다.
3. 기존 게시판별 분류, 원출처 표시, 허용 첨부 변환을 준비하고 대상·보류·누락을 구분한다.
4. 실제 대상 환경과 적용 목록을 확정한 뒤 기존 저장 API·DB 런북에 따라 최종 게시글·첨부만 반영한다. 적용 결과의 대상 ID는 로컬 SQLite에 기록한다.
5. 새 연결의 원본 대비 건수·내용·첨부 연결과 중복 여부를 확인한다. 원본 백업·변환·홈페이지 반영을 서로 대신하는 완료 근거로 쓰지 않는다.

밴드의 새 글 수집만으로 과거 글 수정·삭제를 확인했다고 보고하지 않는다. 과거 변경 확인이 필요하면 전체 목록을 재대조하고 동일 ID/해시의 본문·파일은 재저장하지 않는다. 삭제 여부가 확정되지 않은 자료는 기존 백업을 유지한다.

수집·파일 검증과 당시 이관 전 상태는 [백업 기록](../history/community-backup-2026-11-14.md)에 보존한다. 후속 결정에 따른 개발 DB·Storage·공개 임원 소스 반영과 남은 1건은 [개발 이관 기록](../history/member-albums-2026-11-14.md)에 구분한다. 원문과 상세 대응표는 Git 제외된 로컬 백업 트리에만 보관한다.
