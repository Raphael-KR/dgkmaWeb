# 이관 전 DB 변경안: 동문 사전 등록·게시글 메타데이터


개발 전환 범위는 단일 회원 기본키와 명부 3,458명의 사전 등록이다. 기존 계정은 명부와 정확하게 대조해 같은 동문 행으로 전환한다. 사전 등록은 가입 승인을 부여하지 않는다. 명부 전용 필드는 이 단계에서 연결된 `alumni_database`에 보관한다. 아래의 추가 회원 상태·탈퇴 절차 등은 후속 설계다.

동문 데이터의 users 전환과 posts 출처 저장을 위한 설계다. 관리 원본·탈퇴 보존 범위·고정 ID에 관한 제품 결정은 아래에 반영했다. users 변경과 초기 복사는 미적용이다. posts 메타데이터의 적용 상태는 [스키마 기준서](../reference/database-schema.md#게시글-이관-출처-저장)를 따른다.

## 목표와 범위

- 목표: 전 동문을 users.id로 식별하고 미가입 기록을 연결하며, 카페 원작성자·작성일·출처를 posts에 저장한다.
- 범위: 필드·상태·관리 원본·가입/탈퇴·동기화 종료·집계·전환 순서.
- 완료 조건: 현재 구조와 변경안, 확정 결정, 구현 영향·적용 조건을 설명한다.
- 제외: DB 조회/DDL/DML·Sheets 쓰기·자료 이관·배포·실계정 QA.
- 확인: 현재 소스와 문서 대조, 문서 링크·diff 정합성만 확인한다.

## 확정한 관리 원본과 보존 기준

1. 명부는 최초 이관 입력이다. 한 번 users에 반영한 뒤에는 Google Sheets·alumni_database를 로그인·동문 조회·심사·수정·재가입의 원천으로 다시 참조하지 않는다.
2. 전환 후 지속적인 인물 정보의 정본은 users다. 카카오가 제공하는 가입자 이름·이메일·전화·사진·생일은 기존 사용자 카카오 신원으로 확인한 뒤 갱신한다. 카카오가 제공하지 않는 학과·기수·입학/졸업 정보·직책·관리 메모는 변경하지 않는다.
3. 홈페이지 탈퇴는 동문회 탈퇴로 처리한다. 홈페이지에서 사무국을 통해 회장에게 탈퇴원을 제출한다. 탈퇴 즉시 비공개로 전환하고 아래 [탈퇴 절차](#탈퇴)에 따라 회계·감사 자료의 접근과 보존을 제한한다.
4. 이관 전에는 관리 원본인 `통합주소록` A열(`alumni_uid`)에서 모든 동문에게 연락처 유무와 관계없이 UUIDv4를 한 번 발급한다. 최초 이관 때 원본의 UUID를 그대로 `users.id`에 저장한다. 전환 후 처음 등록하는 동문도 한 번 발급받으며, 전화번호가 바뀌어도 ID를 유지한다.
5. 다음카페 이관 글은 users와 연결하지 않는다. 가입 후에도 수정·삭제 권한을 부여하지 않으며 이름·시각·출처는 posts 메타데이터로 제공한다.

## 현재와 변경 후

| 영역 | 전환 이전 코드 | 목표 구조 |
|---|---|---|
| users | 로그인 회원 중심. name·email 필수, kakao_id NULL 허용 | 모든 동문의 인물 행. 이메일 NULL 허용, 가입 상태·고정 동문 ID·기본 동문 정보 추가 |
| 명부 | Sheets → alumni_database, matched_user_id로 users 연결 | 기존 계정을 정확히 대조해 원본 UUID로 동문을 사전 등록. 전환 후에는 users만 사용 |
| 명부 열람 | 기수가 같거나 조회자의 활동지역이 상대 명부 주소에 포함되면 조회 | 졸업기수가 같거나 양쪽이 직접 등록한 활동지역이 같으면 조회. 관리자는 전체 조회 |
| 신규 가입 | 명부 미연결 행에 대해 users INSERT | users의 미가입 인물과 일치시키고 같은 행에 카카오 신원을 연결 |
| 탈퇴 | users DELETE, 명부/콘텐츠/회비 연결 해제 | 온라인 탈퇴원 제출, 탈퇴 즉시 회원 접근 차단·비공개, 결산 확정 후 자료 정리 |
| 통계 | users 전체가 membersTotal | 전체 동문·미가입·가입 완료·승인 대기 구분 |
| posts | author_name은 개발에 추가됨. 출처는 본문·로컬 대응표 중심 | author_name과 구조화 import_data로 읽기·중복 판정·메타데이터 UI 제공 |

실제 DB 건수·중복·현재 원본은 이번에 조회하지 않았다. [작성자 이름 개발 적용](../history/post-author-name-2026-11-14.md)과 운영 적용을 구분한다.

## users 필드 변경안

| 필드 | 형식·역할 |
|---|---|
| id | UUID PRIMARY KEY, 기본값 없음. 게시글·댓글·회비가 참조하는 유일한 동문 키. 최초 이관은 원본 A열의 UUID를 그대로 저장하며, 이후 새 동문을 명부에 처음 등록할 때만 발급 |
| registration_status | TEXT NOT NULL: pre_registered / registered / withdrawn. 회원 등급과 별개 |
| joined_at | TIMESTAMPTZ NULL. 실제 가입 완료 시각. 인물 행의 created_at과 구분 |
| email | 기존 UNIQUE 유지, NOT NULL만 해제. 미가입·탈퇴는 NULL이며 가짜 이메일을 만들지 않음 |
| alumni_name / alumni_mobile | TEXT NULL. 관리자가 정정할 수 있는 명부 성명·휴대전화번호. 원본에 번호가 없으면 NULL, 대체번호가 있으면 그 값을 유지. 사망 확인 시 [사망 처리 기준](#동문-본인상과-부고-게시글)에 따라 번호 교체 |
| department / generation | TEXT NULL. 학과·졸업기수(시트의 `기수`) |
| admission_date / graduation_date | TEXT NULL. 원문에 있는 날짜 정밀도 유지 |
| alumni_group / alumni_status / alumni_position / alumni_memo | TEXT NULL. 명부의 그룹·상태·동문회직책·메모. 관리자용 범위를 유지 |
| 기존 name·phone_number·email·profile_image·birthday 등 | 카카오 가입 프로필. name은 사전 등록 시 기본 동문 이름으로 초기화하며, 가입 이후 카카오 이름 갱신. 탈퇴 시 가입 프로필을 정리 |
| 기존 graduation_year | 학적 정보에서 도출하는 기존 호환 필드. 카카오 값으로 덮어쓰지 않음 |

주소·일반 전화는 이관하지 않는다. 메모·고정 ID·기본 전화 등 추가 저장 필드를 회원 DTO에 일괄 노출하지 않는다.

명부 목록과 검색은 [회원 열람 범위](planning-proposal.md#접근과-공개-범위)에 따라 조회자와 상대 동문의 `generation`(졸업기수) 또는 `activityRegion`(본인이 직접 등록한 활동지역)이 일치하는지 판정한다. 각 항목은 양쪽 모두 값이 있을 때만 비교한다. 활동지역이 없는 미가입 동문은 같은 졸업기수의 회원에게만 표시하며 관리자는 전체 명부를 조회할 수 있다. 지부 판정에는 옛 명부 주소를 참조하지 않는다.

사전 등록·탈퇴 행은 is_verified=false, is_admin=false, kakao_sync_enabled=false이고 kakao_id=NULL이다. registered 상태만으로 접근을 허용하지 않으며 기존 승인·관리자 가드를 함께 검사한다. 승인 취소/거부를 pre_registered로 덮어써 재로그인을 자동 허용하지 않는다.

카카오 연결 후에는 kakao_id로 기존 사람을 먼저 찾는다. 같은 사람의 프로필이 갱신되어도 명부와 다시 대조하거나 신규 인물을 만들지 않는다. 필수 동의 값 누락·타 계정 이메일/전화 충돌은 구체적으로 처리하며 정상 값을 빈 값으로 덮어쓰지 않는다. 고정 동문 ID는 비밀번호나 인증 수단이 아니다.

### 최초 이관과 등록

- [초기 개발 데이터 정책](../../replit.md#정식-오픈-전-데이터-정책)에 따라 기존 테스트 계정·가입 상태·종속 기록은 전환에 필요한 범위에서 초기화한다. 기존 계정별 UUID 매핑, 글·회비 연결 복원, 임시 NULL 컬럼과 사후 채우기 단계는 생략한다.
- 일회성 이관 CLI는 `통합주소록` A:K를 헤더로 읽고, 원본 행 수와 A열 UUID의 형식·누락·중복을 확인한다. 기존 B:K 동기화는 전환 전 복제본용이다. 원본의 각 동문을 `pre_registered`로 등록하고 연락처가 비어 있어도 포함한다. 동명이인은 각자의 원본 UUID로 구분한다. 가입일·카카오 ID·이메일은 NULL로 두고 로그인 권한을 부여하지 않는다.
- 최초 가입은 카카오가 제공한 이름과 휴대전화를 `users.alumni_name`·`alumni_mobile`과 정규화해 대조한다. `010-0000-NNNN`도 같은 규칙으로 비교한다. 두 값이 모두 일치하는 동문이 한 명이고 사망 상태·기존 카카오 연결·심사 보류·계정 충돌이 없을 때 해당 행을 잠그고 연결한다. 명부 번호가 비어 있거나 카카오 번호와 다르면 관리자 심사로 보낸다.
- 이름·번호 불일치는 승인 대기로 접수한다. 같은 카카오 계정으로 재로그인해도 대기·거부 신청은 한 건으로 유지한다. 본인이 카카오톡으로 신원 확인을 요청하면 관리자는 확인한 내용을 기존 명부 행에 정정한다. 대기 건은 최신 명부와 대조해 승인하고, 거부 건은 재심사로 대기에 돌린 뒤 승인한다. 이 절차에는 신청 삭제나 재접수가 필요 없다.
- 가입 대기·거부·재심사·승인 취소·재가입의 후보 검색은 `users`의 동문 기본 정보로 바꾼다. 심사 기록은 기존 `pending_registrations`에 유지한다.

### 전환 후 명부 등록

- 새 졸업생은 기장이 졸업 직전에 전달한 기수 전체 명부로 졸업식 전에 일괄 등록한다. 최초 이관에 쓴 Google Sheets를 다시 동기화하지 않는다.
- 대학원 동문 등 명부에 처음 등재하는 사람은 관리자가 AI에 SQL 작성을 요청해 DB에 등록한다. 먼저 기존 동문 기록을 확인한다. 같은 사람이 이미 있으면 기존 행과 고정 ID를 유지하고 필요한 항목만 정정한다. 이름·번호 불일치나 홈페이지 미가입만으로 누락으로 분류하지 않는다. [DB 운영 절차](../runbooks/database-operations.md#동문-원본-전환-설계)

### 탈퇴

동문회 탈퇴의 근거는 [회칙 제11조](../../client/src/features/about/bylaws.tsx)다. [「회원관리 및 회계 규정」 개정안 제14조제3항](membership-privacy-amendment.md)에 따라 홈페이지에서 사무국을 거쳐 회장에게 탈퇴원을 제출한 날을 탈퇴일로 기록한다. 제출 즉시 회원·관리자 접근과 기존 세션을 차단하고 회원 정보를 비공개로 전환한다. 회원 검색의 표시 상태는 ‘동문회 미가입자’다. 탈퇴 이력·연락처·프로필·회계 자료는 회원 검색에 제공하지 않는다.

해당 회계연도의 감사와 결산을 확정하는 총회까지 회계·감사에 실제 필요한 최소 정보와 증빙 연결만 담당자가 비공개로 관리한다. 총회 확정 직후 보존 목적이 끝난 정보와 연결을 파기한다. 다른 법령에 따라 보존해야 하는 증빙은 적용 근거와 기한을 확인해 분리한다.

카카오 연결 해제와 OAuth 종료 처리는 회원 접근 차단과 일관되게 처리한다. 미발행 초안은 삭제하고 발행 글·댓글은 작성자 연결을 해제한다. 이관 글의 author_id는 NULL로 유지한다. 재가입에는 새 동의와 자격 확인을 거친다.

### 동문 본인상과 부고 게시글

사무국은 [「회원관리 및 회계 규정」 개정안 제15조제3항](membership-privacy-amendment.md)에 따라 탈퇴 후에도 동문 기본명부에 고정 동문 식별번호, 성명, 입학일자, 졸업일자 및 명부 휴대전화번호를 필요한 범위에서 보유한다. 동문 본인상은 가입 여부와 관계없이 안내한다. 다음은 현행 시트의 사망 처리 방식을 `users` 정본으로 옮기는 설계다.

| 사망 확인 시 대상 | `users`에 기록할 내용 |
|---|---|
| 명부 휴대전화 `alumni_mobile` | 실제 번호를 `010-0000-NNNN` 대체번호로 교체한다. 명부 전체에 부여된 대체번호 중 끝 네 자리의 최댓값에 1을 더하고 네 자리로 표시한다. 연락 불가 등 다른 사유로 부여한 번호도 최댓값 계산에 포함한다. |
| 그룹 `alumni_group` · 상태 `alumni_status` | 각각 `본인사망`, `사망`을 기록한다. 사망 여부는 명부 상태로 판정한다. `registration_status`에는 기존 가입·탈퇴 이력을 유지한다. |
| 메모 `alumni_memo` | 기존 메모를 보존하면서 확인된 사망일을 기재한다. 날짜가 확인되지 않으면 접수일을 대신 입력하지 않고, 확인되면 보완한다. |
| 인물·학적 | `id`, `alumni_name`, `generation`, 입학·졸업 정보는 같은 행에 보존한다. 본인상 안내가 끝나도 이 행과 학적을 유지한다. |

최초 이관 시 시트에서 이미 사망 처리된 행은 배정된 번호·그룹·상태·메모를 그대로 가져온다. 전환 후에는 앱 서버가 최초 사망 처리 시 번호 배정을 직렬화하고 같은 트랜잭션에서 네 필드를 갱신한다. 재처리 시 기존 사망 대체번호를 유지하고 메모의 같은 사망일을 중복 기재하지 않는다. 끝 네 자리가 `9999`에 도달하면 기존 번호를 재사용하거나 일부 필드만 갱신하지 않고 번호 범위 결정을 기다린다.

대체번호는 [가입 대조](#최초-이관과-등록)에 포함하며 실제 연락처 표시·문자 발송 대상에서는 제외한다. 대체번호만 있는 생존 동문도 있으므로 사망 여부는 `alumni_status = '사망'`으로 판정한다. 전환 후 사망 처리된 동문은 로그인·기존 세션·가입 연결을 차단하고 카카오 계정에 남은 `phone_number`로도 문자를 보내지 않는다. 부고 제보나 게시글 작성만으로 명부를 변경하지 않고 사무국의 사망 확인을 기준으로 처리한다.

#### 사무국 부고 안내 절차

사무국은 상주 또는 기수 대표의 부고 안내 요청을 문자나 카카오톡으로 접수한다. 요청 대화에서 상주가 공유에 동의한 정보 항목과 안내 대상을 확인한다. 기수 대표가 요청한 경우에도 상주가 동의한 범위를 확인한다. 상주의 이름·연락처 등은 동의한 항목만 회원 전용 게시판, 카카오톡 권리회원 단체방, 전회원 문자 중 동의한 대상에 해당하는 채널로 안내한다.

홈페이지에서 상주 정보는 부고 게시글의 `posts.content`와 `posts.event_data`에서 관리하며, 동문이나 상주의 `users` 행에 옮기지 않는다. 작성자는 기존 미리보기·게시 확인 절차를 따른다. 외부 채널 안내는 사무국이 담당한다. [개인정보보호위원회 사망자·유족 정보 해설](https://www.korea.kr/news/policyNewsView.do?newsId=148933606)

사무국은 게시 요청을 받을 때 회원 전용 부고 게시글을 별도의 삭제 요청이 있을 때까지 보존한다는 점을 요청자에게 안내한다. 삭제 요청을 받으면 홈페이지의 해당 게시글 전체를 삭제한다. 수신자에게 전달된 문자·카카오톡과 고인의 명부 기록은 각각 별도로 취급한다.

## posts 필드 변경안

| 항목 | 저장·표시 |
|---|---|
| author_id | 기존 users FK. 이관 글은 NULL. 표시명으로 회원을 자동 연결하지 않음 |
| author_name | 원작성자 이름 TEXT NULL. 개발 구현 유지 |
| import_data | JSONB NULL 신설. 원본 정체성·원작성일·출처·이관 시각 저장. 일반 작성/수정 API는 입력 불가 |
| content | 본문·허용 서식. 작성자/날짜/출처 안내 문단은 합성하지 않음. 학술 자료는 첫 문단 #학술 |
| published_at | 원작성 시각으로 기존 정렬 유지. 시간대 변환을 명시하고 원본 정밀도에 맞춰 표시 |
| created_at | 대상 행 생성 시각. 원작성일과 구분 |

import_data의 필수 항목은 schemaVersion=1, platform(daum-cafe 또는 band), containerId, sourceId(게시판ID:글번호), boardPath, url, originalCreatedAt(시간대 포함 ISO), timePrecision(minute 또는 day), importedAt이다. 계약은 코드의 검증 스키마와 DB CHECK를 함께 정의한다. 인증정보·원문 전체·로컬 경로는 넣지 않는다. 경조사의 event_data·source_text를 전용하지 않는다.

플랫폼/컨테이너/복합 원본 ID에 부분 UNIQUE 표현식 인덱스를 추가해 중복 이관을 막는 안이다. 원본 ID 없는 항목은 임의 식별자를 만들지 않고 개별 보류한다. 날짜만 확인되는 원문은 KST 날짜와 day 정밀도를 유지하고 UI에 임의의 00:00을 노출하지 않는다. published_at의 기존 timestamp without time zone에는 ISO 시각을 UTC 기준으로 명시적으로 변환해 저장한다.

목록·상세·검색·가린 글은 연결 users.name → author_name → 작성자 정보 없음으로 표시한다. 원작성일·플랫폼·게시판·출처 링크는 본문 밖의 메타데이터 UI에서 제공한다. 적용 상태·원본/대상 ID·영수증은 로컬 SQLite로 추적하며 서버에 이관 전용 테이블을 추가하지 않는다.

## 구현과 전환 순서

1. **전환 코드 준비.** Replit 개발용 Drizzle 스키마와 변경 SQL에 `users.id UUID PRIMARY KEY`를 기본값 없이 정의한다. 회원 FK 다섯 개를 UUID로 바꾼다. 게시글·댓글·명부 복제 행 자체의 ID는 정수로 유지한다. 현재 회원 행을 생성하는 자동 가입·관리자 승인 경로는 같은 사전 등록 행을 갱신하도록 준비하고, 회원 API의 입력·응답에서는 UUID를 제외한다. 전환 전에 일회성 명부 이관 CLI와 대조 절차를 준비한다.
2. **개발 DB 적용.** 실행 전에 대상이 `heliumdb`인지, 어떤 테스트 행·회원 연결·세션이 영향을 받는지 건수로 확인한다. 전환 중에는 이전 코드의 회원 쓰기를 중지한다. 기존 회원을 명부에 정확히 대조하고 기본키와 외래키를 같은 트랜잭션에서 변환한다. 기존 정수 ID 세션은 만료한다.
3. **명부 사전 등록.** 최초 명부의 UUID 집합을 그대로 저장한다. 카카오 연결이 없는 행은 미가입이고 회원 이메일은 NULL을 허용한다. 기존 명부 필드와 회원의 관계는 `matched_user_id`로 유지한다. 새 연결에서 UUID 집합과 가입 상태별 건수를 대조한다. [개발 적용 결과](../history/member-uuid-2026-11-20.md)
4. **회원 기능 전환.** 자동 가입과 관리자 승인은 UUID 없는 행을 새로 생성하지 않고 조건에 맞는 사전 등록 행에 카카오 계정을 연결한다. 새 코드와 명부가 준비된 뒤 가입을 재개한다. 탈퇴·심사·조회 권한·기수·호칭·통계도 새 상태를 사용하며 행이 존재한다는 이유만으로 회원 권한을 부여하지 않는다.
5. 전환을 마치면 런타임과 운영 도구의 Sheets/`alumni_database` 참조를 종료한다. 원본·옛 테이블·Secrets 삭제 및 운영 환경 적용은 별도 작업이다. 개발 코드는 Replit에서 필요한 정적 검사만 수행한다. 게시글 메타데이터와 카페 자료 이관은 [별도 이관 계획](daum-cafe-migration-plan.md)을 따른다.
