# 동국대학교한의과대학동문회 제품·개발 통합 계획서

> 갱신일: 2026-11-10
> 제품 목표, 확정 정책, 현재 구현 범위와 남은 기능 개발을 관리합니다. 운영 환경별 최신 적용 상태는 [Replit 현재 상태](../../replit.md#현재-적용-상태), 날짜별 결과는 [이력 색인](../history/README.md)에서 확인합니다.

게시판 통합부터 본문 JSONB·canonical, 게시글 관리와 URL 정정까지 PR #22~28로 main에 통합하고 Replit 운영에 반영했습니다. 아래 `구현됨`은 코드 범위를 뜻하며 사용자 흐름의 전체 확인과 구분합니다.

## 1. 개발 방향

현재는 기능 개발 단계입니다. 회원·게시판·경조사와 게시글 수정·삭제·가리기 기반이 있고 관리자 기초 통계도 운영 코드에 반영했습니다. 추가 리포트, 역사 자료·사진 탐색, 메시지 발송, 실제 결제, 주문 관리 등 구현할 기능이 남아 있습니다.

- 다음 작업은 사용자에게 필요한 기능과 현재 구현의 빈 부분을 기준으로 정합니다.
- 개발 직후 점검은 변경 범위에 필요한 정적 검사로 최소화합니다. 구체적인 실행 기준은 [AGENTS.md](../../AGENTS.md#개발-직후-점검)를 따릅니다.
- 이 계획서에는 기능의 입력·처리·화면, 남은 구현과 제품 결정을 적습니다. 실행 절차와 과거 작업 기록은 담당 문서에서 관리합니다.
- `구현됨`은 표에 적힌 코드 범위가 있다는 뜻입니다. `부분 구현`은 사용자 기능의 일부가 남은 상태이고, `미구현`은 해당 기능을 만들어야 하는 상태입니다.
- 정책·공급자·공개 범위가 미정인 항목은 결정할 내용을 명시합니다. 새 결정의 반영 순서는 [AGENTS.md](../../AGENTS.md#결정-반영과-실행-순서)를 따릅니다.

## 2. 제품 목표와 원칙

- 동문회 소개·회칙·회비·경조사 지원을 비회원에게 제공하는 공식 공개 홈페이지를 운영합니다.
- 카카오 로그인을 완료한 동문에게 주소록, 게시판, 경조사, 프로필과 회비 상태를 제공하는 모바일 우선 회원 서비스를 운영합니다.
- PC에서는 비영리 단체와 동문회의 역사·조직·공신력을 전달하는 정돈된 공식 화면을 유지합니다.
- 개인정보는 기능에 필요한 최소 범위만 수집·노출하며 회원 전용 데이터 API는 서버 세션으로 보호합니다.
- 반복 관리 지점을 줄이되 데이터 무결성과 운영자가 확인할 수 있는 복구 절차를 유지합니다.

## 3. 확정된 운영 정책

### 회원과 카카오 로그인

- 로그인은 카카오 REST OAuth authorization-code 흐름을 사용하고 서버가 토큰 교환과 회원 처리를 완료합니다.
- 개발·운영 카카오 앱과 Secret을 분리하며 `REPLIT_DEPLOYMENT="1"`일 때만 운영 설정을 선택합니다.
- 필수 동의는 이름, 카카오계정 전화번호와 이메일이며 선택 동의는 프로필 사진과 생일입니다. 운영 앱만 대표 채널용 `카카오톡 채널 추가 상태 및 내역(plusfriends)`을 추가로 선택 동의 요청하고, 공식 테스트 앱을 사용하는 개발 OAuth에서는 해당 항목을 요청하지 않습니다.
- CI, 카카오 닉네임, 성별, 연령대, 출생 연도, 친구 목록과 메시지·캘린더 접근권한은 사용하지 않습니다.
- 신규 가입은 정규화한 이름·전화번호가 명부의 미연결 행 한 건과 일치하고 기존 계정의 이메일·전화번호 충돌 및 동시 명부 연결 충돌이 없을 때 사용자 생성과 명부 연결을 확정합니다. 명부 불일치·중복·계정 충돌은 회원 가입을 확정하지 않고 `pending_registrations`에서 관리자 승인을 기다립니다. 거절·종료된 OAuth나 유효하지 않은 요청은 해당 오류로 차단하며 가입 대기로 간주하지 않습니다.
- 관리자 가입 승인 대기·거부 목록에는 신청 당시 대기 사유와 조회 시점의 PostgreSQL 명부 대조 결과를 구분해 표시합니다. 이름 또는 전화번호가 일치하는 후보의 이름·기수·졸업 정보, 두 필드의 일치 여부와 기존 회원 연결 여부를 확인합니다. 신청 전화번호와 명부 전화번호는 관리자가 전체를 대조할 수 있도록 표시하며, 관리자 전용 심사 API·화면에서만 제공합니다. 대기·거부 심사 응답에는 카카오 식별자·가입 JSON·생일·사진을 포함하지 않습니다. 후보는 정확 일치를 우선해 최대 5건과 전체 후보 수를 표시합니다. 필수 정보 누락·일치 없음·중복·기존 연결·계정 충돌을 구분하며, 조회 결과가 승인 조건을 충족할 때 승인 버튼을 활성화합니다. 수동 재대조는 DB 복제본을 다시 읽으며 Sheets 동기화나 회원 변경을 수행하지 않습니다. 실제 승인은 기존 트랜잭션에서 최신 조건을 다시 검사합니다.
- 이름·전화번호의 각 대조 항목은 기존 정규화 기준으로 일치하면 명부의 값 하나와 `일치` 표시를, 불일치하면 `신청`·`명부` 값만 모두 표시합니다. 서로 다른 글자는 양쪽에서 강조하며 신청은 연한 노란색, 명부는 연한 파란색을 사용합니다. 색과 함께 출처 라벨을 유지하고 별도의 `불일치` 배지는 붙이지 않습니다. 비교할 값이 없으면 `정보 없음`으로 구분하며, 기수·졸업 정보처럼 신청 측에 없는 참고 정보에 일치 표시를 만들지 않습니다.
- 각 명부 후보에는 12개 관리 항목인 학과·기수·성명·입학일·졸업일·주소·핸드폰·전화·그룹·상태·동문회 직책·메모를 모두 표시합니다. 성명·핸드폰은 위 대조 영역에 한 번 표시하고 나머지는 명부 참고 정보로 제공합니다. 빈 값은 `정보 없음`으로 표시하며, 관리자 심사 외 공개·일반회원 명부 API의 노출 범위는 확대하지 않습니다.
- 2026-11-12 결정에 따라 관리자 `인증 완료` 목록은 회원 관리 정보로 제공합니다. 현재 회원 저장값의 이름·이메일·전체 전화번호·프로필 사진·생일·양력/음력·윤달 여부와 가입 후 입력한 활동지역을 표시합니다. 과거 신청 시점의 원문으로 표현하거나 명부 값으로 대체하지 않습니다. 동문 명부는 이름·전화번호 검색 후보 대신 `matched_user_id = 회원 ID`로 실제 연결된 행을 조회합니다. 후속 결정에 따라 `연결된 동문 명부`는 주소(`address`)·전화(`phone`)를 조회·응답·화면에서 제외한 10개 관리 항목을 제공합니다. 핸드폰(`mobile`)과 현재 회원의 전화번호, 대기·거부 심사의 후보 12개 항목은 유지합니다. 회원 정보와 명부 정보의 출처를 구분하고 빈 값은 `정보 없음`, 연결 행이 없으면 `연결된 명부 없음`으로 표시합니다. 여러 연결 행이 있으면 모두 표시하며 임의로 한 건만 고르거나 자동 연결·정정하지 않습니다. 카카오 내부 식별자·인증정보·원본 가입 JSON은 응답과 화면에서 제외하며 일반회원 공개 범위는 유지합니다.
- 관리자 가입 관리의 상태는 `승인 대기`·`인증 완료`·`승인 거부`입니다. 승인 대기에는 `승인`·`거부`, 인증 완료에는 `승인 취소`, 승인 거부에는 `재심사`·`삭제` 버튼을 제공합니다. 재심사와 승인 취소는 승인 대기로만 이동하며 재승인에는 최신 명부 대조가 필요합니다. 자동 가입한 회원도 인증 완료 목록에 포함합니다.
- 2026-11-12 결정으로 가입 거부는 신청정보를 삭제하거나 카카오 연결을 해제하지 않고 `rejected`로 보존합니다. 승인 취소는 기존 회원의 `isVerified`를 끄고 심사 대기로 전환합니다. 계정·게시글·댓글·회비·명부 연결은 보존하며 현재 세션을 종료하고 이후 회원 API 접근·로그인 완료를 차단합니다. 대기·거부 중 재로그인으로 자동 승인하거나 거부 상태를 초기화하지 않습니다. 회원 재승인 시 본인 계정·명부 연결은 충돌에서 제외하되 타인 연결과 중복은 계속 차단합니다. 관리자는 자신의 승인을 취소할 수 없습니다.
- 승인 거부의 `삭제`는 카카오 연결 해제 성공 또는 이미 해제된 상태를 확인한 뒤 해당 카카오 신원의 신청정보만 삭제합니다. 실패하면 신청을 보존합니다. 기존 계정·글·댓글·회비·명부 연결은 보존하며 회원 탈퇴로 처리하지 않습니다. 기존 계정은 미승인 상태를 유지하고 카카오 연결 상태만 해제합니다. 삭제 이전 OAuth와 세션은 무효화하며, 이후 새 로그인은 새 신청으로 접수해 관리자 승인 없이 복구되지 않도록 합니다. 삭제 버튼은 확인창에서 이 범위를 안내합니다.
- 기존 `pending_registrations.status`와 `users.is_verified`를 사용하며 DB 구조·회비 판정은 변경하지 않습니다. 가입 거부·승인 취소·재심사는 관리자 권한과 현재 상태를 서버에서 다시 검사하고 신원 잠금·트랜잭션으로 처리합니다. 취소 이전에 시작된 OAuth와 늦게 저장된 세션으로 접근이 복구되지 않도록 합니다. 과거 거부 처리로 이미 삭제된 신청정보는 복원하지 않습니다.
- 회원 탈퇴는 카카오 연결 해제 성공 또는 이미 해제된 상태를 확인한 뒤 신청정보와 해당 회원 계정·세션을 정리합니다. 회원 계정 정리 시 미발행 경조사 초안은 삭제하고, 명부는 회원 연결만 해제하며 게시된 콘텐츠·결제 기록은 작성자·사용자 연결을 해제해 보존합니다. 종료 경쟁을 막는 HMAC 식별 해시와 종료 시각은 별도로 유지합니다.
- 로그아웃은 서버의 세션 종료 성공을 확인한 뒤 완료로 표시합니다. 실패하면 로그인 상태를 임의로 비우거나 성공 안내를 띄우지 않고 재시도할 수 있게 합니다. 성공 시 브라우저의 회원 조회 캐시도 비웁니다.
- 활동지역 입력은 `activityRegion` 한 필드로 받습니다. 사용하지 않는 `region` 별칭과 `/api/auth/callback` 호환 경로는 제거하며 실제 Kakao 인가·콜백, 서버 세션과 등록 권한은 유지합니다.

### 회원 등급과 회비

- `회원`: 동문 자격 확인과 가입을 완료한 사용자입니다. 현재 화면의 기본 등급 표기는 `일반회원`입니다.
- `권리회원`의 목표 정책은 공개된 회원관리 및 회계 규정입니다. 평가월까지 직책별 최소 월회비 누계 또는 해당 직책의 연납 기준액을 충족하면 판정합니다. 같은 회비연도의 여러 직책은 가장 높은 기준을 적용하고, 명예회원은 납부 여부만으로 권리회원으로 전환하지 않습니다.
- 2026-11-10 사용자가 공개 규정 기준을 선택했습니다. [확정 결정 기록](../decisions/0005-membership-public-regulations.md)에 대안·선택 이유·후속 구현 범위를 기록합니다.
- **현재 구현의 차이:** 서버는 아직 KST 당해년도 `연회비` 중 `completed` 기록 합계 50,000원으로 판정합니다. 목표 정책 적용에는 직책·귀속월·조정 기록과 과거 상태 보존 구현이 남아 있습니다. 목표 정책의 확정과 계산·DB 적용을 구분하며 공개 규정 원문은 유지합니다.
- **개발 보류:** 2026-11-10 사용자 요청에 따라 회비·권리회원 관리와 관리자 납부 관리의 신규 개발은 Google Sheets 명부 구조와 직책·회비 자료의 관계를 확인한 뒤 재개를 결정합니다. 공개 규정 기반 목표 정책, Sheets 관리 원본·PostgreSQL 복제본 구조와 현재 동기화·판정 동작은 유지합니다.
- 화면의 등급·완료 금액·최근 완료 연회비 날짜와 경조사 호칭은 서버의 회원 상태 응답을 사용합니다. LLM이나 클라이언트가 목표 정책을 추정해 현재 권한을 바꾸지 않습니다.
- 현재 표시는 내부 납부 기록을 사용하며 실제 결제 승인, 정기결제, 취소·환불 또는 영수증 발급을 의미하지 않습니다.

### 동문 명부

- 사용자가 확정한 최종 원본 전환을 이 절과 [DB 운영 런북](../runbooks/database-operations.md)에 반영하기 전까지 Google Sheets를 동문 명부의 **관리 원본**으로 유지합니다.
- Development Database와 Production Database의 PostgreSQL `alumni_database`는 로그인·가입 심사에 사용하는 **런타임 복제본**입니다.
- 로그인 요청은 Google Sheets를 직접 조회하지 않습니다. 관리자가 명시적으로 실행하는 동기화로 PostgreSQL 복제본을 갱신합니다.
- 2026-11-12 결정에 따라 `통합주소록`의 관리 컬럼은 학과·기수·성명·입학일자·졸업일자·핸드폰번호·그룹·상태·동문회직책·메모 10개입니다. 시트에서 삭제한 주소·전화번호는 동기화 대상에서 제외하며 DB의 `address`·`phone` 컬럼과 기존 값은 보존합니다. 회원의 전화번호와 명부의 핸드폰번호는 유지합니다.
- 명부 동기화는 개인정보 없는 변경 집계를 먼저 미리보고, 같은 원본 fingerprint를 다시 확인한 뒤에만 적용합니다. 위 10개 컬럼 헤더, 필수값, 핸드폰번호 형식, 중복 또는 동시 실행 오류가 있으면 DB를 변경하지 않으며 DB에만 있는 행은 자동 삭제하지 않습니다.
- 명부 데이터의 명시적 삭제는 위 동기화의 값 보존과 구분합니다. 2026-11-12 개발 명부에 이어 운영 명부도 데이터가 있으면 전체 행과 종속 이름·별칭을 백업 없이 초기화하도록 승인됐습니다. 테이블·주소·전화 컬럼은 유지하며 회원 계정·게시글·회비·Google Sheets 원본은 삭제하지 않습니다. 자동 재동기화는 하지 않습니다. 환경별 실행 결과와 복구 이력의 확인 한계는 [명부 초기화 기록](../history/alumni-reset-2026-11-12.md)에 남깁니다.
- `ALUMNI_SPREADSHEET_ID`, `GOOGLE_PRIVATE_KEY`, `GOOGLE_SERVICE_ACCOUNT_EMAIL`과 관리자 동기화 기능은 PostgreSQL 단독 원본 전환의 결정·적용 순서가 기준 문서에 반영될 때까지 유지합니다. 실제 종료·제거는 DB 운영 런북의 적용 순서와 조건을 따릅니다.

### 접근과 공개 범위

- 동문 주소록은 회원 전용이며 일반회원은 본인의 기수 또는 활동 지역 범위만 조회합니다. 주소·전화번호·메모는 목록 API에 노출하지 않습니다.
- 커뮤니티 검색의 동문 검색어는 이름·기수에 적용합니다. 게시글 검색 결과는 해당 글의 상세로 연결합니다. 조회 실패와 조회 결과 없음은 화면에서 구분합니다.
- 회비·명부·댓글·게시판·게시글 수정·관리자 연결 상태는 조회 실패를 계속 로딩, 빈 결과, 정보 부족이나 권한 부족으로 바꾸지 않습니다. 실패는 공통 오류 안내와 재조회로 처리하며, 성공한 별도 조회 영역은 계속 표시합니다.
- 활동 지역 변경 후에는 이전 명부 목록·검색 캐시를 비우고 서버의 새 열람 범위로 다시 조회합니다. 일반 글·경조사 게시와 수정·삭제·가림은 공통 게시글 갱신 경로로 목록·상세·검색에 반영합니다.
- 명부의 카카오톡 방은 `권리회원 단톡방`으로 제공합니다. 서버의 현재 권리회원 판정을 충족한 회원에게만 참여 주소를 제공하고, 일반회원에게는 `/about/dues` 회비 안내를 표시합니다. 홈페이지의 공개 카카오 채널과 단체방 참여 주소는 구분합니다.
- 모든 `posts`는 회원 전용입니다. 공지·자유·행사·소식과 부고·경사에 같은 원칙을 적용합니다. 목록·상세·검색·댓글·첨부와 생성·초안·등록 API는 서버 세션으로 접근을 제한합니다. 화면의 로그인 처리만으로 대신하지 않습니다.
- 비회원용 링크 미리보기와 검색엔진 메타데이터에 게시글 제목·본문·경조사 정보를 내보내지 않습니다. 공개 홈페이지와 정적 안내는 게시글 데이터와 분리합니다.
- 일반회원은 본인 경조사만 등록합니다. 관리자는 입력한 동문 이름 또는 명부에 등록된 공식 별칭과 학번이 명부에서 정확히 한 명과 일치할 때만 다른 동문의 경조사를 대리 등록할 수 있습니다. 개명 전 이름은 Google Sheets 복제 이름을 덮어쓰지 않고 별도 `alumni_name_aliases` 레코드로 보존하며, 현재 공식 이름 1개만 미리보기·게시 표시명으로 사용합니다.
- 공개 `/about/condolence`는 경조사 지원 절차를 설명하는 정적 안내이며 회원 경조사 데이터와 분리합니다.
- 실제 결제 연동 전에는 결제 기록을 관리자만 생성할 수 있습니다.

### 권리회원 단톡방 (2026-11-11)

- 사용자가 제공한 초대 주소는 서버 전용 Replit Secret `KAKAO_RIGHTS_GROUP_INVITE_URL`로 관리합니다. 공개 저장소·브라우저 번들·`VITE_` 변수·공개 페이지·로그에 원문을 넣지 않습니다.
- 명부 안내는 기존 회원 등급 API를 사용합니다. 참여 버튼을 누를 때 서버가 세션의 실제 회원과 최신 회비 상태를 다시 조회하며, 일반회원은 참여 주소 API에서도 차단합니다. 관리자라는 이유만으로 권리회원 제한을 우회하지 않습니다.
- 현재 서버의 `getMembershipStatus`를 재사용하며 회비 판정·DB 구조는 바꾸지 않습니다. 회원 상태 조회 실패는 오류·재조회로 표시하고 일반회원이나 준비 중으로 바꾸지 않습니다.
- 초대 주소 응답은 캐시하지 않고 필요한 참여 요청에만 제공합니다. 설정 누락·잘못된 카카오 초대 주소는 연결 오류로 처리하며 공개 채널 주소로 대체하지 않습니다. 이미 전달된 초대 주소의 재공유나 카카오 방 자체의 가입 심사는 홈페이지의 접근 제한과 별개입니다.
- `2.0.0`으로 운영에 반영했습니다. 비로그인 API의 인증 차단과 캐시 금지 응답을 확인했으며, 실제 회원의 주소 수신·단톡방 가입은 확인하지 않았습니다. [릴리스 기록](../history/release-2.0.0-2026-11-11.md)을 따릅니다.

### 관리자 기초 통계

- 2026-11-10 사용자 요청에 따라 기존 PostgreSQL 자료의 읽기 집계와 관리자 통계 탭을 구현합니다. 서버의 공통 관리자 권한 검사를 사용하며 회원 식별자·이름·연락처·게시글 원문을 통계 응답에 포함하지 않습니다.
- **조회 시점 현황:** `users`의 현재 회원 수, `pending_registrations.status = 'pending'`인 가입 대기 수, `alumni_database`의 전체·연결·미연결 행 수를 표시합니다. 명부 연결은 `matched_user_id`를 기준으로 하며 연결된 회원 수는 중복 없이 셉니다. 명부 행 수와 회원 수를 같은 단위로 취급하지 않습니다.
- **기간별 게시글:** `is_published = true`인 글을 발행일(`published_at`, 없으면 `created_at`) 기준으로 집계합니다. 한국시간(`Asia/Seoul`) 시작일 0시부터 종료일 다음 날 0시 직전까지이며 기본은 오늘 포함 최근 30일입니다. 최근 7·30·90일과 직접 날짜 선택을 제공하고 일별 표시 범위는 한 번에 최대 366일입니다.
- 선택 기간의 전체·표시·가림 건수와 분류별·일별 건수를 제공합니다. 가림 여부와 분류는 조회 시점의 값이며 비활성 분류도 포함하고 분류 없는 글은 `미분류`로 표시합니다. 초안·삭제된 글은 제외하며 두 날짜가 모두 없는 발행 글은 기간 통계에서 제외한 건수를 따로 안내합니다. 없는 날짜의 발행 건수는 0으로 표시합니다.
- 회원·가입 대기·명부는 현재 현황이며 과거 시점의 회원 수·신청 유입·삭제 이력을 재구성하지 않습니다. 명부의 최신성은 마지막 관리자 동기화로 반영된 복제본 기준입니다. 통계 조회는 Sheets 조회·동기화와 외부 분석 서비스 호출을 하지 않습니다.
- DB 구조·마이그레이션·집계 저장 테이블과 회비·권리회원 판정을 변경하지 않습니다. 이런 변경이 필요해지면 현재 구조·동작과 변경안을 설명하고 사용자 승인을 먼저 받습니다. 납부·권리회원 통계와 파일 내보내기는 이번 범위에서 제외합니다.
- 초기 개발은 집계 API·기간 선택·오류/빈 결과 표시의 Replit 개발 반영과 정적 검사까지 수행했습니다. 후속 사용자 요청으로 통계 및 기타 미커밋분의 commit·push·PR·main 병합·Replit 릴리스를 완료했습니다. DB 구조·회비 판정 변경과 실계정 QA는 포함하지 않았습니다.
- 적용 상태: [PR #30](https://github.com/Raphael-KR/dgkmaWeb/pull/30)으로 집계 API와 통계 탭을 main에 통합하고 Replit 운영 코드에 반영했습니다. 실제 DB 집계·화면 동작은 실행하지 않았습니다. 정적 검사와 Git·운영 반영, 비로그인 smoke는 [수행 기록](../history/admin-statistics-2026-11-10.md)에서 구분합니다.

### 게시글과 경조사 통합

- `posts`를 모든 게시글의 공통 저장소로 사용하고 `categories`로 분류·표시합니다. 경조사 전용 `community_events`와 레거시 `obituaries` 테이블은 통합에서 삭제했습니다. 경조사 상세를 별도 1:1 테이블로 남기는 안은 채택하지 않습니다. 삭제 대상은 이 두 테이블이며 PostgreSQL 데이터베이스 전체가 아닙니다.
- 부고·경사의 구조화 정보는 `posts` 내부 JSON으로 저장합니다. 공통 제목·본문·작성자·분류·게시 상태·시각은 게시글의 공통 정보로 관리합니다. JSON의 물리 타입과 계약은 [DB 구조 기준서](../reference/database-schema.md#게시글과-경조사-json-계약)에 적습니다.
- 기존 경조사·레거시 부고 데이터와 상세 주소는 폐기했습니다. 출시 전이므로 마이그레이션, ID 매핑, 옛 상세 주소 호환을 만들지 않습니다. 기존 일반 게시글·댓글·명부는 이 폐기 결정에 포함하지 않습니다.
- 기존 공지·자유·행사·소식에 `부고`·`경사` 카테고리를 추가합니다. `경사`의 JSON 유형은 `결혼`·`개원`만 사용합니다. `기타` 유형은 제거하며 `경조사`라는 통합 카테고리는 만들지 않습니다. 새 부고·경사는 공통 게시판의 목록·상세·검색·댓글·첨부 구조를 사용합니다.
- 게시문 호칭은 부고·경사 모두 `동문·회원·권리회원`으로 통일합니다. `정회원`은 `회원`으로 정규화하며 다른 등급으로 바꾸거나 미확인 등급을 추정하지 않습니다. 화면의 기존 `일반회원` 표기와 게시문의 `회원`은 같은 기본 회원 등급을 뜻합니다.

### 일반 게시글 입력과 초안 수명

- 새 글과 수정의 새 제목은 공백 제거 후 1~300자, 본문 이미지·일반 파일 링크와 별도 첨부 이미지는 합계 최대 40개이며 그 안에서 일반 파일은 최대 5개입니다. 업로드 전과 게시글 저장 시 같은 공통 검증을 사용합니다. 이미지는 유효한 `/objects/` 상대 경로만 받고 실제 열람 권한을 서버가 확인합니다. 배열 요소를 문자열로 강제 변환하지 않습니다.
- 이전 글이 새 제목·개수 제한을 벗어나더라도 자동 절삭·삭제하지 않습니다. 제목을 그대로 유지하거나 기존 첨부만 유지·줄이면 본문 등 다른 내용을 수정할 수 있습니다. 제목을 변경하거나 첨부를 추가·교체하면 공통 제한을 적용합니다. 경로 문법·열람 권한·작성자·revision 검사에는 보존 예외를 만들지 않습니다.
- 글쓰기 창의 취소·닫기·게시 성공은 같은 초안 초기화를 사용합니다. 업로드 묶음과 게시 요청 중에는 창 닫기·입력 변경·중복 요청을 막으며, 실패하면 작성 내용을 유지합니다. 업로드 파일의 물리 삭제나 자동 게시를 추가하지 않습니다.

### 게시글 본문 서식 (2026-11-09)

HWP·구형 Office·매크로 전용 문서·압축파일·실행파일은 허용 목록에 넣지 않습니다. 후속 결정으로 일반 파일은 파일당 10MB·게시글당 5개로 제한합니다. 이미지의 파일당 5MB와 이미지·일반 파일 합계 40개는 유지합니다. 일반 파일 개수는 본문에 이미 있는 파일을 포함하며 같은 경로의 텍스트 서식 분할·중복 링크를 하나로 계산합니다. ### 댓글 수정·가리기·첨부 (2026-11-12)

- 댓글은 일반 텍스트 1,000자를 유지한다. 작성자는 본인 댓글을 수정·삭제하고 관리자는 모든 댓글을 가리거나 복원한다. 관리자도 타인의 댓글을 수정·삭제하지 못하며 본인 댓글에는 작성자 권한을 적용한다.
- 수정은 저장·취소와 수정됨 표시를 제공하고 최초 작성 순서를 유지한다. revision으로 오래된 수정·삭제·가리기 요청을 거부한다. 작성자의 수정은 가림 상태를 해제하지 않는다.
- 댓글당 이미지 또는 일반 파일 하나를 첨부할 수 있다. 이미지 5MB·기존 허용 이미지 형식, 일반 파일 10MB·기존 8종과 서버 파일 검증을 재사용한다. 첨부만 있는 댓글은 허용하되 텍스트와 첨부가 모두 비어 있으면 거부한다. 수정 시 교체·제거하며 이미지 미리보기와 일반 파일명·크기·다운로드를 제공한다. 파일은 App Storage에 두고 본문에 Base64를 넣지 않는다.
- URL은 원문 텍스트를 보존하고 표시할 때 안전한 HTTP(S) 링크로 변환한다. HTML·Markdown 편집기나 외부 링크 미리보기는 추가하지 않는다.
- 가린 댓글은 일반 회원에게 `가려진 댓글입니다`로 표시하며 원문·첨부는 댓글 작성자와 관리자만 받는다. 부모 게시글의 열람 권한도 충족해야 한다. 첨부 직접 접근에도 두 권한을 적용한다. 가린 게시글의 댓글 조회·추가 제한은 유지한다.
- DB에는 가림 상태·수정 시각·revision·단일 첨부 JSONB를 추가한다. 첨부 메타데이터는 서버가 저장소에서 확인한다. 최초 개발 전환·정적 검사 결과는 [개발 기록](../history/comments-drag-handle-2026-11-12.md)에 남긴다. 2026-11-12 운영 댓글 네 컬럼·두 CHECK 전환과 [3.0.0 배포](../history/release-3.0.0-2026-11-12.md)를 마쳤다. 이번 전환에는 데이터 초기화 허용을 받았지만 초기화 없이 적용했다. 댓글 편집·가리기·첨부의 실제 회원 동작과 실계정 QA는 계속 보류한다.

### 게시글 수정·삭제·가리기 (2026-11-09)

- 작성자는 본인 게시글을 수정·삭제합니다. 관리자는 타인의 글을 가리거나 다시 표시할 수 있으며 관리자 권한으로 타인의 본문을 수정·삭제하지 않습니다. 관리자가 작성한 본인 글은 작성자 권한을 따릅니다. 작성자는 경조사 대상 동문이 아닌 `authorId`의 실제 등록자입니다.
- 일반 글은 기존 Tiptap JSON 편집기·카테고리·이미지 첨부를 재사용합니다. 경조사는 짧은 정정 입력 → 기존 사실과 공개 자료 해석 → 문안 미리보기 → 작성자 확인 후 반영으로 수정합니다. 경조사 유형·작성자·최초 게시 시각을 바꾸거나 JSON 사실과 본문을 별개로 수정하지 않습니다.
- 경조사 정정에서 입력한 공개 링크는 기존 링크보다 우선해 미리보기와 저장 문안에 표시합니다. 같은 URL은 이번 수집 결과로 갱신하고, 다른 기존 출처와 필드별 근거는 보존합니다. 링크가 없는 정정은 기존 링크를 유지하며 차단된 링크는 표시하지 않습니다.
- 가린 글은 일반 게시판·홈·검색에서 제외하고 작성자와 관리자만 상세와 가린 글 목록에서 관리합니다. 일반 회원의 직접 상세·댓글·해당 글에만 연결된 첨부 접근도 차단합니다. 가린 상태에서는 댓글을 추가하지 않습니다. 작성자의 수정은 가림 상태를 해제하지 않습니다.
- 삭제는 작성자의 확인 후 게시글과 연결 댓글을 제거합니다. Object Storage 파일의 물리 삭제는 포함하지 않습니다. 가리기·다시 표시하기는 본문·댓글을 보존합니다. 서버에서 세션·현재 관리자 여부·작성자·revision을 확인하며 변경 중 충돌은 덮어쓰지 않습니다.
- 기존 미발행 경조사 초안은 작성자 전용으로 유지합니다. 게시된 경조사의 정정은 기존 글에 저장하기 전까지 브라우저의 미리보기로만 유지하며 새 글의 자동저장 초안을 덮어쓰지 않습니다.
- 적용 상태: 게시글 관리 코드와 가림 상태 컬럼은 개발·운영에 반영했습니다. 당시 승인·적용·보존 확인은 [게시글 관리 릴리스 기록](../history/replit-2026-11-09.md#게시글-관리-릴리스-완료-결과)을 따릅니다. 실계정 QA는 계속 보류합니다.

### 공개 홈 검색 대표 주소 (2026-11-09)

- 공개 홈의 검색용 대표 주소는 `https://dgkma.org/`입니다. `/`와 `/about`의 canonical은 로그인 여부와 관계없이 이 주소로 통일합니다. 개발 환경에서 같은 경로를 열어도 공개 대표 주소를 사용합니다.
- `/about/intro`·`/about/executives`·`/about/presidents`·`/about/heritage` 등 하위 페이지는 각자의 경로를 canonical로 사용하며 홈 대표 주소로 합치지 않습니다. 복원한 소개 페이지의 제목·설명을 공통 공개 페이지 정의와 사이트맵에 포함하고 서버 최초 HTML과 클라이언트에서 재사용합니다. 삭제한 `/history`는 계속 제외합니다.
- 공개 페이지 제목·설명은 공통 경로 정의를 서버와 클라이언트가 재사용합니다. `/about/bylaws/regulations`·역대회장·역사관을 포함한 같은 정의에서 사이트맵을 생성하고 `https://dgkma.org/`의 절대 주소만 넣습니다. `/about`은 홈 대표 주소와 중복 등재하지 않으며 회원 전용 경로는 포함하지 않습니다.
- 서버가 처음 반환하는 HTML과 클라이언트의 페이지 전환 후 메타데이터는 같은 주소 생성 기준을 사용합니다. canonical과 함께 쓰는 `og:url`도 같은 주소를 사용하며, `/`의 서버 HTML에서도 canonical이 누락되지 않도록 합니다.

### 경조사 입력과 등록

- 경조사·부고는 상세 필드 입력 폼을 사용하지 않습니다. 사용자는 짧은 텍스트와 필요한 공개 링크를 입력하고, 내부 처리는 JSON을 사용합니다. 사용자에게 JSON 작성이나 DB 필드 입력을 요구하지 않습니다.
- 처리 순서는 `텍스트·링크 → 정적 추출·정규화와 LLM 해석 → 구조화 JSON → 정적 문안 생성·형식 확인 → 미리보기 → 작성자의 게시 명령`입니다. 필요한 정보만 추가 질문하고, 정정도 짧은 텍스트로 받습니다. 자동 게시나 관리자 승인 대기는 추가하지 않습니다.
- 홈페이지 서버에서 OpenAI API를 호출합니다. 필요한 경조사 입력 정보의 전송과 API 사용량 발생을 전제로 채택했습니다. 브라우저에 API 키를 노출하지 않습니다. 실제 호출에는 Replit 서버 Secret `OPENAI_API_KEY`가 필요합니다.
- LLM은 자연어 해석과 구조화 보완을 담당합니다. 날짜·요일·전화번호 표기, 필수 정보 확인, 문안 조합과 권한 판정은 정적 코드가 담당합니다. 정적 코드로 처리되는 정상 경로에 LLM 재작성을 강제하지 않습니다.
- 생성된 JSON도 원문에 근거한 사실만 담습니다. 링크 접근 실패·누락·충돌은 해당 항목만 추가 질문하고, 없는 이름·관계·날짜·회원 유형·연락처·계좌를 만들지 않습니다. 필요한 사실을 덜 입력하게 하는 방향이지 게시에 필요한 사실을 생략하는 방향은 아닙니다.
- 입력 초안의 자동저장·복구·삭제와 게시 후 초기화는 공통 게시글 구조를 사용합니다. 미발행 초안은 작성자만 접근하고, 회원 탈퇴 시 초안 삭제·게시물 작성자 연결 해제 정책을 유지합니다.
- 일반회원 본인·관리자 대리 등록 정책은 유지합니다. 작성자·관리자 권한·관련 동문 표시명은 서버가 정합니다. 대리 등록의 이름 또는 공식 별칭과 학번은 명부에서 한 명과 일치해야 하며 LLM 판단으로 대신하지 않습니다.
- 본인상은 관련 동문과 고인 이름이 일치해야 하며, 연락처는 유가족 연락처를 사용합니다. 입력 원문은 게시 본문과 구분하고 목록·상세·댓글·링크 미리보기 응답에 포함하지 않습니다.

### 공개 경조사 링크 자동 수집

- 저장된 조회 규칙·기존 공개 API·정적 HTML을 우선 사용합니다. HTML 본문·메타데이터·JSON-LD·초기 상태와 연결된 JavaScript의 명시적인 조회 경로를 확인하고, 충분한 정보를 확보하면 브라우저와 OCR을 생략합니다.
- 미지원 사이트도 요청 중에 자동 탐색합니다. 수집 전용 Playwright/Chromium이 실제 Fetch/XHR와 JSON 응답을 관찰하고, 렌더링 본문·iframe·Shadow DOM·펼침·탭·지연 로딩을 읽습니다. 이미지에만 정보가 있으면 제한된 로컬 OCR을 수행합니다. API 발견 실패를 API 부재로 판단하지 않습니다.
- 공개 페이지에 연결되어 있고 인증 없이 해당 페이지의 정보를 읽는 요청임을 확인한 경우에만 직접 재조회합니다. 로그인·CAPTCHA·접근권한을 우회하거나 비공개 경로를 추측하지 않습니다.
- 수집 규칙의 정본은 게시글과 분리된 PostgreSQL `source_collection_rules`의 JSONB입니다. 도메인·페이지 패턴·API 템플릿·메서드·ID 추출·응답 필드 매핑·구조 조건·버전·마지막 성공 시각을 기록합니다. 개별 원문·개인정보·쿠키·인증 토큰과 실행 코드는 저장하지 않습니다.
- 다음 요청은 규칙으로 최신 원본을 다시 조회합니다. 응답 구조나 해당 페이지의 정보가 맞지 않으면 범용 탐색으로 이어지고, 정상 수집한 새 규칙으로 갱신합니다. HTTP 200만으로 성공 처리하지 않습니다.
- 수집 브라우저는 별도 프로세스·일회성 컨텍스트에서 실행하고 앱 Secrets·DB 접속정보·회원 세션을 전달하지 않습니다. 앱 서버가 DB와 공개 요청 중계를 담당하며 리다이렉트·하위 요청에도 공개 주소·DNS 고정·크기·시간·자원 제한을 적용합니다.
- Playwright를 수집 구현의 중심으로 사용하고 Chromium은 그 실행 엔진으로 사용합니다. 별도 Linux namespace·컨테이너 관리 계층은 추가하지 않습니다. Chromium 자체 sandbox와 작업별 프로세스·컨텍스트 분리를 유지합니다.
- 2026-11-09 적용 상태: Replit 개발·운영 코드와 DB에 범용 수집기·규칙 저장을 반영했습니다. 개발 단계에서 지정 공개 링크의 자동 API 발견·규칙 저장·다음 요청의 재사용을 실행했습니다. 다른 사이트와 이미지 전용 자료까지 확인한 것으로 확대하지 않으며 실제 실행 범위는 [수집 적용 이력](../history/replit-2026-11-09.md#개발-수집-적용-결과-2026-11-09)을 따릅니다.
- 수집 결과는 필드별 출처를 가진 공통 JSON으로 정규화합니다. 사용자 정정을 우선하며 누락·충돌만 질문합니다. 기존 회원 권한·본인/관리자 대리 등록·문안 생성·미리보기·작성자 확인 후 게시를 유지합니다.

### 결혼·개원 보완 범위 (2026-11-09)

- 기존 공통 수집기·공개 API 자동 발견·PostgreSQL 규칙 저장소를 재사용합니다. 서버가 보관한 초안 유형을 수집까지 전달하고, 결혼·개원의 필드 매핑과 성공 조건을 부고와 구분합니다. 새 수집기나 경사 전용 DB를 만들지 않습니다.
- 결혼은 동문 혼주와 신랑·신부, 대상 동문과 혼인 당사자의 관계를 구분합니다. 예식 날짜·시각·장소와 확인된 식사·주차·화환 안내를 사용합니다. 링크에 없는 관계·학번·직함을 추정하지 않습니다.
- 부모와 자녀 모두 동문인 경우 스킬의 두 줄 형식대로 두 줄 모두 `본회`로 시작합니다. 자녀도 제공된 이름/공식 별칭과 학번 또는 졸업기수로 명부 한 명을 확인하고, 서버의 회원 연결·회비 상태로 호칭을 정합니다. LLM의 `childMemberType`이나 학번·기수 문구를 그대로 게시하지 않습니다. 부족한 식별 정보만 질문합니다.
- 경사 계좌는 원문에 직접 제공하거나 게시 대상을 특정해 요청한 대상 동문·확인된 동문 자녀의 계좌만 허용합니다. 혼주는 `혼주 성명 은행명 계좌번호`, 동문 당사자는 `신랑/신부 성명 은행명 계좌번호` 순서로 표시합니다. 링크의 다른 가족 계좌를 자동으로 옮기지 않으며 연락처도 직접 제공하거나 특정하여 요청한 범위만 표시합니다.
- 개원은 대상 동문, 한의원명, 개원 날짜와 제공된 시각, 장소·주소, 확인된 안내로 홈페이지 문안을 만듭니다. 결혼 관계·신랑·신부·혼주·청첩장 표현을 넣지 않습니다. 선택 정보가 없으면 항목명·자리표시자·빈 절을 생략합니다.
- 기존 짧은 입력·JSON·추가 질문·미리보기·작성자 확인 후 게시와 본인/관리자 대리 등록 정책을 유지합니다. 상세 필드 폼, 카카오톡·문자 생성·발송은 이 기능의 범위에 넣지 않습니다.
- 적용 상태: Replit 개발·운영 코드에 유형별 수집·규칙 계약, 경사 정규화와 홈페이지 문안을 반영했습니다. 실제 경사 링크 수집·규칙 저장/재사용·게시 흐름을 실행한 기록은 없으며, 적용 근거와 정적 검사 범위는 [개발 운영 기록](../history/replit-2026-11-09.md#결혼개원-보완-2026-11-09-개발-코드-적용)에 둡니다.

[관리자 화면](../../client/src/features/admin/admin.tsx)은 가입 심사·명부 동기화·게시글 관리 연결과 기초 통계를 제공합니다. 관리자 납부 관리 화면은 미구현입니다. [역대회장](../../client/src/features/about/presidents.tsx)·[역사관](../../client/src/features/about/heritage.tsx)의 개발 사본은 공통 JSON을 읽어 표시하며, 관리자 콘텐츠 편집·업로드는 미구현입니다. 회원 전용 `posts`의 접근 정책을 바꿔 공개 역사 자료를 제공하지 않습니다.

## 6. 기존 기능의 보완과 정리

- **코드·문서 유지보수:** 같은 의미의 표시·입력 계약·스타일은 재사용하고 기능별 책임을 분리합니다. 실제 사용처와 구체적인 호환성 보존 이유를 확인한 뒤 미사용 코드·의존성·설명을 정리합니다. 회원 권한·보안 경계·저장 계약·트랜잭션·처리 순서와 실제 사용 중인 주입·동적 로딩 계약은 유지합니다. 현재 구조와 보존 근거는 [구조 기준](../architecture/project-structure.md), 완료된 작업별 범위·검사 결과는 [이력 색인](../history/README.md)에 둡니다.
- **유지 대상:** 실제 소비자가 있는 shared 호환 경로와 단일 저장 receiver, 동적·peer 의존성, 작성기 원본·DB 전환·릴리스 자료를 보존합니다. `artifacts/mockup-sandbox`는 목업 0개여도 실제 사용 중인 [Replit 설계 미리보기 서비스](../../replit.md#설계-미리보기-서비스)이므로 유지합니다.
- **회원·가입·게시판·경조사:** 현재 기반 위에서 빠진 입력·처리·화면을 구체적인 개발 단위로 추가합니다. 기능 요청에는 사용자가 할 일과 저장·표시할 결과를 명시합니다.
- **레거시 부고:** 통합 코드에서 상세·API·전용 저장 경로를 제거했고 개발·운영 DB의 구 테이블도 삭제했습니다. 이관과 옛 주소 호환 계층은 만들지 않습니다.
- **명부 관리:** 기존 1회 이관 이력이 있으며 관리 원본은 Google Sheets입니다. PostgreSQL 단독 원본으로 전환하려면 최종 동기화·대조와 사용자 선언이 필요합니다. 원본 전환은 기능 구현과 별도 운영 결정입니다.
- **DB 복구·백업:** 2026-11-12 결정으로 개발·운영 DB 모두 Replit의 7일 복구를 기준으로 삼고 별도 백업을 기본으로 만들지 않습니다. 명시적 요청·승인에 따른 예외와 실제 설정의 확인 상태는 [DB 운영 런북](../runbooks/database-operations.md#db-복구백업-기본-정책)을 따릅니다.
- **역사 자료 이관:** 네이버 밴드·다음 카페에서 사용할 사진·공지와 출처·공개 범위를 정하고, 승인된 자료를 실제 홈페이지 콘텐츠로 연결합니다.

## 7. 다음 개발 목표

아래 순서는 2026-11-10 코드 대조에 따른 **권고안**입니다. 확정된 제품 정책과 구분하며 실제 착수 기능·범위는 사용자 결정에 따릅니다. 기존 회원·게시판·경조사 기반을 재사용하고, 완료한 전면 코드 정리를 후속 개발의 선행 과제로 반복하지 않습니다.

| 상태·권고 순위 | 개발 단위 | 우선하는 이유와 첫 범위 |
|---|---|---|
| 보류 | 공개 규정 기반 회비·권리회원과 관리자 납부 관리 | 사용자 요청으로 Sheets 구조 확인 후 재개 결정. 확정된 목표 정책과 남은 구현 범위는 유지하며 DB 구조·등급 계산·관리 화면 개발은 착수하지 않음 |
| 1 | 역사관 자료 보완 | 개발 사본에 연결한 명단·연혁·임원·기부 기록을 바탕으로, 사용자 정리가 끝난 수상자·사진을 같은 계약에 추가. 관리자 편집·업로드는 필요 시 별도 범위 확정 |
| 2 | 회원 메시지 | 기존 공지·경조사를 실제 회원 안내로 연결. 발송 종류·대상·동의·승인 절차와 공급자를 정한 뒤 수신 거부·발송 이력까지 한 흐름으로 구현 |
| 3 | 실제 회비·서비스 결제 | 회비 관리 재개와 납부·정정 기준 확정 후 결제박사를 연결. 승인 콜백·중복 방지·취소·환불·영수증을 함께 구현 |
| 4 | 화환·근조기 주문 | 경조사와 회원 상태를 재사용해 접수·관리자 처리·진행 상태를 제공. 공급자·비용·결제/후불 정책을 정한 뒤 연동. 후불을 선택하면 결제 연동과 독립적으로 착수 가능 |
| 5 | 장학사업 관리 | 신청 자격·선발·지급·공시 정책을 정한 뒤 구현. 현재는 소개 외 업무 흐름이 정의되지 않아 앞 기능보다 후순위 |

회비·권리회원 관리는 Sheets 구조 확인 후 사용자의 재개 결정에 따릅니다. **관리자 기초 통계**는 운영 코드에, **역사관 6개 메뉴**도 운영 코드에 반영했습니다. 수상자·사진 자료 반영은 사용자 정리 후 재개합니다. 명부 구조와 회비 판정은 유지합니다.

## 8. 결정이 필요한 사항

게시글 통합의 저장 방식, 회원 전용 접근, 카테고리·유형, 텍스트 입력, 서버 OpenAI API 사용, 작성자 확인·게시, 기존 데이터·상세 주소 폐기와 게시문 회원 호칭은 3절에서 확정했습니다. 아래 항목은 별도 후속 기능의 결정 사항입니다.
- **게시글 관리:** 작성자 수정·삭제와 관리자 가리기·다시 표시하기는 확정했습니다. 신고·처리 이력 등 추가 운영 기능은 별도 범위로 정합니다.
- **회비·권리회원 운영:** 목표 정책은 공개 규정으로 확정했습니다. 연도별 직책·명예회원의 관리 원본과 승인 담당, 시행일·연중 입회/탈퇴 시 적용 세부, 기존 납부·확정 권리상태를 가져올 근거와 미확인 자료 처리 방식을 정합니다. 명부의 자유 텍스트 직책이나 납부 생성일을 새로운 판정 자료로 임의 해석하지 않습니다.
- **통계·리포팅:** 기초 통계의 지표·기간·관리자 접근은 3절의 범위로 구현합니다. 파일 내보내기와 추가 리포트의 지표·형식은 후속 결정입니다.
- **메시지 공급자:** 알리고를 포함해 비교하며 아직 확정하지 않았습니다. 발송 종류·대상·템플릿·동의와 운영 요구사항을 먼저 정합니다.
- **결제:** 결제박사 사용 예정입니다. 수수료가 없다는 사용자 확인 내용이 있으며, 실제 연동 착수 시 API·수수료·정산·환불·영수증·보안 조건을 공식 자료와 계약 조건으로 확인합니다.
- **주문:** 화환·근조기 공급자, 결제 또는 후불 방식과 관리자 처리 범위를 정합니다.
- **역사·장학:** 공개할 자료와 출처·사용 권한, 장학사업 운영 정책과 개인정보 처리 범위를 정합니다.
- **명부 원본:** 사용자 선언과 최종 동기화 절차를 거쳐 전환합니다. 경조사 통합 결정으로 명부 원본 정책을 바꾸지 않습니다.

## 9. 변경되거나 폐기된 방향

| 과거 방향 | 현재 결정 | 이유 |
|---|---|---|
| Supabase 클라이언트 로그인 | 방향 변경: Express 세션 기반 카카오 REST OAuth | 현재 서버 세션·탈퇴·프록시 구조와 일치 |
| Google SSO 관리자 인증 | 방향 변경: 로그인 회원의 서버 `isAdmin` 권한 | 관리자 API 정책을 하나로 통일 |
| 카카오 JavaScript SDK·카카오싱크 | 방향 변경: 서버 REST OAuth authorization-code 흐름 | 환경 분리, Secret 보호와 서버 처리 보장 |
| CI로 중복 가입 방지 | 방향 변경: 카카오 회원번호·이메일·정규화 전화번호·명부 단일 연결 | 현재 가입 경로는 해당 식별자·명부 연결의 충돌을 검사하며 CI를 요청·저장하지 않음 |
| 개발·운영 공용 카카오 앱과 일반 Secret | 방향 변경: 환경별 앱과 10개 서버 Secret | callback, 연결 해제 키와 관리자 복구 allowlist를 환경별로 분리. 환경별 설정은 `replit.md`에서 관리 |
| 게시글·댓글 읽기 공개 API | 방향 변경: 모든 게시글·댓글·검색·첨부를 회원 전용으로 통일 | 일반 게시글과 경조사의 접근 기준 통일. 코드 적용됨 |
| 경조사 전용 테이블과 레거시 부고 테이블 유지 | 방향 변경: `posts`·`categories`와 JSON으로 통합, 두 테이블 삭제 | 사용자 결정. 별도 상세 테이블이나 데이터 이관 없이 공통 게시글로 관리 |
| 상세 필드를 직접 채우는 경조사 폼 | 방향 변경: 최소 텍스트·링크와 정적 코드·OpenAI API로 JSON과 문안 생성 | 필요한 항목만 추가 질문하고 작성자가 미리보기 확인 후 게시 |
| 부고·결혼·개원·기타 네 유형의 전용 경조사 목록 | 방향 변경: `부고`·`경사` 카테고리, 경사 JSON 유형은 결혼·개원만 사용 | 기타 유형 제거, 기존 게시판의 분류와 표시 재사용 |
| 경사 문안의 `정회원` 입력 표현 유지 | 방향 변경: 부고·경사 모두 `동문·회원·권리회원` 호칭 사용 | 사용자 결정에 따라 게시문 회원 호칭 통일 |
| Google Sheets 즉시 폐기 | 방향 변경: Sheets 관리 원본과 PostgreSQL 런타임 복제본의 전환기 운영 | 가입 전 명부 관리와 데이터 대조가 아직 필요 |
| `/events` 전용 게시물과 `/o/:id` 레거시 상세 호환 | 방향 변경: 공통 게시판 사용, 기존 데이터·상세 주소 폐기 | 출시 전이므로 마이그레이션·옛 상세 주소 호환 불필요 |
| URL 전체를 제한 없이 수집하거나 AI가 빈 내용을 추론 | 방향 변경: 문자 우선 파싱, 제한된 공개 링크 수집과 실패 fallback | SSRF·과대 응답·오정보 위험 방지 |
| 직책과 무관한 당해년도 연회비 5만 원 판정 | 목표 변경: 공개 규정의 직책별 월납 누계 또는 연납 기준 | 2026-11-10 사용자 결정. 현재 서버는 기존 5만 원 판정이며 후속 구현과 DB 작업은 별도 |
| 알리고·카카오페이를 확정 공급자로 선기재 | 방향 변경: 메시지는 요구사항 확정 후 비교하고 결제는 결제박사 사용 예정 | 결제 세부 연동 조건은 실제 결제 개발 착수 시 확인 |
