# 다음카페 마이그레이션 계획

다음카페 백업 170건을 원 상위 메뉴·하위 게시판별로 dgkmaWeb에 이관하기 위한 계획이다. 대상별 목적지·변환·도구 보완·적용 순서를 정하며 밴드 이관은 별도 계획으로 다룬다. 공통 저장·접근 기준은 [이관 기준](community-archive-migration-proposal.md)을 따른다. 과거 테스트 결과와 검토 경위는 [개발 이관 기록](../history/member-albums-2026-11-14.md)에 둔다.

## 1. 백업 구조

원 카페의 상위 메뉴 `게시판` 아래 6개 게시판에 83건, `동창회 소개` 아래 5개 게시판에 35건이 있다. 동창회 앨범 52건·Q&A 0건까지 하위 게시판 총 13개, 원본 170건을 대상으로 한다. 댓글·한 줄 수다는 각각 0건이므로 별도 이관 절차를 만들지 않는다.

기존 JSON·SQLite 색인은 하위 `boardId` 중심의 평면 목록이므로 최종 이관 대응표에는 `원 상위 메뉴 → 원 하위 게시판 → 원본 ID → 대상 메뉴/카테고리 → 공개 범위 → 처리 상태`를 함께 명시한다. 원본 백업의 구조·파일은 변경하지 않는다.

| 위치 | 저장 내용 | 이관 시 역할 |
|---|---|---|
| `local-backups/community/daum-dkkmob/index.json` | 게시판별 글 목록, 원본 ID·목록 날짜·원문 주소·저장 파일·해시 | 원본 170건의 대상 목록 |
| `daum-dkkmob/posts/<게시판>-<글번호>.json` | 제목·작성자·목록 날짜·본문 HTML/텍스트·전체 페이지 HTML·댓글·파일 참조 | 본문과 원작성 정보의 근거 |
| `daum-dkkmob/assets/` | 내려받은 이미지·원 첨부 | 실제 업로드할 파일의 원본 |
| `daum-dkkmob/permissions.json`, `audit.json` | 게시판별 열람 범위, 확보·누락과 당시 검사 결과 | 원본 접근 범위와 누락 기록. 이관 후 접근 정책과 구분 |
| `archive.sqlite3` | 원본 복합 ID·해시·변환 선택·대상 ID·적용 상태 | 중복 구분과 원본/대상 추적. Replit에 올리지 않음 |
| `conversions/`, `conversions/selected-overrides.json` | HWP 원본·HWPX·변환 검사·사용자 지정본 | 선택된 변환 파일 재사용 |
| `migration/`, `migration-preview.json` | 변환 본문·앨범 목록·대응표·적용 영수증 | 최종 목적지·입력 해시와 대조해 일치하는 변환물 재사용 |

표의 두 번째 행부터 경로는 `local-backups/community/` 기준이다. `archive.sqlite3`의 다섯 테이블은 다음과 같다.

- `sources`: 원천과 체크포인트. 다음카페 키는 `source='daum-cafe'`, `container_id='1Tcxq'`다.
- `source_items`: `(source, container_id, kind, source_id)`로 원문을 식별한다. 다음카페의 `source_id`는 `게시판ID:글번호`다. 게시판마다 글번호가 겹치므로 글번호만으로 합치지 않는다.
- `assets`: 원본 파일 주소·로컬 파일·해시·크기·확보 상태를 기록한다.
- `conversions`: 원본 파일 해시와 변환 형식별 결과·검사·사용자 선택을 기록한다.
- `migration_items`: 원본과 대상 환경별 분류·최종 본문·첨부·적용 ID·해시를 기록한다.

작성자·작성 시각은 원문 JSON과 저장된 `pageHtml`에서 추출한다. `author`가 없는 자료도 본문의 명확한 작성자 표시를 사용하고 추정으로 채우지 않는다. 분 단위 시각이 있으면 `listDate`의 날짜만 사용하는 대신 한국 시간으로 해석하며 백업일·이관일로 바꾸지 않는다. 앨범의 `date`는 카페 게시일로 보존하고 행사일로 추정하지 않는다.

원 첨부 10개는 HWP 9개와 HWP 2개가 든 ZIP 1개다. 선택된 HWPX 11개를 이관 후보로 사용하고 원 첨부 수와 변환 파일 수를 구분한다.

원 첨부의 표시 파일명 1개는 확장자까지 온전히 남아 있지 않다. 표시 이름만으로 파일 형식을 판정하지 않고 저장된 MIME·파일 내용 검사·해시와 변환 기록을 함께 사용한다. 실제 업로드 파일에는 선택한 HWPX의 유효한 파일명과 기존 검증 규칙을 적용한다.

## 3. 이관 전 보완

1. **적용 도구의 대상 환경 선택.** 개발 workspace·`heliumdb`·`heritage/development`에 고정된 도구를 운영에서도 사용하려면 명시적인 환경 선택·실제 DB 확인·환경별 저장 경로·영수증을 지원한다. 개발 제한을 삭제하거나 개발 Secret을 바꿔 우회하지 않는다. 기존 영수증은 보존하고 실행별 기록을 분리한다.
2. **분류·변환의 재생성.** `prepare-post-migration.py`의 `classified-not-applied` 선택·86건 고정 검사를 확정된 원본 ID 목록과 입력 해시 기준으로 바꾼다. 원본 ID·대상 ID·내용 해시가 같은 변환물은 재사용하고 달라진 부분만 준비한다. 적용 상태만으로 변환 대상을 결정하지 않는다.
3. **게시판 전체 목록 탐색.** `/api/posts`의 기본 50건 반환과 다음 페이지가 없는 목록 화면을 보완한다. 페이지 단위 이어보기와 작성일이 같은 글의 안정적인 정렬을 제공해 이관 글 전체를 탐색할 수 있게 한다.
4. **사진첩 병합.** 원격 카탈로그 전체의 바이트 일치만 비교하는 도구를 앨범 ID별 기존 자료·추가분·충돌을 대조하도록 보완한다. 기존 앨범을 통째로 덮어쓰지 않는다. 46·43·50장인 앨범 3개도 분할하지 않는다.
5. **첨부의 외부 이미지 참조.** `dbpl-33-1.hwpx`의 외부 PCX 참조 5개가 실제 그림 누락인지 확인하고 처리 방식을 정한다. 글자 서식 차이 허용을 이미지 손실 허용으로 확대하지 않는다. 확인은 해당 파일에 한정하며, `dbpl-35.hwpx`는 선택된 사용자 제공 한컴 변환본을 유지한다.

## 4. 이관 절차

### 준비

- 다음카페만 선택한 기존 로컬 SQLite·최종 본문·카탈로그·파일을 입력으로 삼는다. BAND 행과 수집 도구는 포함하지 않는다.
- 먼저 2절의 원 상위 메뉴·하위 게시판별 목적지를 확정하고 목적지의 현행 공개 범위를 적용한다. `dbpm:1`은 제17대 역대임원 자료 후보에 포함한다. 과거 테스트의 분류와 반영 대상을 그대로 사용하지 않는다.
- 회원 게시판으로 정한 자료만 기존 `posts.content` Tiptap JSONB와 카테고리 이름으로 반영한다. 대상 환경의 카테고리 ID는 그 환경에서 찾는다. `author_id=NULL`을 유지하며 원 상위 메뉴·하위 게시판·원작성자·작성일·원문 링크는 본문과 로컬 대응표에 보존한다. `event_data`·`source_text`는 경조사가 아닌 자료에 사용하지 않는다.
- 공개 소개·역사 자료는 목적지별 자료 계약과 현재 표시 항목에 맞춰 준비한다. 회장 인사말·과거 회칙 자료 연결 등 필요한 표시 보완은 별도 확정 후 구현한다. source 1건을 연혁 여러 사건으로 나누거나 기존 항목에 병합하는 경우 원본 수와 대상 항목 수를 따로 기록한다.
- 확보한 이미지는 목적지별 기존 저장 계약으로 반영한다. 게시판·사진첩은 인증된 비공개 저장소 경로, 공개 소개·역사 자료는 해당 자료 계약의 공개 자산 경로를 사용한다. 원본 외부 이미지 URL·base64를 저장하지 않는다. 목적지의 파일 검증·접근 권한을 유지한다. 원문에서 없는 이미지 6개의 누락 표시는 유지하고 원문 대체 그림은 인물 사진으로 등록하지 않는다.
- 원본의 두 단계 분류는 우선 로컬 이관 대응표에 보존한다. 새 카테고리 행·자료 표시 보완과 DB 테이블·컬럼 변경을 구분하며, 최종 분류에 구조 변경이 필요하면 변경안을 먼저 설명한다.

### 대상 환경과 변경 미리보기

- 실제 적용 지시에서 개발 또는 운영을 명시한다. 대상 환경의 기존 자료와 로컬 대응표를 먼저 대조해 동일 자료를 다시 삽입하지 않는다. 개발 ID·완료 상태를 운영에 그대로 복사하지 않는다.
- 최종 후보의 앱 문서 스키마·첨부·카탈로그 검사를 필요한 범위로 수행한다. 대상 DB·Storage를 읽어 기존 자료와 비교하고 추가·동일·충돌·보류 건수를 나눈다. 재사용 결과는 실제 대상 확인으로 판단한다.
- 승인된 범위의 자료만 선택하고, 테스트 본문과 달라진 대상 행을 덮어쓰거나 기존 게시글을 초기화하지 않는다. 원본 백업과 과거 테스트 기록은 보존한다.

### 적용과 기록

- 게시판으로 이관할 자료의 첨부를 저장·대조한 뒤 게시글을 트랜잭션으로 반영한다. 같은 원문 링크·대상 ID·내용 해시를 대조해 중복을 막고 작성 시각·분류·게시/가림 상태를 명시한다. Storage 파일 저장과 PostgreSQL 트랜잭션은 하나의 원자적 작업이 아니므로 실패 시 저장 파일·DB 반영 상태를 분리해 남긴다. 자동 삭제·원복은 수행하지 않는다.
- 앨범은 사진 파일을 먼저 저장·대조하고 최종 카탈로그를 마지막에 반영한다. `posts`의 40개 이미지 제한을 적용하거나 앨범을 게시글로 바꾸지 않는다.
- 공개 임원 자료는 기존 소스·공개 사진을 대조해 코드 릴리스로 반영한다. 사진첩 회원 전용 서버 코드의 배포와 카탈로그 적용 시점을 맞춘다. 데이터 쓰기 성공을 코드 배포·런타임 활성화 성공으로 대신하지 않는다.
- 적용 후 새 DB 연결에서 대상 글의 건수·내용 해시·원작성 시각·첨부 참조를 확인하고, 저장된 파일·앨범 목록을 대조한다. 원본 ID·환경·대상 ID·해시·결과는 로컬 SQLite와 새 실행 기록에 남긴다.
- 결과는 다음카페 전체 170건을 분모로 원 상위 메뉴·하위 게시판별 대상·적용·재사용·보류·실패를 보고한다. 대상별 합계는 보조 집계로 둔다. 본문 반영과 첨부 보류, 원본 건수와 변환된 대상 항목 수도 분리하며 밴드 상태와 합산하지 않는다.

## 5. 결정할 사항

- 원 상위 메뉴·하위 게시판별 목적지와 ‘학술’ 분류 추가 여부.
- 과거 회장 인사말·모교 연혁·과거 회칙의 연결 위치와 표시 방식.
- `dbpm:1`의 제17대 임원 자료 병합 범위.
- 외부 PCX 참조가 있는 첨부의 확인 결과에 따른 처리 방식.
- 실제 적용 환경·대상 범위·시점.

분류가 확정되면 자료 표시·목록 탐색·이관 도구를 보완하고 적용 미리보기를 준비한다. 공개 범위는 목적지의 현행 정책을 적용하며 원본 등급을 이유로 다시 결정하지 않는다.
