# 다음카페 마이그레이션 계획

다음카페 백업 170건을 원 상위 메뉴·하위 게시판별로 dgkmaWeb에 이관하기 위한 계획이다. 대상별 목적지·변환·도구 보완·적용 순서를 정하며 밴드 이관은 별도 계획으로 다룬다. 공통 저장·접근 기준은 [이관 기준](community-archive-migration-proposal.md)을 따른다. 과거 테스트 결과와 검토 경위는 [개발 이관 기록](../history/member-albums-2026-11-14.md)에 둔다.

## 1. 백업 구조

원 카페의 상위 메뉴 `게시판` 아래 6개 게시판에 83건, `동창회 소개` 아래 5개 게시판에 35건이 있다. 동창회 앨범 52건·Q&A 0건까지 하위 게시판 총 13개, 원본 170건을 대상으로 한다. 댓글·한 줄 수다는 각각 0건이므로 별도 이관 절차를 만들지 않는다.

기존 JSON·SQLite 색인은 하위 `boardId` 중심의 평면 목록이므로 최종 이관 대응표에는 `원 상위 메뉴 → 원 하위 게시판 → 원본 ID → 대상 메뉴/카테고리 → 공개 범위 → 처리 상태`를 함께 명시한다. 원본 백업의 구조·파일은 변경하지 않는다.

| 위치 | 저장 내용 | 이관 시 역할 |
|---|---|---|
| `local-backups/community/daum-dkkmob/index.json` | 게시판별 글 목록, 원본 ID·목록 날짜·원문 주소·저장 파일·해시 | 원본 170건의 대상 목록 |
| `daum-dkkmob/posts/<게시판>-<글번호>.json` | 제목·작성자·목록 날짜·본문 HTML/텍스트·전체 페이지 HTML·댓글·파일 참조 | 본문과 원작성 정보의 근거 |
| `daum-dkkmob/assets/` | 내려받은 이미지·원 첨부 | 실제 업로드할 파일의 원본 |
| `daum-dkkmob/permissions.json`, `audit.json` | 게시판별 열람 범위, 확보·누락과 당시 검사 결과 | 원본 접근 범위와 누락 기록. 이관 후 접근 정책과 구분 |
| `archive.sqlite3` | 원본 복합 ID·해시·변환 선택·대상 ID·적용 상태 | 중복 구분과 원본/대상 추적. Replit에 올리지 않음 |
| `conversions/`, `conversions/selected-overrides.json` | HWP 원본·HWPX·변환 검사·사용자 지정본 | 선택된 변환 파일 재사용 |
| `migration/`, `migration-preview.json` | 변환 본문·앨범 목록·대응표·적용 영수증 | 최종 목적지·입력 해시와 대조해 일치하는 변환물 재사용 |

표의 두 번째 행부터 경로는 `local-backups/community/` 기준이다. `archive.sqlite3`의 다섯 테이블은 다음과 같다.

- `sources`: 원천과 체크포인트. 다음카페 키는 `source='daum-cafe'`, `container_id='1Tcxq'`다.
- `source_items`: `(source, container_id, kind, source_id)`로 원문을 식별한다. 다음카페의 `source_id`는 `게시판ID:글번호`다. 게시판마다 글번호가 겹치므로 글번호만으로 합치지 않는다.
- `assets`: 원본 파일 주소·로컬 파일·해시·크기·확보 상태를 기록한다.
- `conversions`: 원본 파일 해시와 변환 형식별 결과·검사·사용자 선택을 기록한다.
- `migration_items`: 원본과 대상 환경별 분류·최종 본문·첨부·적용 ID·해시를 기록한다.

작성자·작성 시각은 원문 JSON과 저장된 `pageHtml`에서 추출한다. `author`가 없는 자료도 본문의 명확한 작성자 표시를 사용하고 추정으로 채우지 않는다. 분 단위 시각이 있으면 `listDate`의 날짜만 사용하는 대신 한국 시간으로 해석하며 백업일·이관일로 바꾸지 않는다. 앨범의 `date`는 카페 게시일로 보존하고 행사일로 추정하지 않는다.

원 첨부 10개는 HWP 9개와 HWP 2개가 든 ZIP 1개다. 선택된 HWPX 11개를 이관 후보로 사용하고 원 첨부 수와 변환 파일 수를 구분한다.

원 첨부의 표시 파일명 1개는 확장자까지 온전히 남아 있지 않다. 표시 이름만으로 파일 형식을 판정하지 않고 저장된 MIME·파일 내용 검사·해시와 변환 기록을 함께 사용한다. 실제 업로드 파일에는 선택한 HWPX의 유효한 파일명과 기존 검증 규칙을 적용한다.

동창회 앨범 `eir` 52건은 회원 전용 역사관 사진첩으로 이관한다. Q&A `eis`는 0건이다. 두 항목의 원 상위 메뉴는 미확인이므로 위 두 상위 메뉴에 임의로 포함하지 않는다. 전체 원본은 **83 + 35 + 52 = 170건**이다.

모교 연혁은 [공식 출처 보강안](college-history-supplement.md)을 사용한다. 학장 취임·연임과 기관 선정·교육 인증은 제외하며, 개인 수석 합격은 연혁 대신 수상자 항목에 반영한다.

## 3. 이관 전 보완

먼저 [동문 사전 등록·게시글 메타데이터 DB 변경안](pre-migration-database-design.md)을 확정한다. users의 미가입 동문 관리는 별도 전환 단계로 유지하며, posts 작성자·원작성일·출처의 개발 적용 계약은 [스키마 기준서](../reference/database-schema.md#게시글-이관-출처-저장)를 따른다.

1. **일회성 이관 실행 준비.** 다음카페는 확정된 전체 자료를 한 번에 이관한다. 반복 증분·재동기화·추가/동일/충돌 병합 기능은 도입하지 않는다. 백업은 개발로만 이관하고 운영은 개발 완료본을 별도 이전한다. 명시적인 리셋 실행에서 posts 전체 행과 종속 댓글을 정리하고 DB·Storage 경로와 반영 결과를 확인한다. 개발 전용 도구를 운영에 무단 전용하지 않는다.
2. **분류·변환의 재생성.** `migration-preview.py`와 `prepare-post-migration.py`는 원본 index의 ID·해시와 2절의 목적지를 기준으로 준비한다. 과거 적용 여부는 참고 이력이며 후보 선택 조건이 아니다. 고정된 총 글 수 대신 원본별 대응·중복·누락을 대조한다. 원본 ID·대상 ID·내용 해시가 같은 변환물은 재사용하고 달라진 부분만 준비한다. 적용 상태만으로 변환 대상을 결정하지 않는다.
3. **게시판 전체 목록 탐색.** `/api/posts`의 기본 50건 반환과 다음 페이지가 없는 목록 화면을 보완한다. 페이지 단위 이어보기와 작성일이 같은 글의 안정적인 정렬을 제공해 이관 글 전체를 탐색할 수 있게 한다.
4. **사진첩 일회성 반영.** 확정된 앨범 52건을 한 번에 반영하며 증분 병합 기능은 만들지 않는다. 기존 테스트 사진첩은 실제 이관 시 초기화 후 전체 반영한다. Storage 파일의 물리 삭제 범위는 DB 행 리셋과 구분한다. 46·43·50장인 앨범 3개도 분할하지 않는다.
5. **변환 첨부.** 선택된 HWPX를 내부 내용 대조 없이 첨부한다. 외부 PCX 참조는 원래 파일의 특성으로 기록하며 누락을 이유로 보류하지 않는다. `dbpl-35.hwpx`는 사용자 제공 한컴 변환본을 유지한다. 기존 업로드 형식·용량·보안 검사는 유지한다.

## 4. 이관 절차

### 준비

- 다음카페만 선택한 기존 로컬 SQLite·최종 본문·카탈로그·파일을 입력으로 삼는다. BAND 행과 수집 도구는 포함하지 않는다.
- 2절의 확정 목적지와 현행 공개 범위를 적용한다. `dbpm:1`은 제17대 역대임원 자료에 대조·병합한다. 과거 테스트의 분류와 반영 대상을 그대로 사용하지 않는다.
- 회원 게시판으로 정한 자료만 기존 `posts.content` Tiptap JSONB와 카테고리 이름으로 반영한다. 대상 환경의 카테고리 ID는 그 환경에서 찾는다. `author_id=NULL`을 유지하며 원 상위 메뉴·하위 게시판·원작성자 이름·원작성일·원문 링크·원본 ID는 본문이 아닌 posts 메타데이터와 로컬 대응표에 보존한다. 작성자·날짜·출처 UI는 이 DB 값을 사용한다. 메타데이터 필드와 날짜 저장 계약은 [스키마 기준서](../reference/database-schema.md#게시글-이관-출처-저장)를 따른다. `event_data`·`source_text`는 경조사가 아닌 자료에 사용하지 않는다.
- 공개 소개·역사 자료는 목적지별 자료 계약과 현재 표시 항목에 맞춰 준비한다. 회장 인사말·과거 회칙 자료 연결 등 필요한 표시 보완을 구현한다. source 1건을 연혁 여러 사건으로 나누거나 기존 항목에 병합하는 경우 원본 수와 대상 항목 수를 따로 기록한다.
- 확보한 이미지는 목적지별 기존 저장 계약으로 반영한다. 게시판·사진첩은 인증된 비공개 저장소 경로, 공개 소개·역사 자료는 해당 자료 계약의 공개 자산 경로를 사용한다. 원본 외부 이미지 URL·base64를 저장하지 않는다. 목적지의 파일 검증·접근 권한을 유지한다. 원문에서 없는 이미지 6개의 누락 표시는 유지하고 원문 대체 그림은 인물 사진으로 등록하지 않는다.
- 원본의 두 단계 분류는 우선 로컬 이관 대응표에 보존한다. 새 카테고리 행·자료 표시 보완과 DB 테이블·컬럼 변경을 구분하며, 최종 분류에 구조 변경이 필요하면 변경안을 먼저 설명한다.

### 대상 환경과 변경 미리보기

- 백업에서의 테스트 이관은 개발 DB·개발 파일 저장소만 사용한다. 운영 이전을 승인한 릴리스에서는 개발에서 완성한 콘텐츠 묶음을 별도 도구로 운영 DB·운영 파일 저장소에 이전한다. 운영에서 백업을 재변환하지 않는다. 실제 실행 시 해당 환경을 확인한다. 대상 환경을 확인하고 posts 전체 행과 종속 댓글을 리셋한 뒤 확정된 전체 후보를 일회성으로 반영한다. 운영 이전은 개발 완료본의 게시글 ID·상태를 보존하며, 로컬 백업의 과거 테스트 적용 이력으로 운영 적용 결과를 대신하지 않는다.
- 최종 후보의 앱 문서 스키마·첨부·카탈로그 검사를 필요한 범위로 수행한다. 대상 DB·Storage의 posts 전체 리셋 대상과 최종 후보·제외·오류 건수를 확인한다. 증분 비교·병합 기능을 추가하지 않는다.
- 승인된 범위의 자료만 선택하고, 실제 이관 직전에 posts 전체 행과 종속 댓글을 리셋한다. 이 리셋을 회원·명부·회비·카테고리·로컬 백업 삭제로 확대하지 않는다. 원본 백업과 과거 테스트 기록은 보존한다.

### 적용과 기록

- 게시판으로 이관할 자료의 첨부를 저장·대조한 뒤 게시글을 트랜잭션으로 반영한다. 같은 원문 링크·대상 ID·내용 해시를 대조해 중복을 막고 작성 시각·분류·게시/가림 상태를 명시한다. Storage 파일 저장과 PostgreSQL 트랜잭션은 하나의 원자적 작업이 아니므로 실패 시 저장 파일·DB 반영 상태를 분리해 남긴다. 자동 삭제·원복은 수행하지 않는다.
- 앨범은 사진 파일을 먼저 저장·대조하고 최종 카탈로그를 마지막에 반영한다. `posts`의 40개 이미지 제한을 적용하거나 앨범을 게시글로 바꾸지 않는다.
- 공개 임원 자료는 기존 소스·공개 사진을 대조해 코드 릴리스로 반영한다. 사진첩 회원 전용 서버 코드의 배포와 카탈로그 적용 시점을 맞춘다. 데이터 쓰기 성공을 코드 배포·런타임 활성화 성공으로 대신하지 않는다.
- 적용 후 새 DB 연결에서 대상 글의 건수·내용 해시·원작성 시각·첨부 참조를 확인하고, 저장된 파일·앨범 목록을 대조한다. 원본 ID·환경·대상 ID·해시·결과는 로컬 SQLite와 새 실행 기록에 남긴다.
- 결과는 다음카페 전체 170건을 분모로 원 상위 메뉴·하위 게시판별 대상·적용·재사용·보류·실패를 보고한다. 대상별 합계는 보조 집계로 둔다. 본문 반영과 첨부 보류, 원본 건수와 변환된 대상 항목 수도 분리하며 밴드 상태와 합산하지 않는다.

## 5. 실행 준비

확정한 분류에 맞춰 자료 표시·목록 탐색·이관 도구를 보완하고 적용 미리보기를 준비한다. 선택된 HWPX는 내부 내용 대조를 추가하지 않는다. 외부 PCX 참조 누락은 원본 특성으로 기록하고 보류하지 않는다. 업로드 형식·용량·보안 조건 위반은 별도로 처리한다.

실제 적용 환경·대상 범위·시점은 별도 실행 지시에서 정한다. 공개 범위는 목적지의 현행 정책을 적용하며 원본 등급을 이유로 다시 결정하지 않는다.

## 최종 자료 생성 계약

- 결과는 로컬 `local-backups/community/migration/final/`에 둔다. 기존 `migration-preview.json`, 개발 테스트 payload·영수증·SQLite 적용 기록은 변경하지 않는다. 원본 백업과 선택된 변환 파일도 수정하지 않는다.
- `classification.json`은 원본 전체의 두 단계 분류·해시·목적지·공개 범위와 기존 테스트 이력을 구분한다. `posts/`는 회원 게시판 후보만 담는다. 게시글 외 자료는 해당 목적지에 남겨 중복 게시하지 않는다.
- 게시글 후보의 `authorId`는 NULL, `authorName`은 확인된 원작성자다. `importData`에는 schemaVersion·platform·containerId·sourceId·boardPath·url·originalCreatedAt·timePrecision을 담고, 실제 쓰기 시점의 importedAt은 적용 도구가 채운다. created_at·updated_at도 실제 대상 생성 시각으로 채우고 published_at은 원작성 시각으로 유지한다.
- 본문에 작성자·날짜·출처 안내를 합성하지 않는다. 원문 자체에 있는 해당 표현은 제거하지 않는다. 학술 대상의 첫 문단은 일반 텍스트 `#학술`이며 본문 전체 보존 대조와 별도로 추가 여부를 확인한다.
- 입력 해시는 원본 JSON·확정 목적지·선택 첨부 해시·변환 도구 버전으로 계산한다. 같은 ID·입력 해시·결과 파일 해시를 가진 변환물만 재사용하고 바뀐 항목만 재생성한다. 개별 실패는 원본 ID·실패 단계·실제 판정 근거를 남겨 분리하며 성공 후보의 준비는 계속한다.
- 적용 도구의 원본 판별은 import_data의 플랫폼·컨테이너·원본 ID로 한다. 본문 URL 검색으로 동일 글을 판정하지 않는다. 메타데이터 없는 과거 테스트 글은 자동 갱신·삭제·원복하지 않는다. 실행 영수증은 새 파일로 남기며 데이터 적용은 별도 실행 지시에서 한다.

게시판은 50건 단위 이어보기를 제공하며 카테고리·가림 보기별로 목록을 구분한다. 공개 글은 게시일(없으면 생성일) 내림차순·ID 내림차순, 가린 글은 수정일 내림차순·ID 내림차순으로 정렬한다. API 배열 응답 계약은 유지하고 limit·offset을 검증해 적용한다. 이는 고정 스냅샷 조회가 아니므로 목록 열람 중 신규 작성·삭제가 있으면 새로 불러와 정렬을 갱신한다.

도구의 인자·환경·명시적 리셋·전체 카탈로그 반영·영수증은 [일회성 이관 도구 런북](../runbooks/community-migration.md)을 따른다.

## 자료별 개발 반영 방식

개발 posts 전체와 종속 댓글은 리셋 후 최종 게시글을 넣는다. 사진첩은 최종 카탈로그로 전체 교체하고 연결 사진을 저장·대조하며 기존 파일을 물리 삭제하지 않는다. 연혁·역대회장·역대임원·수상자 등 공개 역사관은 기존 Notion·공식·동문회 자료를 보존하고 확정 카페 자료를 반영한 최종본을 사용한다. 과거 인사말·회칙은 문서·링크만 추가하고 현행 내용을 교체하지 않는다. 역사관 전체 리셋이나 반복 증분 이관 기능은 만들지 않는다. 결과는 원본 170건 중 반영 168건·제외 2건을 원 게시판별로 집계하며 한 원문에서 파생된 연혁·수상 항목 수와 구분한다.
