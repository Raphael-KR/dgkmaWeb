# 긴급 보안 개선 설계

## 목적

`roadmap.md`의 긴급 과제 중 운영 정책이 확정된 다음 세 항목을 함께 처리한다.

- P0 관리자 API 보호
- P0 결제 기록 보호
- P1 개인정보 로그 제거

부고 API 접근 정책은 운영 공개 범위 결정이 필요하므로 이번 구현에서 제외한다.

## 확정 정책

- 모든 `/api/admin/*` 요청은 로그인한 관리자만 실행할 수 있다.
- 비로그인 요청에는 `401`, 로그인했지만 관리자가 아닌 요청에는 `403`을 반환한다.
- 실제 결제 연동 전까지 `POST /api/payments`의 기록 작성 주체는 관리자다.
- 본인 또는 관리자가 납부 내역을 조회하는 기존 `GET /api/payments/user/:userId` 정책은 유지한다.
- 동문 원본 행, 이름, 전화번호, 주소, 이메일, 생일, 사용자 객체를 서버 로그에 기록하지 않는다.
- DB 스키마와 프로덕션 데이터는 변경하지 않는다.

## 인증 구조

### 공통 미들웨어

`server/auth-middleware.ts`에 관리자 인증을 담당하는 미들웨어를 둔다. 미들웨어는 세션의 `userId`만 신뢰하고 요청 본문이나 URL의 사용자 식별자를 권한 판단에 사용하지 않는다.

처리 순서는 다음과 같다.

1. `req.session.userId`가 없으면 `401`을 반환한다.
2. 세션 사용자 ID로 저장소에서 사용자를 조회한다.
3. 사용자가 없으면 만료되거나 유효하지 않은 세션으로 보고 `401`을 반환한다.
4. `isAdmin`이 참이 아니면 `403`을 반환한다.
5. 관리자이면 다음 핸들러로 진행한다.
6. 사용자 조회 중 예외가 발생하면 민감정보 없이 오류 종류만 기록하고 `500`을 반환한다.

테스트에서 DB 없이 동작을 검증할 수 있도록 사용자 조회 함수를 주입받는 `createRequireAdmin` 팩터리를 제공하고, 실제 서버에서는 `storage.getUser`를 연결한 `requireAdmin`을 사용한다.

### 적용 범위

`server/routes.ts`에서 관리자 라우트를 등록하기 직전에 `app.use("/api/admin", requireAdmin)`을 등록한다. 이렇게 하면 현재 다섯 개 관리자 API뿐 아니라 같은 경로 아래 추가되는 향후 API에도 기본 보호가 적용된다.

현재 보호 대상은 다음과 같다.

- `GET /api/admin/pending-registrations`
- `PATCH /api/admin/pending-registrations/:id`
- `POST /api/admin/sync-alumni`
- `GET /api/admin/sync-progress`
- `GET /api/admin/test-google-sheets`

`POST /api/payments`에는 `requireAdmin`을 라우트 미들웨어로 직접 적용한다. 실제 결제 승인 콜백을 도입할 때는 관리자 세션 API와 별도의 콜백 경로 및 서명 검증 정책을 설계한다.

## 개인정보 로그 정책

### 제거 대상

다음 데이터 또는 이를 포함한 객체를 `console` 출력 인자로 전달하지 않는다.

- Google Sheets 헤더와 원본 행
- 동문 이름, 휴대전화번호, 일반 전화번호, 주소, 이메일, 생일
- 카카오 인증 요청 본문과 생성·조회된 전체 사용자 객체
- 동문 레코드와 가입 신청의 `userData`

현재 실행 경로인 `server/routes.ts`, `server/google-sheets.ts`, `server/storage.ts`를 정리한다. 현재 import되지 않는 `server/google-sheets-old.ts`도 이후 재사용 시 같은 문제가 되지 않도록 동일 기준을 적용한다.

### 허용 대상

운영 진단에 필요한 다음 정보는 기록할 수 있다.

- 처리 시작·완료 단계
- 전체·성공·건너뜀·오류·중복 건수
- 필요한 경우 일부만 남긴 마스킹 사용자·레코드 식별자
- 설정값의 존재 여부
- 예외의 클래스 이름처럼 데이터 값을 포함하지 않는 오류 종류

카카오 OAuth의 기존 디버그 로그는 `DEBUG_KAKAO_AUTH=true` 게이트를 유지하되, 전체 키·토큰·인가 코드·사용자 개인정보를 출력하지 않는 기존 원칙을 보존한다.

## 오류 응답

- 인증 실패 응답은 기존 한국어 메시지 형식을 유지한다.
- 권한 거부 응답에는 사용자 존재 여부나 관리자 판정 상세를 노출하지 않는다.
- 관리자 인증 내부 오류는 `500`과 일반적인 메시지만 반환한다.
- 기존 각 API의 입력 검증 및 업무 오류 응답은 변경하지 않는다.

## 테스트

별도 테스트 프레임워크를 추가하지 않고 Node 내장 `node:test`와 기존 `tsx`를 사용한다.

### 관리자 미들웨어 단위 테스트

- 세션이 없으면 `401`이고 사용자 조회를 호출하지 않음
- 세션 사용자를 찾지 못하면 `401`
- 일반회원이면 `403`
- 관리자이면 `next`를 한 번 호출
- 사용자 조회가 실패하면 `500`이고 원본 오류 객체를 로그에 넘기지 않음

### 라우트·로그 회귀 검사

- `/api/admin` 라우트 그룹에 공통 미들웨어가 적용됐는지 확인
- `POST /api/payments`에 관리자 미들웨어가 적용됐는지 확인
- 서버 소스의 민감 로그 패턴이 다시 추가되지 않았는지 확인

테스트 명령은 `npm test`로 제공하고, Replit에서 다음 검증을 순서대로 수행한다.

```bash
npm test
npm run check
npm run build
```

## 배포 검증

코드 반영 후 Replit 개발 워크스페이스에서 자동 테스트, 타입 검사, 프로덕션 빌드를 통과시킨다. Republish 후 실제 세션을 이용한 다음 검증은 운영 데이터 변경을 최소화해 수행한다.

1. 비로그인 `/api/admin/sync-progress` 요청이 `401`
2. 일반회원 요청이 `403`
3. 관리자 화면의 가입 승인·명부 동기화·진행 조회가 정상 동작
4. 비로그인 및 일반회원 `POST /api/payments` 요청이 각각 `401`, `403`
5. 관리자 결제 기록 생성이 `201`
6. 실행 로그에 동문 원본 행과 개인정보가 나타나지 않음

관리자 결제 생성 검증은 중복 또는 허위 납부 기록이 남지 않도록 테스트 대상을 정한 뒤 수행하고, 필요하면 생성한 테스트 레코드를 프로덕션 SQL 콘솔에서 확인 후 삭제한다.

## 문서 갱신

구현과 Replit 검증이 끝나면 다음 문서를 갱신한다.

- `roadmap.md`: 코드 확인이 끝난 항목과 프로덕션 검증이 필요한 항목을 구분
- `walkthrough.md`: 관리자·결제 보안 검증 절차 추가
- `CHANGELOG.md`: 긴급 보안 변경을 `Unreleased`에 기록

`roadmap.md`의 항목을 `기능 검증 완료`로 바꾸는 시점은 Republish 후 완료 조건을 실제로 확인한 뒤로 제한한다.

## 제외 범위

- 부고 목록·상세·파싱의 공개 범위 변경
- 가입 불일치 정책 변경
- 실제 결제 업체 연동, 웹훅 서명, 환불·취소 처리
- PostgreSQL 기준 명부 일원화
- DB 스키마 또는 seed 변경
- 관리자 화면의 기능 또는 디자인 변경

## 완료 조건

- 모든 `/api/admin/*`가 비로그인 `401`, 일반회원 `403`, 관리자 성공 정책을 공유한다.
- `POST /api/payments`가 관리자 외 요청으로 결제 기록을 만들지 못한다.
- 기존 본인 납부 내역 조회와 관리자 기능이 유지된다.
- 명시된 개인정보와 원본 데이터가 서버 로그에 출력되지 않는다.
- 자동 테스트, TypeScript 검사, 프로덕션 빌드가 Replit에서 통과한다.
- Republish 후 프로덕션 검증 결과가 운영 문서에 반영된다.
