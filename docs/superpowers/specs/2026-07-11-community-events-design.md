# 경조사 통합 시스템 설계

## 목적

현재 부고 전용 기능을 회원용 경조사 시스템으로 확장한다. 한 화면에서 경조사 원문과 링크를 입력하고 결과를 확인한 뒤 게시하며, 같은 화면 아래에서 기존 경조사 목록을 확인한다.

경조사 유형은 다음 네 가지다.

- `obituary`: 부고
- `wedding`: 결혼
- `opening`: 개원
- `other`: 기타

## 확인된 현재 상태

- `/o`, `/o/new`, `/o/:id`와 부고 API는 구현되어 있다.
- 모바일 하단 메뉴에는 부고 진입점이 없고 사이드 메뉴는 열기 동작이 없어 일반 사용자가 부고 화면을 찾기 어렵다.
- 홈의 URL 등록은 서버가 요구하는 `text` 대신 `url`을 보내고, 파싱 결과를 카테고리 없는 게시글로 만들려 하므로 현재 정책과 맞지 않는다.
- 기존 파서는 전달된 문자열만 정규식으로 분석하며 외부 URL 본문을 가져오지 않는다.
- 기존 `obituaries` 테이블은 부고 전용 필드가 필수라 결혼과 개원을 함께 저장하기 어렵다.

2026-07-11 조사에서 외부 부고 링크의 상태는 다음과 같았다.

- Funein: 서비스 종료 메시지만 반환
- 우리부고: 발인 후 확인 불가 메시지만 반환
- 기품: 공개 화면은 남아 있지만 해당 공개 API는 빈 응답
- 애도: 발인 후에도 공개 HTML에 부고 본문과 구조화 가능한 정보가 남음

따라서 링크 수집은 성공을 보장하지 않는 보조 입력이어야 한다.

## 선택한 구조

### 통합 데이터 모델

새 `community_events` 모델을 사용한다. 게시글 카테고리나 부고 전용 테이블에 다른 유형을 억지로 넣지 않는다.

공통 필드:

- ID와 작성자 ID
- 경조사 유형
- 상태: `draft` 또는 `published`
- 제목
- 행사 일시
- 장소
- 관련 동문
- 연락처
- 계좌 정보
- 사용자가 붙여넣은 원문
- 출처 URL
- 유형별 세부 정보 `details`
- 생성·수정·게시 시각

`details`는 유형별 엄격한 검증 스키마를 사용한다. 새 초안과 게시 요청의 알 수 없는 세부 키는 모두 거부하며, 임의 JSON을 그대로 저장하거나 게시하지 않는다. 기존 데이터 이관 행만 `LegacyObituaryDetails`를 허용한다.

### 부고 세부 정보

필수:

- 고인 이름과 나이
- 회원과 고인의 관계: 본인, 부친, 모친, 빙부, 빙모, 시부, 시모, 자녀
- 발인 날짜
- 장례식장과 빈소

선택:

- 마음 전하실 계좌
- 모바일 부고장 URL
- 회원 직함
- 별도 유가족 연락처
- 장지와 상주

회원 이름, 졸업 기수, 학번, 회원 등급, 회원 연락처는 서버의 회원 정보에서 채우고 게시 전에 확인한다. 요청 본문의 다른 사용자 ID나 등급을 신뢰하지 않는다.

### 세부 정보 계약

- `obituary` 초안은 기존의 엄격한 부고 세부 정보 필드를 사용하며, 초안 단계에서는 모든 필드가 선택이다. 게시에서는 위 부고 필수 정보를 모두 요구한다.
- `wedding`, `opening`, `other`의 초안과 게시 세부 정보는 동일한 엄격한 `{ memo?: string }` 계약을 사용한다. `memo`는 선택이고 앞뒤 공백을 제거하며 5,000자 이하여야 한다.
- 결혼·개원·기타 게시 요청에서 세부 정보를 생략하면 `{}`로 처리한다.
- 데이터베이스의 `details` 타입은 부고 세부 정보, 메모 세부 정보, 이관된 레거시 부고 세부 정보의 유니온으로 유지한다. 물리 컬럼 또는 SQL 스키마 변경은 필요 없다.

### 다른 유형

결혼, 개원, 기타는 공통 초안과 게시 흐름 및 위 메모 세부 정보 계약을 먼저 제공한다. 유형별 필수 필드와 표준 게시문은 실제 예시를 받아 별도 지침으로 확장한다.

## 화면과 라우팅

정식 경로는 `/events`다.

### 2026-07-14 승인 화면

기본 화면은 경조사 입력과 전체 목록을 짧게 보여준다. `등록 도구를 항상 보인다`는 전체 상세 양식을 펼쳐 둔다는 뜻이 아니라, 유형 선택·원문 입력·등록 명령을 첫 화면에서 바로 찾을 수 있다는 뜻이다.

상단 등록 입력:

- 화면에 항상 노출한다.
- 유형 선택은 `부고`, `결혼`, `개원`, `기타` 분할 제어를 사용한다.
- `경조사 등록` 소제목과 별도 설명 문구를 표시하지 않는다.
- 문자와 링크를 함께 붙여넣을 수 있는 입력을 유형 선택 바로 아래에 둔다.
- 입력 옆 또는 모바일에서는 입력 아래에 선택 유형에 맞춘 `부고 등록`, `결혼 등록`, `개원 등록`, `기타 등록` 명령을 제공한다.
- 기본 상태에서는 유형별 상세 필드, 미리보기, 임시저장 상태와 초안 삭제 명령을 표시하지 않는다.

등록 내용 확인:

- 등록 명령을 누르면 원문을 분석한 뒤 같은 화면의 입력 아래에만 확인·수정 영역을 연다. 모달, 접이식 메뉴 또는 별도 등록 경로를 사용하지 않는다.
- 자동 입력 결과, 누락 필드, 유형별 상세 필드와 부고 미리보기는 확인·수정 영역이 열린 동안만 표시한다.
- 자동 저장은 확인·수정 영역이 열린 뒤에만 동작하고, 닫아도 입력과 초안은 보존한다.
- 확인 영역의 취소 또는 닫기는 게시하지 않고 영역만 닫는다. 초안 삭제는 별도의 명시적 명령으로 유지한다.
- 최종 `게시` 성공 시 확인 영역을 닫고 입력을 초기화하며 아래 전체 목록을 즉시 갱신한다.

하단 목록:

- 등록 입력 바로 아래에 모든 유형의 게시된 경조사를 함께 표시한다.
- `전체`, `부고`, `결혼`, `개원`, `기타` 목록 필터를 표시하지 않는다. 등록 유형 선택과 목록 필터가 입력 위아래에 중복되지 않게 한다.
- 목록은 최신 게시 순서를 유지하고 각 행의 유형을 라벨로 구분한다.
- 등록 성공 시 목록을 즉시 갱신한다.

진입점:

- 게시판 상단에 `경조사` 버튼을 둔다.
- 홈의 고장 난 부고 URL 등록 도구는 제거하고 `/events` 진입 버튼으로 바꾼다.
- `/o`는 `/events?type=obituary`로 리다이렉트한다.
- `/o/new`는 `/events?type=obituary&compose=1`로 리다이렉트한다.
- `/o/:id`는 명시적인 레거시 부고-이벤트 조회가 생길 때까지 기존 레거시 상세 경로로 유지한다.

모든 목록, 상세, 파싱, 초안, 등록 API는 로그인 회원 전용이다. 공개 `/about/condolence` 안내 페이지는 유지한다.

## 파싱 흐름

1. 사용자가 경조사 유형을 선택한다.
2. 서버가 입력에서 일반 텍스트와 URL을 분리한다.
3. 일반 텍스트를 유형별 파서에 전달한다.
4. 공개 URL을 안전하게 가져올 수 있으면 HTML에서 본문 텍스트와 공개 메타데이터를 추출한다.
5. 원문과 링크 본문을 합쳐 초안 필드를 제안한다.
6. 링크를 읽지 못하면 원문만 사용하고 경고를 반환한다.
7. 파싱 결과, 누락 필드, 링크별 수집 상태를 화면에 표시한다.
8. 사용자가 수정하고 필수값을 채운 뒤 게시한다.

사용자가 선택한 유형이 기준이다. 자동 분류 결과가 유형을 임의로 바꾸지 않는다.

## 외부 URL 보안

프로덕션 URL 수집기는 일반 공개 페이지를 안전하게 읽는 최소 기능만 제공한다.

- `http`와 `https`만 허용
- URL 사용자 정보와 비표준 목적지는 거부
- localhost, 사설 IP, link-local, loopback, 클라우드 메타데이터 주소 차단
- DNS 결과와 모든 리다이렉트 목적지를 재검증
- 짧은 연결·전체 제한시간 적용
- 응답 크기와 `text/html`, `text/plain` MIME 제한
- 쿠키, 로그인, CAPTCHA 우회, TLS 위장, 브라우저 JavaScript 실행 금지
- HTML 스크립트·스타일을 제거하고 텍스트만 파서에 전달
- 외부 본문을 신뢰하지 않는 데이터로 취급

`insane-search`는 개발 중 공개 자료를 조사하는 개인 Codex 스킬로만 사용하고 애플리케이션 의존성이나 운영 수집기에 포함하지 않는다.

## 초안 자동 저장

- 초안은 로그인 회원 ID에 귀속한다.
- 입력과 파싱 결과를 변경할 때 지연 저장한다.
- 사용자는 마지막 초안을 복구하거나 삭제할 수 있다.
- 게시 성공 시 상태를 `published`로 전환한다.
- 다른 회원의 초안을 읽거나 수정할 수 없다.
- 필수값이 빠진 초안은 저장할 수 있지만 게시할 수 없다.

## 표준 부고문 생성

[부고문 작성 지침](../../obituary-writing-guide.md)의 템플릿을 서버에서 생성한다.

- 선택 정보가 없으면 해당 줄을 출력하지 않는다.
- 본인상은 `#부고 #동문본인상`으로 시작한다.
- 회원 직함은 회원 등급 뒤 괄호에 표시한다.
- 게시 전 최종 결과를 사용자에게 미리 보여준다.
- 필수 정보가 빠지면 누락 항목을 반환하고 게시를 거부한다.

## 마이그레이션

1. 새 테이블과 유형별 검증 스키마를 추가한다.
2. 기존 `obituaries`를 `obituary` 유형의 게시 상태 이벤트로 복사한다.
3. 원본 ID와 새 ID 대응을 검증한다.
4. 새 목록·상세 API와 화면을 전환한다.
5. 기존 경로를 호환 리다이렉트로 유지한다.
6. 프로덕션 검증과 복구 절차가 확인되기 전에는 기존 테이블을 삭제하지 않는다.

## 테스트

- 네 유형 값과 유형별 입력 검증: 부고 초안의 부분 필드, 결혼·개원·기타 메모의 trim·5,000자 제한, 새 초안·게시 요청의 알 수 없는 세부 키 거부
- Notion 부고 예제의 이름, 관계, 나이, 발인, 빈소, 연락처, 계좌 추출
- 필수 부고 정보 누락 시 게시 거부
- 본인상과 회원 직함의 표준 게시문 생성
- 원문만, URL만, 원문과 URL 혼합 입력
- 공개 HTML 성공, 종료 메시지, 빈 응답, 제한시간 초과의 fallback
- 사설 IP, 리다이렉트 우회, 과대 응답, 잘못된 MIME 차단
- 비로그인 API `401`
- 초안 소유권과 자동 저장·복구·삭제
- 기존 부고 마이그레이션 건수와 필드 대응
- 등록 후 동일 화면의 목록 갱신
- 기존 `/o` 주소 호환

## 단계

1. 문서·필드·DB 마이그레이션 설계
2. 통합 모델과 기존 부고 마이그레이션
3. 간결한 등록 입력, 점진적으로 열리는 확인 영역, 전체 목록과 초안 자동 저장
4. 정규식 기반 부고 파서와 표준 게시문
5. 보안 URL 수집과 실패 fallback
6. 결혼·개원·기타 유형별 지침과 파서 확장
7. 알림톡·SMS, 화환, 결제는 별도 프로젝트로 진행

## 완료 조건

- 회원이 `/events`에서 네 유형을 선택해 초안을 저장하고 게시할 수 있다.
- 유형 선택·원문 입력·유형별 등록 명령과 전체 경조사 목록이 기본 화면에 보인다.
- 상세 필드와 미리보기는 등록 명령을 누른 뒤에만 같은 화면에 표시된다.
- 입력 위아래에 중복 유형 메뉴 또는 목록 필터가 없다.
- 부고 필수 정보와 표준 게시문이 작성 지침과 일치한다.
- 공개 링크를 읽지 못해도 원문 입력으로 작성이 중단되지 않는다.
- URL 수집이 SSRF와 과대·비텍스트 응답을 차단한다.
- 기존 부고 데이터와 주소가 보존된다.
- 비로그인 API 요청은 `401`이다.
- Replit 테스트, 타입 검사, 빌드와 Republish 후 실제 회원 흐름이 검증된다.
