# dgkmaWeb 릴리스

## 대상과 기준

프로젝트 저장소 안의 `.agents/skills/dgkma-release/`에서 사용하는 스킬이다. 전역 스킬로 복제하거나 다른 저장소에 적용하지 않는다. 작업 사본의 Git 최상위 경로와 `origin`이 `Raphael-KR/dgkmaWeb`인지 확인한다. 로컬·같은 저장소의 worktree·Replit 개발 사본을 구분한다.

최신 전역 지침과 [프로젝트 AGENTS.md](../../../AGENTS.md)를 읽는다. 다음 문서가 정본이다. 스킬의 요약보다 현재 사용자 결정과 최신 기준 문서를 우선한다.

- [replit.md](../../../replit.md): 현재 적용 상태, 환경 구분, 릴리스 버전 관리 규칙, 배포, 장애 확인 순서. 실행 전에 해당 절을 읽는다.
- [검사 카탈로그](../../../docs/runbooks/feature-checks.md): 공통 필수·변경 영향별 선택 검사와 목적·명령·환경·부수 효과·결과 재사용 기준. 검사를 선택하기 전에 읽는다.
- [CHANGELOG.md](../../../CHANGELOG.md): 실제 포함할 미배포 변경과 후보·배포 기록.
- [제품·개발 계획](../../../docs/product/planning-proposal.md): 변경 범위·접근 경로·권한·입출력 계약을 판단할 때 해당 정책을 읽는다.
- [구조와 보존 계약](../../../docs/architecture/project-structure.md): 변경 코드의 소유 위치·실제 소비자·동적 의존성과 호환성 보존 근거를 검토할 때 읽는다.
- [DB 운영 런북](../../../docs/runbooks/database-operations.md)과 [스키마 기준서](../../../docs/reference/database-schema.md): DB 변경이 포함될 때만 추가로 읽는다.

현재 버전, 다음 버전, 후보 SHA, deployment ID나 접속 대상을 이 스킬에 고정하지 않는다. 실제 파일·Git·Replit 상태와 기준서에서 확인한다.

## 요청 범위 확인

1. 현재 요청과 이어지는 승인 기록에서 실행 단계와 사용자 제한을 확인한다. 이 프로젝트의 **전체 릴리스**는 [기본 범위](../../../replit.md#전체-미커밋분과-git-마무리)에 따라 전체 미커밋분 커밋·push·PR·main 병합과 후속 기록, 세 환경 main 일치·브랜치 정리를 포함한다. 같은 범위를 반복 승인받지 않는다. `릴리스 준비`나 스킬 수정은 실행 요청이 아니며, `PR·배포`만 요청한 경우 main 병합으로 확대하지 않는다. 운영 DB·실계정 QA의 별도 승인 경계는 유지한다.
2. 로컬·GitHub·Replit의 브랜치·HEAD·작업 트리를 대조한다. 전체 릴리스에서는 로컬·Replit의 staged·unstaged·untracked 프로젝트 변경을 이번 세션 작성 여부와 관계없이 모두 검토해 후보에 포함한다. 사용자 제한과 비밀정보·개인 설정·캐시·빌드·로그·무관한 사용자 자료의 제외 이유를 기록한다. 사본 간 다른 수정을 덮어쓰지 않으며, 제외 파일을 삭제하거나 stash로 숨겨 완료 상태를 만들지 않는다. Replit SSH는 개발 워크스페이스이며 운영 인스턴스 셸이 아니다.
3. 필요한 단계의 승인이 없으면 독립적으로 가능한 후보·차이·적용 조건을 먼저 준비한다. 해당 경계를 넘기 직전에 구체적인 대상·영향과 승인이 필요한 근거를 설명한다. 스킬 생성·수정이나 과거 완료된 릴리스는 새 배포 승인이 아니다.

## 변경 범위의 코드·문서 정리

[릴리스 전 정리와 검증](../../../replit.md#릴리스-전-정리와-검증)을 먼저 읽고 다음 순서로 진행한다. 이번 변경과 직접 영향받는 사용처를 대상으로 하며 관련 없는 전수 정리로 확대하지 않는다.

1. 마지막 실제 배포 소스와 후보를 비교한다. 승인된 staged·unstaged·untracked 변경까지 포함해 변경 전후를 읽고 기준 SHA와 후보 SHA/tree 또는 작업 사본의 파일 해시를 기록한다.
2. 대체된 함수·이벤트 연결·라우트·UI·CSS·테스트를 찾아 `rg` 등으로 실제 사용처를 추적한다. import/export뿐 아니라 동적 import·이벤트 등록·DI·템플릿/동적 클래스·외부 주입 경로도 확인한다. **Lint 통과나 검색 결과 0건을 사용처 검토의 대체 근거로 삼지 않는다.**
3. 변경으로 불필요해졌고 사용처·호환성 보존 이유가 없는 코드와 연결을 함께 정리한다. 관련 테스트·정적 검사·CI의 삭제·수정·보존은 아래 검사 정리 절차를 따른다.
4. 기존 저장 데이터를 읽는 코드와 실제 소비자가 있는 호환 export·동적/peer 의존성·외부 주입 계약은 보존한다. 어떤 데이터 형식·소비자·호출/등록 위치 때문에 필요한지 근거를 남긴다. 미확인은 미확인으로 기록하며 막연한 미래 호환성을 보존 사유로 만들지 않는다. 기존 권한·보안·저장 계약과 사용자 자산의 보존 경계를 유지한다.
5. 담당 기준 문서를 먼저 갱신하고 바뀐 기능의 설명·경로·명령·참조를 맞춘다. 현재 문서의 중복·낡은 내용은 정리하고 원본·결정·마이그레이션·릴리스 이력은 현재 정책과 구분해 보존한다.

## 불필요·중복·과잉 검사 정리

코드·문서 정리 뒤, 최종 후보 검증 전에 [검사 정리 기준](../../../replit.md#불필요중복과잉-검사-정리)을 적용한다. 이번 변경과 영향받는 경로만 대상으로 하며 무관한 검사 체계 개편은 별도 작업으로 남긴다.

1. 관련 테스트·정적 검사·실제 CI의 목적, 막는 위험, 적용 대상, 입력·환경·실패 유형, 중복, 실행 범위·빈도·비용과 차단 조건을 검토한다. 비용은 기존 실행 기록을 우선 사용하며 없으면 미측정으로 남긴다. 매번 전체 목록이나 별도 성능 측정을 요구하지 않는다.
2. 폐기된 기능만 검사하는 항목은 제거하고, 과도한 구현 세부사항 의존은 **확정된 기능·보안·저장 호환 계약**을 기준으로 수정한다. 현재 코드의 오류를 기대값으로 만들지 않는다. 기존 기능·저장 호환성·보안·실제 회귀와 필요한 내부 제약을 보호하는 검사는 근거를 확인해 유지한다.
3. 같은 위험·실패 유형을 같은 조건에서 확인하는 검사는 보호 범위를 유지하며 통합한다. 같은 기능이라도 입력·환경·실패 유형이 다르면 중복으로 단정하지 않는다. 상위 명령에 포함된 검사의 반복 실행과 검사 자체의 중복을 구분하고, 실제 사용 중인 독립 실행 명령은 보존한다.
4. 과도한 범위·빈도·차단 조건은 실제 영향에 맞게 축소하거나 경고로 전환한다. 막는 위험·대체 검사·남는 검증 공백을 근거로 판단하며 비용·번거로움이나 실패 이력이 없다는 이유만으로 불필요하다고 판단하지 않는다. 실패를 숨기려고 검사를 삭제하거나 결과를 무시·성공 처리하지 않는다.
5. 기준을 바꾸면 담당 문서·공통 검사·명령 연결·실제 CI 설정을 함께 맞추고 기존 외부 변경 승인 경계를 유지한다. 관련 CI가 없으면 새로 만들지 않고 외부 설정의 미확인을 없음으로 단정하지 않는다. 개정된 기준의 필수 검사는 정리한 최종 후보에서 수행하며 아래 완료 보고에 변경·유지 근거와 검증 공백을 남긴다.

## 후보 준비와 Git 통합

[개발 반영과 릴리스 동기화](../../../replit.md#개발-반영과-릴리스-동기화)를 구분한다. 개발 중에는 로컬 변경을 Replit에 직접 반영해 검사하며 중간 변경마다 커밋·push하지 않아도 된다. 아래 검사 전 반영은 파일 단위 개발 작업이고, main 병합 후 반영은 GitHub 후보의 Git 동기화다.

먼저 마지막 실제 배포와 **전체 릴리스 후보**의 앱 산출물 영향을 대조한다. 앱에 포함되지 않는 문서·개발 도구만 바뀌었다면 [앱 배포가 없는 변경](../../../replit.md#앱-배포가-없는-변경)에 따라 버전 변경·버전별 CHANGELOG 이동·앱 테스트/빌드·운영 배포·새 태그 단계를 생략한다. 필요한 정적 검사 후 요청된 Git 통합과 아래 Git 마무리로 종료한다. 이번 요청이 문서 수정이어도 후보에 미배포 코드가 포함돼 있다면 이 경로로 처리하지 않는다. 별도로 요청한 동일 소스·Secret 설정 재배포는 기존 재배포 규칙을 따른다.

1. [버전 번호와 정본](../../../replit.md#버전-번호와-정본)에 따라 GitHub의 번호 태그·마지막 실제 배포·패키지 버전을 대조한다. `archive/*`는 제외한다. 여러 변경은 가장 큰 SemVer 증가 기준을 적용하며, 앱에 포함되지 않는 문서·개발 도구만 바뀌면 앱 버전을 유지한다.
2. 버전 변경이 필요한 후보는 Replit 프로젝트 루트에서 확정한 `release_version`으로 다음 명령을 실행한다. 루트 `package.json`, lockfile 최상위와 루트 패키지의 버전을 대조하고 기존 `APP_VERSION` import를 유지한다. 설계 미리보기 패키지는 변경하지 않는다.

   ```bash
   npm version "$release_version" --no-git-tag-version --ignore-scripts
   ```

3. `CHANGELOG.md`의 `미배포 (Unreleased)` 중 실제 포함하는 항목만 `X.Y.Z — 배포 준비`로 옮긴다. **버전을 바꿀 때마다 변경 내용·증가 이유를 기록하고 패키지·lockfile·변경 기록을 같은 릴리스 PR로 Git에 남긴다.** 이미 배포된 기능을 새 변경으로 다시 넣지 않는다.
4. 코드·문서·검사 기준과 버전·변경 기록 수정을 마친 후보가 Replit 개발 사본에 반영됐는지 대조한 뒤 아래 최종 후보 검증을 수행한다. 양쪽의 다른 변경을 보존하고 검사한 소스를 파일 해시 또는 후보 tree로 식별한다. 일상 개발의 최소 정적 검사 규칙으로 필요한 릴리스 검증을 생략하지 않는다.
5. Replit에서 수정한 버전 파일 등도 커밋할 후보에 포함한다. `codex/` 작업 브랜치에서 검토한 커밋 대상 전체를 빠짐없이 커밋하고, 요청 범위의 push·PR·main 병합을 순서대로 수행한다. PR에는 변경 결과·제거 항목과 사용처 근거·보존 이유·문서 정리·검사·DB/Secret 적용 조건·미검증 범위를 적는다. 병합 후 실제 배포할 **main 후보 SHA와 tree**를 기록한다.
6. 직접 반영으로 남은 변경을 Git 통합 대상과 대조하고 기존 작업을 보존한 뒤 **GitHub main 후보를 Replit에 Git으로 동기화**한다. 검사한 소스·조건과 같으면 결과를 재사용하고 병합·후속 수정으로 달라졌다면 영향받는 검사만 다시 수행한다. `Published your App` 커밋은 별도 SHA일 수 있으므로 배포 후보와 tree를 비교하고 기존 이력을 보존한다. 이 비교는 아래 Git 마무리의 최종 main SHA 일치 확인을 대신하지 않는다. 별도 개발 서버 재시작은 릴리스 준비에 자동으로 붙이지 않는다.

## 최종 후보 검증

[릴리스 규칙](../../../replit.md#최종-후보-검사)과 [검사 카탈로그](../../../docs/runbooks/feature-checks.md)를 적용한다. 검사 명령표를 스킬에 복제하지 않는다.

1. 마지막 실제 배포와 최종 후보의 변경·직접/간접 소비자를 기준으로 공통 필수 검사와 영향받는 선택 검사를 정한다. 코드 릴리스의 lint·서식·앱 타입/경계·배포 빌드와 문서 확인은 카탈로그의 적용 조건을 따른다. 앱 산출물이 달라지지 않는 문서·스킬 변경에는 관련 정적 검사만 선택한다.
2. 선택한 기능 검사 파일·목적·선택 이유·실행 명령·환경·부수 효과를 기존 릴리스 기록에 적는다. top-level import·fixture·환경 접근을 확인한다. 선택 조건이 충족된 검사는 필요하며, 목록에 있다는 이유만으로 모든 검사를 실행하지 않는다. 공통 변경의 영향을 좁힐 근거가 없으면 관련 영역 또는 일반 회귀 전체로 확대한다. DB·브라우저·외부 호출과 합성 자료 생성은 해당 승인 경계를 유지하며 실계정 QA는 보류한다.
3. [결과 재사용 기준](../../../docs/runbooks/feature-checks.md#결과-재사용-기준)으로 검사 입력·의존성·설정·도구·환경 일치를 대조한다. 유효한 기존 결과에는 원래 소스/범위·환경·일시·로그와 현재 일치 근거를 연결한다. 병합·후속 수정·버전 변경이 영향을 주면 해당 검사만 다시 수행한다. 상위 명령에 포함된 검사와 같은 최종 후보의 빌드를 중복 실행하지 않는다. DB 상태·브라우저 빌드 조건·새 deployment는 각각의 재사용 제한을 적용한다.
4. Replit의 최종 후보에서 필요한 검사를 수행하거나 유효 결과를 재사용한다. 통과·경고·실패·미실행·해당 없음과 재사용 여부를 구분한다. 관련 있지만 승인 부족으로 보류한 검사를 해당 없음으로 바꾸거나 skip·미실행·실패를 통과로 보고하지 않는다. 필요한 차단 검사의 문제는 해당 배포 범위에만 적용하고, 기존 검사로 확인하지 못한 경로는 미검증으로 남긴다.

## Replit 운영 배포

[배포 절차](../../../replit.md#배포)의 승인된 단계만 실행한다.

1. DB 변경이 있으면 런북에 따라 운영 대상·preview·코드 호환·적용 순서를 준비하고 승인된 변경만 적용한다. [DB 복구·백업 기본 정책](../../../docs/runbooks/database-operations.md#db-복구백업-기본-정책)에 따라 개발·운영 모두 Replit의 7일 복구를 기준으로 삼고 별도 백업을 기본으로 만들지 않는다. 별도 백업은 해당 작업에서 명시적으로 요청·승인된 경우에만 생성한다. 개발 DB 전환을 운영 적용으로 간주하지 않는다. DB 변경이 없는 릴리스에는 직접 DB 작업을 추가하지 않는다.
2. 현재 제공되는 Replit `publish_app` 또는 확인된 CLI 경로를 우선 사용한다. 직접 Publishing GUI가 필요하면 전역 GUI 승인 규칙을 적용한다. 웹 DB 스키마 검토가 요구되면 승인된 SQL 범위를 확인하며 다른 경로로 우회하지 않는다.
3. 새 deployment ID와 실제 상태 전환·배포 성공을 확인한다. 과거 success, 게시 커밋 생성, 명령 접수만으로 성공을 선언하지 않는다.
4. Republish 후 승인 범위의 비로그인 HTTP·canonical·회원 API의 401과 후보 정적 자산 해시를 확인한다. 공개 페이지 대상은 현재 공통 정의 `shared/public-pages.ts`와 변경 범위에서 정한다. 삭제한 과거 URL 목록이나 오래된 검사 건수를 그대로 재사용하지 않는다. 이 확인을 화면 상호작용·실계정 QA로 보고하지 않는다.

## 태그와 완료 기록

[배포 커밋과 완료 기록](../../../replit.md#배포-커밋과-완료-기록)에 따라 마무리한다.

1. 새 배포 성공과 요청된 운영 smoke를 확인한 뒤, Git 게시가 승인된 릴리스의 `vX.Y.Z` annotated tag를 **실제 배포 소스와 tree가 일치한 main 후보 커밋**에 붙인다. 기존 같은 이름의 태그는 대상을 확인하고 강제로 이동·덮어쓰지 않는다.
2. 해당 릴리스 태그만 push하고 GitHub·로컬·Replit에서 같은 커밋을 가리키는지 확인한다. 보존 태그를 일괄 push하지 않는다. GitHub Releases 게시글은 요청된 경우에만 작성한다.
3. `CHANGELOG.md` 후보 제목을 실제 성공일의 `X.Y.Z — YYYY-MM-DD`로 바꾼다. KST 일시와 버전·태그·후보 SHA/tree·PR·Replit 게시 커밋·deployment ID·검사/미실행 범위·DB/Secret 변경 여부를 `docs/history/`에 기록하고 `replit.md`의 현재 적용 상태를 갱신한다. Secret 값은 기록하지 않는다.
4. 완료 기록은 앱 산출물에 영향 없는 문서 전용 후속 커밋으로 GitHub main에 반영하고 아래 Git 마무리를 수행한다. 이 커밋을 위해 다시 배포하거나 태그를 옮기지 않는다. 최신 main과 실제 운영 후보 SHA가 다르면 각각 보고한다.
5. 실패한 단계만 미완료로 남기고 가능한 독립 작업은 계속한다. 배포 전 실패한 후보는 같은 소스·버전으로 재시도할 수 있다. 운영 반영 후 코드·의존성·배포 설정 등 앱 산출물에 영향을 주는 변경은 **새 버전의 후보 준비 → 필요한 검사 → Git 통합·Replit 동기화 → 배포**로 돌아간다. 승인 범위 밖이거나 배포하지 못한 변경은 미배포·미완료로 보고한다. 같은 소스나 Secret 설정만 바뀐 재배포는 기준서의 재배포 규칙을 따른다. 자동 롤백은 하지 않는다.

## 전체 미커밋분·main 일치·브랜치 정리

전체 릴리스의 마무리로 [Git 완료 조건](../../../replit.md#전체-미커밋분과-git-마무리)을 적용한다. 준비·문서 수정 요청에서는 실행하지 않으며 명시적인 보존·범위 제한을 우선한다.

1. 작업 중 추가된 변경의 앱 영향을 먼저 구분한다. 배포 후 앱에 영향을 주는 변경은 위 새 버전 절차로 처리하고 문서 마무리에 섞지 않는다. 앱 산출물에 영향 없는 후속 기록은 커밋·push·main 통합으로 마무리한다. 로컬·Replit의 Git 관리 대상 미커밋분이 남지 않았는지 확인하고 제외한 로컬 전용 파일은 별도 보고한다.
2. Replit 게시 커밋의 내용·부모 관계를 확인하고 소스를 바꾸지 않는 게시 이력을 정상 병합 또는 fast-forward로 공유 main에 연결해 보존한다. 실제 코드 차이는 승인된 후보와 대조해 처리한다. 후속 기록을 포함한 GitHub main을 로컬·Replit에 fast-forward하고 main을 checkout한다. 강제 push·hard reset으로 이력을 맞추지 않는다.
3. 로컬·Replit의 로컬 브랜치와 프로젝트 GitHub 원격에서 main 외 브랜치를 정리한다. 병합 여부·고유 커밋·열린 PR·활성 worktree·stash·진행 중 작업을 확인한다. squash 병합은 PR·변경 내용도 대조한다. 미병합 고유 작업은 확정된 릴리스 범위에 통합하거나 승인된 위치의 보존 태그·번들로 원본 커밋의 복구 가능성을 확인한 뒤 참조를 제거한다. 처리 방침이 불명확하거나 진행 중인 항목만 판단을 요청하고, 정리를 위해 배포하지 않을 코드를 main에 합치거나 worktree·사용자 파일을 강제 삭제하지 않는다.
4. 원격 삭제 후 stale remote-tracking ref를 prune하고 실제 원격 refs를 다시 조회한다. **로컬 HEAD·main = Replit HEAD·main = GitHub 서버의 main SHA**, 두 작업 사본의 Git 관리 대상 미커밋분 0건, 세 곳 모두 main 외 브랜치 0개를 확인한다. 오래된 origin/main이나 tree 일치로 대신하지 않는다. origin/HEAD와 보존 태그는 브랜치와 구분한다.
5. 최종 SHA와 삭제·보존 근거, 남은 예외를 보고한다. 미완료 항목이 있으면 main만 남았거나 전체 동기화가 끝났다고 보고하지 않는다. 실제 배포 후보·태그·deployment ID는 최종 main과 구분한다. 앱 산출물에 영향 없는 문서·게시 메타데이터의 Git 마무리를 위해 재배포하지 않는다.

## 완료 보고

사용자에게 버전·증가 이유, 변경 요약과 [CHANGELOG.md](../../../CHANGELOG.md)·수행 기록의 정확한 경로를 제공한다. 다음 상태를 구분한다.

- 전체 미커밋분의 commit·push·PR·main 병합과 후속 기록 반영
- 개발 후보의 직접 파일 반영, 검사한 소스와 Git 동기화 후 배포 후보의 대조 결과
- 로컬·Replit·GitHub main의 최종 SHA, 두 작업 사본의 미커밋·제외 파일, 남은 브랜치와 삭제·고유 작업 보존 근거
- 실제 운영 후보 SHA/tree·deployment ID·Republish·운영 smoke, 태그 생성·게시
- 제거한 코드·이벤트 연결·UI·CSS·테스트와 사용처 확인 근거
- 보존한 항목과 구체적인 데이터 호환성·실제 사용 근거, 맞춘 문서·참조
- 삭제·통합·축소·경고 전환한 검사와 이유, 유지한 검사의 보호 근거, 남은 검증 공백
- DB/Secret 변경 여부, 카탈로그에서 선택한 검사와 선택/미선택 이유, 실제 명령·대상·부수 효과·최종 소스 식별자·도구/설정·실행일·환경·결과 및 재사용 출처와 일치 근거, 미완료 단계와 다음 조치

같은 제거·보존·문서·검사 정리 근거와 실행 결과를 기존 릴리스 수행 기록에 남기고 주요 제거·호환성 변화는 CHANGELOG에도 요약한다. 검사 명령·선택 조건을 바꿨다면 기존 검사 카탈로그를 갱신하고 목록·결과 대장을 별도로 복제하지 않는다. 정리할 항목이 없으면 검토 범위와 함께 없다고 적는다. 준비만 요청됐다면 준비한 결과와 실행하지 않은 단계를 보고한다. 태그나 문서가 있다는 이유로 운영 배포·검증을 완료로 표시하지 않는다.
